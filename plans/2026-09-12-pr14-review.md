## 2. 架构导览

### 2.1 四个插座（宿主服务，`src/host/`）

| 服务 | 能力 | 备注 |
|---|---|---|
| `files` | readTree / readText / writeText / pickFolder / assetUrl / onFsChanged | Tauri 绑定构造注入（`host/files.ts:16-21` 是真绑定，全前端少数合法 import `@tauri-apps` 的位置之一） |
| `windows` | currentLabel / create(root?) / fetchRoot / confirmDialog / guardClose | 57 行小服务；guardClose 语义 = 脏时弹原生确认、用户拒绝才 preventDefault（`host/windows.ts:52-56`）——但多守卫并存会互相短路 → §6.7 |
| `workspace` | root + activeFile 双状态；setRoot / openFile | setRoot 同时清 activeFile 并补发 file-opened(null)（`host/workspace.ts:27-32`，观看插件据此自动清空）；同值 setRoot 也全量广播（重新选同一文件夹时树重读，无害；树自带的"刷新"按钮不走这里，直接调自己的 reload） |
| `slots` | UI 槽位注册（topbar.left / sidebar.tree / main.viewer） | 同一槽允许多个渲染者、各自子元素、按注册序（`host/slots.ts:7-9`）——doc-markdown 与 doc-video 共存 main.viewer 靠这个 |

基础件两枚——

**`emitter.ts`：25 行手写广播站（发布-订阅）**。服务层不 import cordis（测试可裸 `new WorkspaceService()` 直接用），事件机制因此自带：`on(key, fn)` 把订阅者加进 Map 集合并返回一张"退订券"，`emit(key, payload)` 把该频道订阅者依次喊一遍；泛型参数锁死 payload 类型（`emit("file-opened", 123)` 编译不过）。真实链路举例：Rust 落盘广播 `fs://changed` → FilesService 桥接转发 `emit("fs-changed")`（`host/files.ts:35-37`）→ 树插件经 `onFsChanged` 收到重读（`host/files.ts:71`）；插件卸载时用退订券退订（`view-filetree/index.ts:78` 的 `offFs()`）。`workspace.events.on("file-opened", ...)` 是同一套的第二个用户。（换成成熟 emitter 包的提议已评估并否决，见 §6.8）

**`context.d.ts`：插座面板的标签纸（纯类型，零运行时）**。接线是一动一静两半边：

- **动**（真插电）：`bootstrap.ts:52-55` 的 `ctx.reflect.provide("files", files)`——在登记表记下"名字→实例"（cordis 的 Context 是 Proxy，取 `ctx.files` 时查表，`vendor/cordis/src/reflect.ts:63`；登记在 :177）、广播"电来了"让等依赖的插件激活（boot 审计等的正是这个）、返回拔插头销毁券
- **静**（标签纸）：本文件 `declare module "cordis"` 声明合并，把 `files: FilesService` 等四个键并进 cordis 的 `Context` 接口——没有它 `ctx.files` 运行时正常但 tsc 报错；反过来 `provide` 的类型签名（`K extends keyof this`）能通过检查也靠这张标签
- 插件头上的 `inject: [...]` 是报名表兼访问凭证：没声明就取服务，cordis 直接拒（"cannot get property without inject"）

### 2.2 装载三件套（`src/loader/`）

- **table.ts:21-27**：静态花名册，五个内置插件 id → 模块 + 默认配置
- **manifest.ts:21-53**：读 app 配置目录 `plugins.json`；首启缺失则按表生成全 enabled 默认清单并回写（:48-52）；JSON 损坏或行形状不对逐行点名抛错（:36-45），残缺行不会伪装成"禁用"
- **boot.ts:10-26**：按清单激活；id 不在表里点名抛错（:15）；等 50ms 后逐个查 fiber 状态，非 ACTIVE 点名抛错（:20-25）——注入没就位/激活抛异常都是启动即响，不默默挂

### 2.3 五个内置插件（`src/plugins/`）

| 插件 | inject | 占的槽 | 一句话 |
|---|---|---|---|
| app-shell | files, workspace, slots | —（提供槽容器） | 画栅格 topbar+sidebar+main、mount 三槽（:51-53）、无 root 时欢迎态（:55-74） |
| app-windows | files, windows, workspace, slots | topbar.left | "新建窗口"携带当前 root；"打开文件夹…"只换本窗 root（:14-27） |
| view-filetree | files, workspace, slots | sidebar.tree | 树 + 展开/折叠；点文件 → workspace.openFile |
| doc-markdown | files, windows, workspace, slots | main.viewer | 预览/编辑（CodeMirror 6）、脏标记、Ctrl+S、关窗守卫、读写失败错误条 |
| doc-video | files, workspace, slots | main.viewer | activeFile 是视频时渲染 `<video controls>`（asset protocol），否则清空自己（:15-25） |

插件之间互不认识，只通过 workspace 事件与 slots 槽位间接握手。

### 2.4 Rust 壳（`src-tauri/`）

- `lib.rs:21-44`：文件类型由扩展名单一分派点判定（markdown / video / other）
- `lib.rs:49-72`：walk_dir 递归整树；目录排前、同级大小写不敏感排序；**不跟随符号链接**（列出但不递归，杜绝循环，有测试覆盖）
- `lib.rs:87-91`：write_text_file 落盘后广播 `fs://changed`（payload = 路径），各窗口据此重读
- `windows.rs:8-26`：窗口注册表 label→root，**全局唯一权威**；create_window 失败回滚登记（:42）；manifest 原子写 tmp+rename（:80-82）
- `lib.rs:105-113`：窗口销毁时清注册表并广播 `win://closed`

为什么 root 记在 Rust：F5 刷新后前端内存清零，bootstrap 重启时凭 label 问回原 root（`src/bootstrap.ts:57`）。

## 3. 数据流走查（主线剧本）

检视时照这条链在代码里走一遍，每步都给了锚点：

1. **首启**：webview 起来 → `bootstrap()`（`src/bootstrap.ts:41`）建 cordis Context、四服务 provide、files.start() 桥接 `fs://changed`（`host/files.ts:33-37`）→ 凭窗口 label 问 Rust 要 root（:57）→ 读 manifest（首启自动生成全默认）→ `boot()` 逐插件激活 + 审计
2. **开文件夹**：点"打开文件夹…"（app-windows 或欢迎态按钮）→ `files.pickFolder()` 系统对话框 → `workspace.setRoot(root)` 广播 **root-changed**
3. **树出现**：view-filetree 听 root-changed（`view-filetree/index.ts:65`）→ 清展开态、readTree、渲染；目录行点击切换展开/折叠（:44-48），文件行点击 → `workspace.openFile(node)` 广播 **file-opened**
4. **文档打开**：doc-markdown 听 file-opened（`doc-markdown/index.ts:134`）→ `files.readText` → 预览渲染；失败则清空正文 + 错误条（:113——不留上一个文档的内容）
5. **编辑与脏标记**：切"编辑"建 CodeMirror；每次输入 `editText` 更新状态、标题栏出现 `●`（paintChrome :58-62）
6. **保存**：Ctrl+S / 按钮 → `files.writeText` → Rust 写盘 + 广播 `fs://changed`（`lib.rs:89`）→ 本窗与**其它窗口**的文件树都听到（`view-filetree/index.ts:70-72`）重读 → 脏标清除
7. **多窗口**：点"新建窗口"携带当前 root → Rust 注册表登记 win-N → 新 webview 走同一 bootstrap；各窗可独立开不同文件夹
8. **关窗**：doc-markdown 脏状态下注册了关窗守卫（:129-132），弹原生确认；窗口销毁 → Rust 清注册表 + 广播 `win://closed`
9. **F5**：前端状态全丢 → bootstrap 重启 → 凭 label 问注册表要回 root → 回到原文件夹

## 6. 检视关注点（讨论题）

逐条讨论，结论填"结论"栏后再分流到 §7。预判 = 我的初步看法，供拍砖。

### 6.1 装载静默等待是固定 50ms

- **位置**：`src/loader/boot.ts:19`
- **现象**：`await new Promise(r => setTimeout(r, 50))` 后才查 fiber 状态
- **问题**：慢机器/大量插件时 50ms 不够 → 误报"未激活"（fail-loud 变误伤）；反之等待过长拖慢启动
- **预判**：五插件现状大概率够用；cordis fiber 有状态可轮询/可等待完成，固定延时是权宜。可接受为 Phase 1 已知欠账，或列为 fast-follow 改显式等待
- **结论**：

### 6.2 视图全量重建：编辑器销毁重建丢 undo 历史

- **位置**：`src/plugins/doc-markdown/index.ts:64-104`（render 每次 `host.replaceChildren()` + `editor?.destroy()`）
- **现象**：预览↔编辑每次切换都销毁并重建 CodeMirror；文件树每次重读也是全量重建
- **问题**：① 编辑↔预览来回切，undo 栈丢失；② 树全量重建丢滚动位置（展开态存在 Set 里所以不丢）
- **预判**：Phase 1 范围内可接受（文本本体在 DocState 里不丢，丢的只是 undo 栈与滚动位置）；树在保存/外部变更时全量重读在大库上有性能尾巴，可记 Phase 2 议题
- **结论**：

### 6.3 读失败清空正文

- **位置**：`src/plugins/doc-markdown/index.ts:113`
- **现象**：读文件失败时正文清空 + 顶部错误条，不保留上一个文档内容

- **预判**：宁可空也不给"内容与文件名不符"的假象，方向正确；错误条 + 返回树再点即可恢复

### 6.4 fs-changed 前缀匹配误伤

- **问题**：卸载语义不完整；但 app-shell 事实上单例（禁用即无壳），无实际触发路径
- **预判**：接受，注释或 owning note 里记一句即可

### 6.7 多个关窗守卫并存会互相短路

- **位置**：`src/host/windows.ts:52-56`；短路根源在 Tauri 包装层——`onCloseRequested` 的实现是"await 处理器 → 自己没 preventDefault 就 `destroy()`"（已核对 `node_modules/@tauri-apps/api/window.js`）
- **现象**：每次 guardClose 都注册一个独立监听，各自独立判定。两个守卫 A、B 并存且都脏时：关窗 → **两个原生确认框同时弹出**；用户在 A 选"取消"（A preventDefault），但 B 脏且用户路径放行或 B 不脏从不 preventDefault → B 的 wrapper 照样 destroy——**A 的拦截被短路，窗口照关**
- **问题**：实际语义是"任一守卫放行即关"，与直觉的"全部放行才关"（AND）相反；Phase 3 外置插件进场后多守卫的概率上升
- **预判**：当前唯一注册者是 doc-markdown（单守卫），无实害，不阻塞本 PR。修法明确：WindowsService 内收敛为单监听 + 多谓词 AND 合成（任一拒绝即拦截），属服务层小改；建议登记为 Phase 2/3 前置欠账
- **结论**：

### 6.8 emitter.ts 自写 vs 引入成熟 emitter 包（已决：保留自写）

- **提议**：检视中提出——用主流、高 star、无环境依赖、可打包进产物的 emitter 包替代 25 行自写 `src/host/emitter.ts`
- **候选实测**（2026-09-12；零传递依赖 / 零 `node:` 引用四者全过 `verify:dep-audit` 红线，技术上均合规）：

| 包 | stars | 月下载 | 否决/匹配点 |
|---|---|---|---|
| mitt | 11.9k | 1.17 亿 | `on` 返回 `void`，退订另调 `off`——契约不匹配，引入即需 adapter |
| eventemitter3 | 3.5k | 5.89 亿 | `on` 返回 `this`（链式）非退订券——同上 |
| emittery | 2.1k | 1.77 亿 | `on` 返回退订券✓，但 `emit` **异步**——破坏 setRoot 的同步双广播时序（root-changed → file-opened(null)） |
| nanoevents | 1.6k | 438 万 | 契约全匹配（退订券/同步/泛型），但社区最小，"成熟度"收益为零 |

- **论证**：① 全库 6 处 teardown（`offRoot` / `offFs` / `offSlot` / `offFile` / `offGuard`）依赖"`on` 返回退订券"，最主流的 mitt 恰不满足——换成 mitt+adapter 后 25 行变"依赖 + 10 行包装"，行数不省依赖白加；② 本仓库加依赖的流程成本（dep-allowlist 登记 + dep-audit + 背书 + Note）是刻意摩擦，对此文件 ROI 为负；③ 25 行的全部复杂度是一个 `Map<string, Set>`，不存在需要外部库兜底的 bug 空间；④ emittery 异步 emit 属语义退步
- **结论**：**已决（2026-09-12）：先不换，保留 `emitter.ts` 自写**。将来事件需求扩张（once / wildcard / 跨 fiber 等）再评估 mitt + 薄 adapter 路径（届时走 dep-allowlist 登记 + simplification Note），重评估以本节数据为起点

### 6.9 emitter 无错误隔离（外置插件时代的饿死风险）

- **位置**：`src/host/emitter.ts:21-23`（emit 循环无 per-订阅者 try/catch）
- **现象**：同频道任何一个订阅者抛错，循环中断，后续订阅者收不到本次通知
- **问题**：现状订阅者全是宿主与内置插件（出错即 bug，fail-loud 合理）；Phase 3 外置插件进场后，一个第三方监听器的异常可能饿死排在它后面的内置插件通知（如 fs-changed → 文件树不再刷新），且难以归因
- **预判**：Phase 3 开放订阅面之前加固——emit 内逐订阅者 try/catch 并把错误显式上抛/记日志；改动约 3 行 + 一条测试。当前不阻塞本 PR
- **结论**：

### 6.10 外置插件会用 cordis 装载器吗？契约离开装载器会异常吗？（已答：不用 / 不会）

- **问题来源**：检视讨论（2026-09-12），cordis 定位问答的收口一环。前两轮结论铺垫——① cordis 当运行时地基、StudyWiki 做生态产品：**不可行**（生态地基是 Node 进程，装载器 / registry 线被环境无关铁律结构性挡死；dsh 的浏览器层同样退回静态表 + fail-loud stub）；② 当前方案的实际收益：**复用的是契约本体**（三段式契约 / 依赖等待 / 可逆生命周期 / ctx 服务模型），装载器从来不在复用清单里（"取契约、弃装载器"）。本轮问最后一环：Phase 3 外置插件的装载。
- **答 ①：外置插件不用 cordis 装载器，一寸都没用**——Phase 3（`phase3-plugin-authoring` 分支）自建装载缝，`src/loader/external.ts` 的 `loadExternalModule` 约 20 余行：

  ```text
  Rust 命令 read_plugin_module 读插件入口源码（根域校验拒 .. 逃逸）
    → JS 端 Blob → 动态 import(blobURL)   ← 全前端唯一动态 import 点，layering-allowlist.json 单条登记
    → 用后即 revoke                       ← URL 生命周期归零
    → 形状校验（PluginsService：封闭契约全表 + inject 非法形态拒载）
    → 进同一条 manifest/boot 流水线 → ctx.plugin 装上树
  ```

  cordis 生态的 plugin-loader（npm 包解析 / 按 `cordis` 字段找入口 / HMR）全程未参与——它绑 Node API，webview 里既装不进也不该装。选 blob 通道的理由（external.ts 文件头注释转述）：**单文件零依赖契约让 blob 的两个经典弱点——相对导入解析、URL 生命周期——直接归零**；插件要带依赖须在构建期打成单文件（脚手架 `pnpm gen:plugin` 的构建流程）。
- **答 ②：契约没有装载器不会异常，结构性不会**——三层理由：

  1. **vendor 的 cordis 里本来就没有装载器**：九个文件（context / events / fiber / logger / reflect / registry / service / utils / index）grep `loader|import(` **零命中**。生态装载器是独立包，vendor 时就没带走——"没有 cordis 装载器"不是缺件状态，是拿进来的东西本来就不含它。核心 = 契约本体（Context / Fiber / Registry / injector / reflect / 可逆 effect）
  2. **契约的起点是"模块对象"，不问出处**：`ctx.plugin(module, config)` 收一个普通对象（name / inject / apply），静态表 `import` 来的、blob `import()` 来的对它完全同形。装载器在生态里的角色只是"模块对象的供应商"，位于契约**上游**；换供应商不碰契约本身——"取契约、弃装载器"在结构上成立，cordis 自己就把接口开在模块对象上
  3. **实证：两种来源走同一条流水线**：内置插件（静态表）与外置插件（blob）汇入同一 manifest → boot → `ctx.plugin` → inject 等待 → fiber 激活审计，行为无差别。Phase 3 的加固 commit（inject 非法形态拒载 / 根域校验拒 .. 组件）测的就是这条混合流水线

  比喻：**cordis 核心是电路系统，生态装载器是家电物流**。StudyWiki 自建物流——内置件随 bundle 出厂、外置件经 Rust 读文件 + blob 单件验收进屋——电路系统原装未动。
- **接管的看护面**（不是契约异常，是自建物流的长期责任清单；生态 loader+schema 顺手挡掉的错，永远由下面的接管者看护）：

  | 生态装载器原本管的 | StudyWiki 的接管者 |
  |---|---|
  | 包解析 / 入口发现 | 静态模块表（内置）+ `read_plugin_module`（外置） |
  | config schema 校验 | manifest 行级校验 + Phase 3 封闭契约全表 |
  | inject 声明合法性 | inject 非法形态拒载 + 根域校验 |
  | 模块来源信任（npm 装了就信） | 不信——封闭契约验收后才上树 |
  | HMR / 热重载 | 没有；装载在启动期，重载 = 重开窗（离线产品取舍） |
  | 装载完成等待 | 手搓 50ms + 审计（§6.1 在案，已知最糙一环） |

- **结论**：**已答（2026-09-12）**：外置插件复用的是 cordis 的"插座和电路"（契约），物流自建；契约可靠性不依赖装载器——它依赖的模块对象形状与 inject 语义全在 cordis 核心里，而核心是原装的。自建校验面（封闭契约全表 / inject 拒载 / 50ms 审计）为长期维护责任。

### 9.1 `src/host/files.ts` —— 文件通道服务（74 行，本 PR 新增）

**职责一句话**：把五类文件系统能力（读树 / 读文本 / 写文本 / 选文件夹 / 媒体 URL）收进一个类型化门面，是插件层唯一合法的文件通道。

**关键依赖：`@tauri-apps` 是什么**

Tauri **官方** npm scope 的第一方包（非社区第三方，类比 `@angular/core` 之于 Angular）。本仓库运行时仅两个：`@tauri-apps/api@^2.9.0`（core / event）与 `@tauri-apps/plugin-dialog@^2.4.0`；均在 `dependencies` + `dep-allowlist.json` 白名单，vite 构建期打进产物、运行时零下载。dialog 包是官方插件的 JS 半边，Rust 半边 crate 在 `lib.rs:103` 初始化，两侧配对。

比喻：webview 前端被关在玻璃房（沙箱）里——看不见磁盘、弹不了系统对话框、不知道文件变了；Rust 进程在外面什么都能干。这些 import 的函数**自己不干活，只当传话员**：把请求递过 IPC 桥送到 Rust，把结果带回来。逐个对应到本文件：

| 传话员 | 对应方法（本文件） | 传的话 |
|---|---|---|
| `invoke`（:1） | readTree / readText / writeText（:46-59） | 敲门喊命令名 + 递参数，Rust 侧 `#[tauri::command]` 函数接活，结果以 Promise 带回 |
| `convertFileSrc`（:1） | assetUrl（:66） | 绝对路径 → asset 协议 URL（macOS 实际为 `http://asset.localhost/...`）——沙箱默认只准加载打包资源 |
| `listen`（:2） | start()（:34-38） | 订阅 Rust 广播（`fs://changed`，`lib.rs:89` 发出），桥进自家 emitter |
| `open`（:3） | pickFolder（:61） | 原生选文件夹对话框，返回路径或 null（取消） |

这些值导入被 `verify:layering` 锁在 host + bootstrap 三处；插件只能经 `ctx.files.*` 拿到门面，拿不到传话员本人。

**变更代码块分析（对照旧 `src/main.ts`：`git show main:src/main.ts`，本 PR 同时重写该文件）**

```ts
async start() {
```

旧应用是"读一次看一次"，外部改文件无感知。这段是验收项 7（保存后跨窗树刷新）的前半段：Rust 落盘广播 `fs://changed` → 这里收下 → 转发进自家 emitter。为什么不让插件直接 listen Rust 事件：① 事件名解耦（Rust 改名不动插件）；② 退订统一走 emitter 退订券；③ 将来一个 Rust 事件可分发为多个内部频道。`stop`（:40-43）基本只服务测试/对称性——窗口销毁时整个 webview 就没了。

```ts
assetUrl(path: string): string       { return this.#deps.assetUrl(path); }
```

`open` → `pickFolder`、`convertFileSrc` → `assetUrl`：从"框架 API 名"换成"业务语义名"，插件读代码不再需要知道 Tauri 的存在。

**`convertFileSrc` 深看一眼（assetUrl 背后的机关）**——它本身几乎不干活：实现就一行（`node_modules/@tauri-apps/api/core.js:234`），转交 Rust 启动时注入 webview 的函数，纯粹做字符串换算——把"磁盘绝对路径"换成"webview 认识的 URL"。为什么非换不可：webview 遵守浏览器安全模型，`<video src="/Users/.../a.mp4">` 直接塞绝对路径会被拒——不是文件不存在，是"门卫不收这种单子"（`file://` 协议也默认封死）。Tauri 的解法是墙上开一扇专门的取货窗，三步，快递比喻：

1. **开窗**（Rust 侧一次性配置，`src-tauri/tauri.conf.json:24`）：注册自定义协议 `asset://`——`{"enable": true, "scope": ["**"]}`；scope 是白名单（允许读哪些路径），当前全放开，Phase 2 backlog 的"assetProtocol 收紧"就是指把这里缩到只准当前库根
2. **开票**（`convertFileSrc` 的全部工作）：`/Users/x/a.mp4` → `asset://localhost/Users%2Fx%2Fa.mp4`（macOS 形态；Windows/Linux 是 `http://asset.localhost/...`——各平台格式不同，所以用官方函数别手拼）
3. **取货**（真正干活的在 Rust）：`<video src="asset://...">` 发起的请求**不走网络**，被 Rust 协议处理器拦截 → 解码路径 → 查 scope 白名单（不在名单直接 403）→ 从磁盘读字节流 → 像普通 HTTP 响应一样递回 webview → 播放

比喻收尾：磁盘文件 = 仓库里的货；webview = 只收正门正规快递单（允许来源 URL）的门卫；`convertFileSrc` = 开票窗口（自己不搬货）；asset protocol = 传送带（验单、取货、递进门）。

**为什么视频不走 `invoke`**：`invoke` 是一次性 RPC，用它拿视频得把整个文件序列化过 IPC 桥——大文件内存爆炸；asset URL 让 webview 把本地文件当流媒体源（按需读、支持 seek、随播随取）。所以本服务的分工是：**文本小文件走 invoke（readText），大二进制媒体走 asset URL（assetUrl）**——`files.ts` 把两条通道都收进了同一个门面。

**实现思路总结（三行）**：① 收口——四段直呼变一个类，命令名字符串离开 UI；② 增能力——写通道 + 变更流是 Phase 1 新功能（编辑保存 / 跨窗刷新）的服务侧落点；③ 留缝——deps 接口让 Tauri 在测试中可整体替换。这个"接口 + 默认绑定 + 薄门面"三件套是 host 层的通用模式，`windows.ts` 同构复刻。

**检视发现**

- invoke 返回值全部 `as Promise<T>` 断言（:47 / :52 / :57）：类型对齐靠人肉对 Rust 签名——Rust 侧改返回形状，TS 编译**不会**报错，契约由命令目录 / type-equiv 文档层看住。根源在块 ① 的取舍（deps 接口丢泛型）。记为已知弱点，现状可接受
- 其余无发现：74 行职责单一，结构干净

### 9.2 `src/host/slots.ts` —— 槽位注册表（50 行，本 PR 新增）

**职责一句话**：UI 版的"中介所"——壳插件声明**哪里**能放东西（容器），功能插件声明**放什么**（渲染者），本服务负责配对；两边互不认识。

**它解决什么问题（对照旧 `src/main.ts`）**

旧版是一张写死的页面：HTML 里预埋好容器 ID，JS 顶部一把抓过来：

```ts
// 旧 main:src/main.ts（本 PR 删）
const openLibraryButton = document.getElementById("open-library") as HTMLButtonElement;
const fileList = document.getElementById("file-list") as HTMLElement;
const viewer = document.getElementById("viewer") as HTMLElement;
// 然后同一个文件里直接往里塞内容：fileList.appendChild(...)、viewer.replaceChildren()
```

谁往哪放、页面长什么样，全部焊死在一个文件里——五个插件拆开后这个写法立刻失效：文件树插件想把树放进侧栏，但侧栏的 DOM 是壳插件建的，**插件之间不许互相认识**（这是插件化的底线）。槽位注册表就是中间那块公告板：壳说"侧栏有个位置叫 sidebar.tree"，树说"我来画 sidebar.tree"，配对由服务完成。

**变更代码块分析**

**块 ① 类型面（:1-5）——槽名是封闭集合**：

```ts
export type SlotName = "topbar.left" | "sidebar.tree" | "main.viewer";
export type SlotRenderer = (el: HTMLElement) => void;   // "给你一个空盒子自己画"
```

槽名不是随便的字符串——是三个成员的联合类型。插件写 `ctx.slots.register("sidebar.trea", ...)`（拼错）**编译直接红**。加一个新槽 = 改这里 + 壳建对应容器，两处同步、编译器看住。这是刻意收紧的宿主权：UI 骨架由宿主定义，插件只能往既有的孔里填（与 Phase 3 外置插件的封闭契约一脉相承）。

**块 ② register（:14-34）——登记 + 自留地 + 两种时序**：

```ts
register(slot: SlotName, render: SlotRenderer): () => void {
  const list = this.#entries.get(slot) ?? [];
  const el = document.createElement("div");            // ① 每个渲染者分一个自留地 div
  el.className = `slot slot-${slot.replace(".", "-")}`;
  const entry = { el, render };
  list.push(entry);                                     // ② 登记住册序
  const container = this.#containers.get(slot);
  if (container) { container.appendChild(el); this.#render(entry); }   // ③ 容器已在：立刻上墙
  return () => { /* 从数组剔除 + el.remove() */ };      // ④ 退订券
}
```

四个要点：

- **自留地（①）**：不是把渲染内容直接塞进容器，而是每人先分一个专属子 div。效果：`main.viewer` 槽里 doc-markdown 和 doc-video **同时在场、各占一个盒子**，互不覆盖——"同一槽不竞争"的共存设计。谁显示谁隐藏由渲染者自己判断（doc-video：不是视频就把自己画空，见 `doc-video/index.ts:19`）。这是 §6.5 讨论的"软约定"的机制面：服务提供共存，自律靠插件
- **注册序（②）**：同槽内渲染顺序 = 注册顺序 = 模块表顺序，确定的布局
- **时序无关（③）**：容器已经挂好就立刻上墙渲染；还没挂就先排队。这样**壳先挂 / 插件先注册两种顺序收敛到同一结果**——装载顺序不是隐性契约
- **退订券（④）**：与 emitter 同一惯用法，插件 teardown 用

**块 ③ mount（:37-44）——壳独占的另一半**：

```ts
mount(slot: SlotName, container: HTMLElement): void {
  this.#containers.set(slot, container);
  container.replaceChildren();                          // 清场
  for (const entry of this.#entries.get(slot) ?? []) {
    container.appendChild(entry.el);                    // 已登记的逐个重放
    this.#render(entry);
  }
}
```

`register` 是"内容方"的入口，`mount` 是"位置方"的入口——全库只有 app-shell 调它三次（`app-shell/index.ts:51-53`，把运行时建的 topbar/侧栏/主区容器绑上）。注意 `replaceChildren()` 清场后**重放**：重复 mount 同一槽是幂等的重绑，不留旧盒子。

**块 ④ `#render`（:46-49）——每次一个空盒子**：

```ts
#render(entry) { entry.el.replaceChildren(); entry.render(entry.el); }
```

调用渲染者之前先清空它的自留地——渲染函数永远拿到干净盒子，不用自己防"上次画的东西还在"。插件后续的重画（树重读、文档切换）不走这里，是插件自己闭包里重调（如 `view-filetree/index.ts:19` 的 `render()`）。

**实现思路总结（三行）**：① 中介解耦——"位置"（壳拥有）与"内容"（插件提供）经两张登记表（`#entries` 渲染者 / `#containers` 容器）配对，插件互不认识；② 时序无关——register/mount 两阶段设计，谁先到都收敛到同一结果，装载顺序不是隐性契约；③ 共存而非竞争——每渲染者一个自留地 div，同槽多插件叠放、显隐自律，避免了"一槽一主"的竞争驱逐语义。

**检视发现**

- 无缺陷发现：50 行职责单一，清场/重放/退订语义完整，测试对齐在 `tests/host-workspace-slots.test.ts`
- 一个设计层面备注：`SlotRenderer` 只在 register/mount 时被服务调一次，后续重画全靠插件闭包自驱——服务管"进出场"，不管"刷新"。理解插件代码时记住这一点（为什么每个插件 render 里都有 `if (!host) return`——盒子可能还没上墙）

### 9.3 `src/host/windows.ts` —— 窗口通道服务（57 行，本 PR 新增）

**职责一句话**：窗口的"身份证 + 传令兵"——我是哪个窗（身份）、开新窗（创建）、问 Rust 我原来看的是哪个文件夹（恢复）、关窗前拦一道（守卫）。

**变更形态：与前两个文件不同，这是"盖新房"不是"搬家"**

`files.ts` 的前身是旧 main.ts 里的内联调用，`slots.ts` 的前身是写死的页面容器——而 `windows.ts` 在旧代码里**完全没有对应物**：旧应用是单窗口，没有"新建窗口"概念，也没有未保存守卫。它是 Phase 1 新功能（多窗口 / 脏关闭确认 / F5 恢复）的服务侧落点。但结构上刻意**复刻 files.ts 的三件套**（接口 + 默认绑定 + 薄门面）——host 层已经模式化，读通一个就读通全部。

**变更代码块分析**

**块 ① deps 注入缝（:5-19）——同一个模具，四个不一样的绑定**：

```ts
export interface WindowsDeps {
  invoke: (cmd, args?) => Promise<unknown>;
  currentLabel: () => string;                    // 我是谁（窗口身份）
  onCloseRequested: (cb) => Promise<() => void>; // 关窗事件拦截
  confirmDialog: (msg) => Promise<boolean>;      // 原生确认框
}
export const defaultWindowsDeps: WindowsDeps = {
  invoke,
  currentLabel: () => getCurrentWebviewWindow().label,
  onCloseRequested: (cb) => getCurrentWebviewWindow().onCloseRequested(cb),
  confirmDialog: (message) => confirm(message, { title: "StudyWiki" }),
};
```

与 files.ts 同构，但值得看的是三个 Tauri import 怎么变成四个能力：`getCurrentWebviewWindow()` 返回"我所在的这个 webview 窗口"的句柄，从它身上取 `.label`（工牌号）和 `.onCloseRequested`（关窗闸门）；`confirm` 来自 dialog 插件。比喻：files 的传话员都在"往外递话"，这里多了一个"照镜子的"——`getCurrentWebviewWindow` 不出门，只回答"我自己是谁"。

**块 ② 身份：currentLabel（:29-32）**。每个 webview 窗口在 Rust 侧有个唯一工牌（`win-1`、`win-2`…，由 `windows.rs:14-19` 发号）。这个方法就是掏工牌——它是多窗口一切交互的起点：bootstrap 靠它问 Rust"我原来开的是哪个文件夹"（`bootstrap.ts:57`）。

**块 ③ 创建与恢复：create / fetchRoot（:34-43）**——多窗口的一对镜像操作：

```ts
async create(root?: string): Promise<string> { return invoke("create_window", { root }); }
async fetchRoot(label: string): Promise<string | null> {
  const state = await invoke("get_window_state", { label });
  return (state as string | null) ?? null;
}
```

- `create`：让 Rust 发新工牌、登记 root、开新 webview（`windows.rs:29-46`）。注意 root 是可选的——"新建窗口"按钮传当前 root（`app-windows/index.ts:18`），新窗开同一个文件夹；不传则新窗进欢迎态。**新窗跑的是同一份 bundle**，起来后走同一个 bootstrap，所以不需要任何"传内容"的动作
- `fetchRoot`：F5 恢复的关键。webview 的内存是易碎品（刷新即清零），Rust 进程的注册表是耐用品——刷新后前端凭工牌回去问"我原来看的是哪个文件夹"，null 归一为欢迎态。**权威永远在 Rust 侧，webview 只是租客**，这是本 PR 一以贯之的分工
- 返回值 `(state as string | null) ?? null`：Rust 侧两层语义（未登记 = None / 未设 root = Some(None)，见 `windows.rs:96-99` 的测试）在服务这层压平成"null = 欢迎态"——命令的边界语义归一也是服务层的职责之一

**块 ④ 守卫：confirmDialog + guardClose（:45-56）——本文件的心脏**：

```ts
async guardClose(isDirty: () => boolean, confirmDiscard: () => Promise<boolean>): Promise<() => void> {
  return this.#deps.onCloseRequested(async (e) => {
    if (isDirty() && !(await confirmDiscard())) e.preventDefault();
  });
}
```

读法：注册一个关窗监听——关窗瞬间，先做一次**廉价的同步检查**（isDirty，纯内存判断，不打扰用户）；确实脏才弹**昂贵的异步确认**（原生对话框）；用户拒绝放弃才 `preventDefault()` 把关窗拦下来。一行代码里三个时序：同步查 → 异步问 → 可能拦。

设计上的机制/策略分离：服务只提供**机制**（拦截、确认、prevent 的管道），什么算脏、问什么话由插件决定——doc-markdown 的接线（`doc-markdown/index.ts:129-132`）：

```ts
ctx.windows.guardClose(
  () => current?.kind === "markdown" && isDirty(state),           // 策略：md 文档且有脏标
  () => ctx.windows.confirmDialog(`放弃对 ${current?.name} 的未保存修改并关闭？`),  // 策略：问的话
)
```

这正是宿主服务的价值：换一个插件（比如将来的表格编辑器）能用自己的脏判断复用同一条守卫管道。

**注意**：每次 guardClose 都注册一个**独立**的关窗监听，而 Tauri 包装层的语义是"各自判定、任一放行即关"——多守卫并存会互相短路（弹两个框、拦截被绕过）。已核对 `node_modules/@tauri-apps/api/window.js` 的 `onCloseRequested` 实现坐实此点。当前全库只有 doc-markdown 一个注册者，无实害；详见 §6.7。

**实现思路总结（三行）**：① 同构复刻——files.ts 的三件套模具原样再浇一遍，host 层就此定型为模式；② 权威外置——窗口身份与工作区 root 记在 Rust 注册表，webview 凭工牌租用，F5 也冲不掉；③ 机制/策略分离——守卫管道是宿主的，脏判断与提示语是插件的，多插件可各接各的（多注册语义的欠账见 §6.7）。

**检视发现**

- §6.7：多关窗守卫互短路（见讨论点，当前无实害，修法已指明：服务内收敛单监听 + 多谓词 AND）
- 其余无发现：57 行职责单一，与 files.ts 的同构性让认知成本趋近于零

### 9.4 `src/host/workspace.ts` —— 工作区状态店（39 行，本 PR 新增）

**职责一句话**：一个窗口内"现在开着哪个文件夹、正看哪个文件"的**唯一记账处**——私账只留两个写口，每次落账必广播。

**变更形态：前身是旧 main.ts 里的一个裸变量**

```ts
// 旧 main:src/main.ts（本 PR 删）
let entries: LibraryEntry[] = [];     // 模块级裸变量：谁都能改，改了没人知道
```

旧版的状态就这一行——没有任何通知机制，UI 函数直接读它重画。插件化后这不够用：文件树和文档查看器都要对"换了文件夹 / 换了文件"做反应，但它们**不许互相认识**。解法和 slots 同族：把状态和它的变更通知收进一个服务，插件只对状态变化做反应，不对彼此喊话。这个文件因此成为四个服务里唯一**零 Tauri 依赖**的（见思路总结第 ③ 条）。

**变更代码块分析**

**块 ① 两个频道（:4-8）——先定义"世界会发生的两件事"**：

```ts
export type WorkspaceEvents = {
  "root-changed": string | null;   // null = 回到欢迎态
  "file-opened": FileNode | null;  // null = 无活动文件（观看区清空）
};
```

payload 类型带着语义：两个频道都允许 null，且 null 各有明确含义。这是 §2.1 讲过的 typed emitter 的第一个用户。

**块 ② 私账 + 只读窗（:11-24）——状态只能从两个门进**：

```ts
#root: string | null = null;
#activeFile: FileNode | null = null;
readonly events = createEmitter<WorkspaceEvents>();

get root() { return this.#root; }            // 外部只能看
get activeFile() { return this.#activeFile; }
```

`#` 私有字段 + getter：外部**读得到、改不了**，所有写入必须走 `setRoot` / `openFile` 两个门——门里才能保证"落账必广播"这个不变量。对比旧版的 `let entries`：谁都能改、改了没人知道。

**块 ③ setRoot（:26-32）——"换店、清桌、喊两嗓子"**：

```ts
setRoot(root: string | null): void {
  this.#root = root;
  this.#activeFile = null;                    // 不变量：换店必清桌
  this.events.emit("root-changed", root);     // 树听到：清展开态、重读
  this.events.emit("file-opened", null);      // 观看区听到：清空
}
```

两个设计点：

- **不变量内建**：`activeFile` 永远属于当前 root——换了文件夹，上一个文件必然失效，所以清桌写在门里而不是交给插件自觉（忘清就出现"新文件夹的树 + 旧文件夹的文档"鬼画面）
- **补发 file-opened(null)**：观看插件只需订阅自己关心的一个频道，就能同时覆盖"点了别的文件"和"换了文件夹"两种清空场景——不用再订阅 root-changed。同步双发、先树后观看区，顺序确定可预期

另注：**同值 setRoot 也会全量广播**（重新选同一个文件夹 → 树重读一次，无害且可当刷新用）；树自带的"刷新"按钮则不走这里，直接调自己的 `reload()`（`view-filetree/index.ts:33`）。

**块 ④ openFile（:34-38）——对照旧版的"指挥棒"变化最直观**：

```ts
// 旧：openEntry 里直接点名调用者——调用者必须知道"谁负责渲染"
if (entry.kind === "markdown") void renderMarkdown(entry.path);
else if (entry.kind === "video") renderVideo(entry.path);

// 新：只落账 + 喊一嗓子，谁听谁画
openFile(file: FileNode): void {
  this.#activeFile = file;
  this.events.emit("file-opened", file);
}
```

旧版树点文件要**点名** markdown 渲染器和视频渲染器（指挥棒）；新版谁都不认识，只宣布"现在看这个文件"（公告板）。doc-markdown 和 doc-video 各自听 file-opened、各自判断"是不是我的菜"——这就是"插件互不认识"能成立的最后一环：**状态是唯一的中介**。

**实现思路总结（三行）**：① 裸变量 → 私账 + 只读窗 + 双写口——状态有了单一事实源和内建不变量（activeFile 必属当前 root）；② 写口即事件源——每次落账自带广播，插件对状态反应而非对彼此喊话（与 slots 的"公告板"配合，插件间零认识）；③ host 四服务至此分出两类——**传话类**（files / windows：包系统能力，要 Tauri 注入缝）与**记账类**（workspace / slots：纯内存协调，不需要缝）。workspace 是后者的范式。

**检视发现**

- 无缺陷：39 行极简，写口完备、不变量内建、广播顺序确定
- 备注一个"将来可能要长大"的点：状态机目前只有两个频道（root / activeFile），没有"关闭文件""多标签页"的概念——file-opened(null) 只能由换文件夹触发。将来做标签页 / 关闭按钮时，要么加第三个频道，要么给 openFile 加 null 参数；到时这是一个**接口演进点**，好在订阅方都在插件层，改起来集中

### 9.5 `src/host/emitter.ts` —— 微型广播站（25 行，本 PR 新增）

**职责一句话**：全库最小文件、最大架构分量——typed 发布订阅的 25 行实现，host 服务层"框架无关"这块基石就是它。

**变更形态：全新，且旧代码零对应物**

旧 main.ts 没有任何事件概念——UI 更新全是"直接调函数"（点了文件就 `renderMarkdown(...)`）。插件化后"直接调"全面失效（插件互不认识），需要广播站；而宿主服务又**不许 import cordis**（要保持可裸 `new` 的可测性，见 §9.4），cordis 自带的事件系统用不了——于是自己带一个。本文件因此是"服务层框架无关"的前提条件，files（fs-changed 桥）和 workspace（root-changed / file-opened）都站在它上面。

顺带分清两层事件，读插件代码不迷路：`ctx.on(...)` 是 **cordis 的事件**（插件生命周期、内部协议）；`ctx.files.onFsChanged(...)` / `ctx.workspace.events.on(...)` 是 **host 的 emitter**（业务状态流）。两层各管各的，互不串台。

**变更代码块分析**

**块 ① 类型面（:1-8）——"频道表"即类型**：

```ts
export type PayloadMap = Record<string, unknown>;
export interface Emitter<M extends PayloadMap> {
  on<K extends keyof M & string>(key: K, fn: (payload: M[K]) => void): () => void;
  emit<K extends keyof M & string>(key: K, payload: M[K]): void;
}
```

泛型 `M` 是一张频道表（频道名 → payload 类型），`keyof M` 限定 key 只能是表里的名字，`M[K]` 让 payload 类型**自动跟着频道走**。举例（`WorkspaceEvents`，`workspace.ts:5-8`）：

```ts
emit("file-opened", 123)                          // ✗ 编译红：payload 须为 FileNode | null
emit("root-changed", null)                        // ✓ 频道本身就允许 null（欢迎态）
```

拼错频道名、传错 payload 都是**编译错误而不是运行时 bug**——25 行里最值钱的就是这两行泛型。API 面刻意只有 on/emit，连 off/once 都没有（够用即止；引库替代的评估见 §6.8，已决保留自写）。

**块 ② 实现（:12-25）——一个 Map、一层闭包**：

```ts
const map = new Map<string, Set<(p: unknown) => void>>();
return {
  on(key, fn) {
    const set = map.get(key) ?? new Set();     // 频道不存在则建
    set.add(fn);
    map.set(key, set);
    return () => set.delete(fn);               // 退订券：一个闭包
  },
  emit(key, payload) {
    for (const fn of map.get(key) ?? []) fn(payload);   // 没人订阅 = 白喊，不报错
  },
};
```

三个细节，每个都有讲究：

- **为什么用 Set 不用数组**：天然去重（同一函数订两次只算一个听众）、`delete` O(1)；且 Set 按插入序迭代——同频道通知顺序 = 订阅顺序，确定可预期
- **退订券是闭包**：`on` 返回 `() => set.delete(fn)`，闭包捕获 fn 与 set，调用方**不需要持有任何句柄**、也不需要知道内部结构。全库六个 `off*`（`offRoot` / `offFs` / `offSlot` / `offFile` / `offGuard` / slots 的 disposer 同族）全源于这个模式——插件 teardown 的统一惯用法
- **回调里退订是安全的**：Set 迭代中删除的成员不会再被访问（订阅者在自己的回调里自杀不炸）；本库没有"回调里再订阅同频道"的用法，不依赖该边界行为

**实现思路总结（三行）**：① 频道表即类型——泛型把"拼错频道 / 传错 payload"从运行时 bug 前移成编译错误；② 退订券模式——on 返回闭包实现零句柄退订，奠定全库 teardown 惯用法；③ 它是服务层框架无关的基石——没有它，FilesService / WorkspaceService 就得 import cordis 才能发事件，host 层"裸 new 可测"就塌了。

**检视发现**

- **emit 无错误隔离**：`for (const fn of ...) fn(payload)` 里任何一个订阅者抛错，**同频道后面的订阅者全部收不到通知**。现状无害——订阅者都是宿主与内置插件自己的 render/reload，出错本来就是 bug 该响；但 Phase 3 外置插件进场后，一个外置插件的监听器抛错可能**饿死后续的内置插件通知**。建议列为 Phase 3 前的小加固点（emit 内逐订阅者 try/catch，或至少文档声明该边界）→ §6.9
- 其余无发现：25 行无冗余

### 9.6 `src/loader/types.ts` —— 插件契约的形状卡（10 行，本 PR 新增）

**职责一句话**：用 10 行回答"什么算一个插件"——name / inject / apply 三件套 + 可选的清理函数返回值；文件头自称"cordis 插件契约的结构子集"。

**变更形态：全新，且旧世界连这个问题都不存在**

旧 main.ts 里"功能"就是代码本身——侧栏、预览、播放是同一个文件里的一段段函数，没有"功能单元"的边界，自然没有"功能单元长什么样"的契约。插件化的第一件事是把边界画出来：五个内置按同一形状写，Phase 3 的外置插件按同一形状验——**这张卡两头用（作者照着写、装载器照着验）**。

**变更代码块分析**

**块 ① 三件套，各配一句契约注释（:4-9）**：

```ts
name: string;                    // 插件 id：manifest 记账、审计点名都用它
inject?: string[];               // 服务报名表：apply 跑之前等这些服务就位
apply(ctx: any, config: any): void | (() => void);   // 插件本体；返回函数 = 全部效果可逆
```

三个值得看的取舍：

- **为什么是 cordis 的"结构子集"**：cordis 自己的 Plugin 接口很宽（可复用标记、匿名插件、schema 描述……），StudyWiki 只认三件套——收窄即纪律：内置插件不许用宽接口的花活，外置插件的验收面也小到可以逐项机械校验（Phase 3 的"封闭契约全表"正是这张卡的展开，见 §6.10）
- **为什么 ctx / config 都是 `any`**：契约只管"形状存在"，不管参数具体类型——各插件自己 `import type { Context } from "cordis"` 拿精确类型（如 `app-windows/index.ts:1`），类型不收敛在装载器。代价是契约面丢了参数类型检查，收益是外置插件（运行时 blob 来的，本来就没有 TS 类型）与内置插件走**同一张卡**
- **可逆性写进契约**：返回类型 `void | (() => void)`——返回清理函数即"退订券"惯用法的契约根据（§2.1 讲过的全库六个 `off*` 撤销券，源头都在这个返回值）

**实现思路总结（三行）**：① 契约先行——先定义"插件是什么形状"，内置作者与外置验收共用一张卡；② 结构子集——从 cordis 宽接口里只取三件套，验收面小到可机械校验；③ 可逆内建——teardown 不是约定俗成而是契约返回值。

**检视发现**

- 无发现：10 行纯类型，注释即文档（TS 导出带契约注释的门禁要求在此文件上是零成本满足）

### 9.9 `src/loader/boot.ts` —— 点兵与查岗（26 行，本 PR 新增）

**职责一句话**：把账本变成活的插件——逐行激活（`ctx.plugin`）、等全树静置、逐个查 fiber 状态，非 ACTIVE 点名抛错。

**变更形态：旧世界的"启动"是脚本跑到底**

旧 main.ts 没有"启动"这个概念——脚本从 import 跑到 `addEventListener` 绑完监听即就绪，所有功能天然在场，"某个功能没起来"这个状态不存在（失败 = 整个应用白屏）。插件化后功能成了可失败的个体，启动从"跑代码"变成"**点兵（激活）+ 查岗（审计）**"。

**变更代码块分析**

**块 ① 装载器里唯一 import cordis 运行时值的点（:1）**：

```ts
import { Context, FiberState } from "cordis";
```

`FiberState` 是枚举**值**（不是类型）——装载器与 cordis 的直连面全前端只有两处：bootstrap 建 Context（`bootstrap.ts:1`）、这里查 fiber 状态。table / manifest / types 全是纯数据与类型，不碰 cordis——"心脏直连"被压缩到最小面。

**块 ② 点兵循环（:12-18）——三个分支各挡一种情况**：

```ts
for (const row of manifest.plugins) {
  if (!row.enabled) continue;                                   // ① 用户说关：跳过（合法状态）
  const entry = table[row.id];
  if (!entry) throw new Error(`装载失败：清单条目 "${row.id}" 不在静态模块表中`);   // ② id 拼错：点名抛
  const fiber = ctx.plugin(entry.plugin, { ...entry.defaults, ...row.config });  // ③ 激活：用户配置覆盖默认
  states.push({ id: row.id, state: () => fiber.state });        // 记取值器（getter），不是记值
}
```

- 分支 ② 与 manifest.ts 哲学同源：**残缺不许伪装禁用**——手改清单写错 id，宁可启动炸出点名错误，也不静默少一个插件
- config 合并 `{ ...defaults, ...row.config }`：用户值压默认值，没改的字段用出厂设置
- `state: () => fiber.state` 存 getter 是时点语义：fiber 状态是活字段，循环时记快照会全是"刚挂起"，审计必须取"静置之后"的值

**块 ③ 50ms 静置 + 查岗（:19-25）**：

```ts
await new Promise((r) => setTimeout(r, 50)); // 全树静默（注入等待 + 激活）
const stuck = states.filter((s) => s.state() !== FiberState.ACTIVE)
  .map((s) => `${s.id}（state=${s.state()}）`);
if (stuck.length) throw new Error(`装载审计失败：${stuck.join("、")} 未激活——声明的服务未提供？`);
```

为什么要等：inject 是**异步等待**——插件声明的服务没 provide 前 fiber 挂起（不是失败），`ctx.plugin` 返回那一刻状态未定，必须静置后查。审计 fail-loud：卡死的插件点名 + 带状态值 + 给排查方向（"声明的服务未提供？"——最常见原因是 inject 拼错服务名）。固定 50ms 的权宜性与已知风险见 §6.1。

**后续演进（phase3 分支实况，呼应 §6.10）**：骨架未动，长出双轨——boot 多收一个 `loadExternal` 参数、多返一份 `BootReport { loaded, broken }`：`ext:*` 行走 blob 装载缝，坏行（目录缺失 / 入口损坏 / 形状不符 / 审计卡死）**分治隔离**为 broken 点名、不阻断其余插件（外置资源是用户侧状态，不许挡整个应用）；内置行保持 fail-loud 不变。"内置严、外置宽"的双轨正是 §6.10 自建物流的验收现场。

**实现思路总结（三行）**：① 点兵三分支——关 = 跳过、拼错 = 点名抛、正常 = 激活（用户配置盖默认）；② 查岗——静置后逐个验 fiber 状态，非 ACTIVE 点名，"残缺不伪装"哲学的最后一站；③ cordis 直连面最小——装载器四文件只有这里碰运行时值。

**检视发现**

- §6.1 已立案（50ms 固定等待），不重复展开
- 备注一个管辖边界：审计是启动期一次性动作，运行期插件死亡（dispose）不归它管——cordis 可逆 effect 机制接管运行期，属设计内分工，不构成发现

**变更代码块分析（tree.ts——两个纯函数）**

```ts
export function filterTree(nodes, config) {         // 开关式递归过滤 dotfile；flag 关时原样返回（零拷贝）
  if (!config.ignoreDotfiles) return nodes;
  return nodes.filter((n) => !n.name.startsWith("."))
              .map((n) => (n.children ? { ...n, children: filterTree(n.children, config) } : n));
}
export function visibleRows(nodes, expanded) {      // DFS 展平；只在 expanded 的目录里下钻
  const walk = (list, depth) => { for (const node of list) { out.push({ node, depth });
    if (node.children && expanded.has(node.path)) walk(node.children, depth + 1); } };
  walk(nodes, 0); return out;                       // 行序 = 显示序，深度跟着走
}
```

为什么单独成文件：树的"算"与"画"分离——这两个函数不碰 DOM，测试裸调即可穷举（隐藏文件、嵌套展开、深度计算），jsdom 都不用起。immutable 风格（filter/map 返回副本、不 mutation 输入）让调用方无需防御。

**实现思路总结（三行）**：① 算/画分离——过滤与布局是纯函数，渲染只是消费 {node, depth} 行流；② 展开态以 path 为 key，重读存活、换店清空；③ 三订阅对应三种变化源（root / 磁盘 / 槽位），全量重建的取舍见 §6.2。

### 9.15 `src-tauri/src/lib.rs` —— 系统能力唯一入口（修改，85 → 190 行）

**职责一句话**：Rust 壳的总部——文件三命令（读树/读文/写文+广播）、类型分派单一决策点、多窗接线（注册表托管 + 关窗清理）、以及一组可裸跑的纯函数测试。

**变更形态：M——前身是旧版 85 行（两个命令、单窗口、只读）**。旧版的全部家当：`list_library`（平铺清单）+ `read_text_file` + 一个两行的 `run()`。新版三个文件命令、事件广播、窗口接线、64 行测试。逐块对照：

**块 ① 数据形状换形：LibraryEntry → FileNode（:8-16）**

```rust
// 旧：平铺三项清单，只收可打开类型
pub struct LibraryEntry { name: String, path: String, kind: String }
// 新：递归树节点，所有条目都列出
pub struct FileNode { name, path, kind, children: Option<Vec<FileNode>> }
```

`children: Option<Vec>` 而非空数组——区分"文件（无子女概念）"与"目录（子女可能空）"；`#[serde(rename_all = "camelCase")]` 对齐 TS 侧共享类型。这是 read_tree 换形（§9.1 块③）的 Rust 半边。

**块 ② kind 分派链扩容，单一决策点不破（:21-44）**：`kind_for_ext` 逐字保留（新旧测试断言相同），新增 `kind_of` 包装一层"目录判定 + 扩展名分派 + 兜底"。**语义变化**值得注意：旧版对非可打开类型 `continue` 静默跳过（清单里不出现），新版照列不跳、标 `other`——树要展示全貌，"能不能打开"的判断前移给前端（树插件 :49 的 `markdown || video` 分支）。加一种可打开类型的改动面：两行常量 + 一个新查看器插件，决策点仍然唯一。

**块 ③ walk_dir 纯函数化 + 防环（:49-72）**：旧版核心逻辑内嵌在 `#[tauri::command] fn list_library` 里（宏+框架耦合，测试要起整个 Tauri）；新版抽成无宏纯函数，命令只剩一行委托 `read_tree = walk_dir(...)`。三个遍历决策：

- **防环**：目录性取 `read_dir` 条目的 `file_type()`（**不解析符号链接**）——指向目录的 symlink 照样列出（走扩展名分派成 other）但绝不递归。fixture 测试里真的造了一个指向自身根的 self-loop 符号链接验证"能返回即未成环"
- **排序**：`(kind != "dir", name.to_lowercase())` 元组比较——目录排前 + 同级大小写不敏感，一行搞定双规则
- **错误**：逐层带路径原文上抛（`format!("open {}: {e}")`），前端错误条显示的就是 OS 原话

**块 ④ write_text_file + `fs://changed` 广播（:86-91）**：全新——旧版只读不写。`std_write` 又一次纯函数抽取（roundtrip 测试裸跑）。落盘成功后 `app.emit("fs://changed", &path)`，广播**包括写方自己**（files.ts:55 注释明说，自窗树重读一次是设计内）——跨窗刷新的 Rust 半边。

**块 ⑤ run() 接线扩容（:100-125）**：旧版 builder 只挂 dialog 插件 + 2 命令；新版三件事——

```rust

.on_window_event(|window, event| {                        // 关窗：清注册表 + 广播 win://closed
  if let tauri::WindowEvent::Destroyed = event { /* remove + emit */ }
})
.invoke_handler(generate_handler![read_tree, read_text_file, write_text_file,
  windows::create_window, windows::get_window_state, windows::read_manifest, windows::write_manifest])
```

命令从 2 个到 7 个（4 个来自 windows 模块）。事件回调拿不到 State 提取器，经 `app.try_state` 查询、Option 防御。

**块 ⑥ 测试 1 → 3 个（:127-189）**：旧版只有 kind 分派一个测试；新版 fixture 造真目录树（含子目录、大小写混合扩展名、txt、self-loop 符号链接；目录名带线程 id 防并行互删），覆盖排序/防环/写回读。

**实现思路总结（三行）**：① 命令薄壳化——逻辑抽纯函数，`#[tauri::command]` 只做委托，测试不需要 Tauri 运行时；② 数据换形驱动（平铺→树、跳过→other），分派单一决策点不破；③ 新能力（写通道/广播/多窗）全部在 Rust 落根——系统能力与权威状态住外壳，与前端插件化形成分工。

### 9.16 `src-tauri/src/windows.rs` —— 窗口注册表（113 行，本 PR 新增）

**职责一句话**：多窗口的户口所——label→root 注册表（全局唯一权威）、create_window（失败回滚）、get_window_state、外加 plugins.json 的物理读写（§9.8 已详析账本侧）。

**变更形态：全新，旧世界是单窗口、零对应物**。

**变更代码块分析**

**块 ① 注册表与双层语义（:7-26）**：

```rust
pub struct WindowRegistry {
    next: u32,                                        // 单调发号：win-1, win-2, …
    roots: HashMap<String, Option<String>>,           // label → Option<root>
}
pub fn get(&self, label: &str) -> Option<Option<String>> { ... }
```

`Option<Option<String>>` 不是炫技——三层语义各有含义：**未登记 = None**（查无此窗）、**登记未设 root = Some(None)**（欢迎态窗）、**设了 = Some(Some(path))**。测试注释明说"注册表层保留两层语义"，压平（后两者归一为 null）发生在 `get_window_state` 命令层（:54 的 `.flatten()`）——**精确语义住底层、wire 契约住命令层**，这正是 §9.3 块③ 说的"边界语义归一也是服务层的职责"在 Rust 侧的同款纪律。

**块 ② create_window：先登记、失败回滚（:29-46）**：

```rust
let label = state.lock().unwrap().register(root.clone());      // ① 先领工牌登记
if let Err(e) = WebviewWindowBuilder::new(&app, &label, WebviewUrl::default())
    .title("StudyWiki").inner_size(1180.0, 760.0).build() {
  state.lock().unwrap().remove(&label);                        // ② build 失败 → 手动回滚
  return Err(format!("create window {label}: {e}"));
}
```

两个设计点：**先登记再建窗**——新 webview 起来跑 bootstrap 时第一次 `fetchRoot` 就能查到（不留时序窗口）；**手动回滚**的存在理由写在注释里——build 失败的窗口不会触发 Destroyed 事件，lib.rs :105-113 的自动清理路径覆盖不到它。注册表每个登记项都有出口：失败回滚、关窗自动清，两条路闭合。`WebviewUrl::default()` = 同一 bundle——新窗与主窗跑同一份代码、各自 bootstrap（§9.11 块② 的服务侧对应）。

**块 ③ manifest 读写住在这里（:57-83）**：`read_manifest`（NotFound→None = 首启信号）与 `write_manifest`（tmp+rename 原子写）的语义已详析于 §9.8 块①/③，不重复。

**测试两层（:85-113）**：注册表原语层（两层语义 + 发号 + remove）与命令视图层（flatten 压平后的 wire 契约）分开测——块① 的语义设计有测试背书。

**实现思路总结（三行）**：① 权威住外壳——窗口身份与 root 记在 Rust 注册表，webview 凭 label 租用，F5 冲不掉；② 每个登记项有出口——build 失败回滚 + Destroyed 自动清，两条路径闭合；③ 语义分层——精确双层语义住结构体，wire 契约在命令层压平。

**检视发现**

- 一个命名视角的小别扭（非缺陷）：manifest 的物理读写住在 windows.rs——文件名与职责不完全匹配（"窗口"文件管着插件账本）。Phase 3 仍在此；将来 Rust 文件多了可拆 config.rs/fs.rs，顺手事，无实害

### 9.17 `src-tauri/capabilities/default.json` —— 权限面收编（修改）

**职责一句话**：Tauri 2 的能力声明——哪些窗口拿到哪些插件权限；本 PR 只动了一处：窗口名单从单窗扩到通配。

**变更代码块分析（全部 diff 就这一行）**：

```json
- "windows": ["main"],                    // 旧：只盖主窗
+ "windows": ["main", "win-*"],           // 新：主窗 + 所有 win-N 新窗
```

description 同步从 "Main window" 改 "All windows"。两个理解点：

- **为什么必须改**：Tauri 2 里每个 webview 窗口要被 capabilities 覆盖才有插件权限（`core:default` 基础 API + `dialog:default` 选文件夹对话框）。旧名单只有 main——本 PR 新开的 win-N 窗口会**调不动 dialog**（打开文件夹按钮在新窗直接被拒）。`win-*` 通配与 windows.rs 的 `win-N` 发号约定跨文件咬合：**命名约定同时是权限约定**，发号规则一变这里就得跟着变
- **什么没改**：`permissions` 保持两项不动。没有加 `fs:default` 之类宽权限——文件访问仍然只走自定义命令 + asset protocol（description 原话 "File access goes through the two custom commands and the asset protocol"）。权限最小面的一贯纪律：多窗口是扩"谁"，不是扩"什么"

**实现思路总结（三行）**：① 权限跟着窗口走——多窗功能的最小权限改动就是窗口名单加通配；② 命名约定（win-N）与权限声明（win-*）是同一契约的两半；③ 能力面只扩覆盖不扩内容。

**检视发现**：无——一行 diff，职责清晰。
