## 这个 PR 想合入什么

以前 Agent 面板像一个没有分区的会议室：每一件工具调用都站起来大声汇报，审批单还直接插在发言中间；用户真正要看的助手结论被过程噪声淹没。Shell 也只有一个藏在文件栏旁边的细拉手，右侧 Agent 栏连拉手都没有，全局命令、品牌和文件标题都挤在顶栏。

这个 PR 做两件互相关联的事。第一，把 Agent 面板重排成“会议纪要”：一个回合的工具过程先收进一个可展开的抽屉，运行中只显示当前动作，回合结束自动收成一行摘要和耗时；需要用户拍板的审批不再挤进 transcript，而是接管底部 composer——好比收银台暂时变成审批台，批准或拒绝后它又变回输入框，并把你刚才打的草稿原样还回来。第二，把主窗口从三栏改成“固定图标栏 + 两个可折叠抽屉 + 阅读区”：Activity Rail 是大楼一层的服务目录，文件栏和 Agent 栏是两侧可推开的抽屉，宽度和开合状态记在本机 `localStorage`；macOS 把标题栏做成 overlay，让应用内开关与系统红绿灯同一层。

读完应能回答：它解决过程噪声、审批注意力弱和 shell 空间归属混乱；做法是回合折叠 + composer 三态接管 + 四栏几何/持久化 + 槽位别名；代价是 `app-agent` 状态机更复杂、审批接管引入全局键盘与生命周期边界、PR 还携带一个值得单独确认的 ripgrep 依赖面。

## 2. 架构导览

### 2.1 Agent 会话状态机：一个插件，五个事件汇合点

`app-agent` 仍然是右栏插件，不把 `agent-core` 拉进 UI 决策。它订阅三类源头：workspace 的 `file-opened/root-changed`（`index.ts:145-150`）、会话事件 `on(handleEvent)`（`index.ts:553`）、审批事件 `onApproval`（`index.ts:557-561`）。启动时 `queueMicrotask` 先加载模型再开新会话（`index.ts:1083-1089`）；换库根时先递增 generation，再中止并拆绑旧会话（`index.ts:508-531`），异步回来后 generation 不一致就丢弃，避免旧库根的会话飞进新库根界面。

审批接管像“收银台变审批台”。`presentNextApproval` 只在 composer 处于 `normal` 时取出队首，把输入值存进 `savedDraft`，再用 `renderApprovalPrompt` 的根替换 composer 子树（`index.ts:582-598`）。决策后先调用 `session.respond`，transcript 增加一行决策记录，composer 进入 400ms `decided` 短态，随后 `restoreComposer()` 还原草稿并立刻展示下一个审批（`index.ts:602-642`）。全局键盘把 Esc 分层：详情浮层开着只关浮层，否则拒绝；`⌘/Ctrl+Enter` 批准（`index.ts:647-668`）。 outside click 只关详情，不代用户拍板（`index.ts:669-681`）。

回合过程组则像会议纪要的抽屉。`turn-start` 建组，`tool-start/end` 增删/替换工具卡并更新摘要，`turn-end/aborted/error` 分别 settle 成完成、中断、出错（`index.ts:407-470`）。`createProcessGroup.settle` 只在焦点不在组内时收起（`render.ts:258-264`），所以用户正展开检查结果时不会被强行合上。历史渲染按 JSONL 契约只能用 `assistant.toolCalls`，没有工具结果内容就明确显示占位（`index.ts:344-364`）。

### 2.2 Shell 布局：纯函数算几何，DOM 只画结果

`layout.ts` 把规则拆成两层：绝对边界（Files 220–440、Agent 300–520）先在持久化归一化时兜底（`layout.ts:97-119`）；活动窗口边界再由 `maxRailWidth/clampRailWidth` 扣掉 54px Activity Rail、另一栏和 340px 阅读区（`layout.ts:60-83`）。localStorage 读写都被 try/catch 包住，坏 JSON、超版本、非布尔/非数只让对应字段回退，不抛错（`layout.ts:110-153`）。

`index.ts` 每次绘制前都 `constrainState()`，所以窗口变小、隐藏栏重新打开或收到跨窗 storage 后，渲染宽度总会重新让路给阅读区（`index.ts:102-141`）。拖拽用 Pointer Capture 保证指针离开 12px 命中区仍继续；移动只记 latestX 并用 rAF 合帧；`pointercancel` 恢复按下时宽度，`pointerup` 若还有待渲帧则先 flush 再持久化一次（`index.ts:155-234`）。键盘 Home/End 映射到当前约束下的最小/最大值，双击重置默认宽度（`index.ts:215-229`）。

### 2.3 槽位兼容：旧插件的“旧门牌”自动指向新房间

`SlotsService.register` 在入口把 `topbar.left` 归一成 `activity.left`（`slots.ts:9-19,28-40`）；`mount` 仍只接受四个当前槽位（`slots.ts:51-59`）。这相当于旧信封上写“前台”，前台改叫“服务目录”后由收发员自动改投；旧插件不用重编译。Preview 的独立 fake slot service 也调用同一个函数（`preview.ts` diff），避免原型与产品行为漂移。

### 2.4 macOS overlay 与窗口一致性

主窗配置（`tauri.conf.json`）和动态建窗（`windows.rs:115-127`）都把最小内尺寸提升到 920×480，macOS 设置 Overlay、隐藏标题、红绿灯 `(12,12)`。动态窗用 `#[cfg(target_os = "macos")]` shadow builder，避免非 macOS 编译看到平台方法。CSS 给 `.is-macos .topbar` 预留 78px，给按钮设置 no-drag（`styles.css:174-177`），所以左侧开关不会压到系统红绿灯。

## 3. 数据流走查

1. **启动**：shell 创建四栏并 `loadShellLayout()`（`app-shell/index.ts:85,253-259`）。`slots.mount` 把已注册插件挂进容器；旧 `topbar.left` 已被归一，因此与内置命令一起出现在 Activity Rail。
2. **调整窗口**：用户拖 Files 手柄 → Pointer Capture 记录起点 → rAF 调 `setWidth` → `constrainState()` 保证阅读区 ≥340px → pointerup 持久化一次。另一窗收到 `storage` 事件后重读并重绘；若自己也在拖拽则先忽略（`index.ts:317-322`）。
3. **打开 Agent**：右栏隐藏时子树仍挂载，只是宽度为 0 且子内容 `visibility:hidden`（`styles.css:254-262`），所以流式回合和会话状态不丢。`Cmd/Ctrl+B` 切文件栏，`Cmd/Ctrl+Option/Alt+B` 切 Agent 栏（`index.ts:323-329`）。
4. **发送回合**：`sendDraft` 组装文本/附件、清空输入、调用 `session.send`（`index.ts:707-738`）。`turn-start` 建过程组，快照经 rAF 流式渲染，工具事件进组，`turn-end` 收起为摘要。
5. **等待审批**：agent-core 发出 request → `showApproval` 排队 → composer 接管。用户查看详情、批准/拒绝，草稿恢复；第二个审批自动顶上。历史里的已裁决行变只读决策线。
6. **新建动态窗**：Rust 登记 root、授权 asset scope、建窗；macOS 动态窗与主窗同样 overlay/最小尺寸（`windows.rs:101-134`）。新窗前端领取 root 后重建 shell/plugin 状态。

## 5. 讨论点

### 6.1 `@vscode/ripgrep` 是 merge 回归，已从本 PR 移除

- **位置**：merge head `992bead` 的 `package.json:43`、`scripts/dep-allowlist.json:6,21`、`pnpm-lock.yaml:686-1775`；这些行号是修复前事实。
- **现象**：`main` `fba0e1e` 的 `package.json` 没有 `@vscode/ripgrep`；本 PR `992bead` 相对 main 新增了 wrapper、12 个平台 optionalDependencies 和白名单豁免。仓库源码没有任何 `import '@vscode/ripgrep'`；`scripts/provision-ripgrep.mjs` 按 `scripts/ripgrep-manifest.json` 直接 fetch、SHA-256 验证并落位 sidecar，不使用 wrapper 的 `rgPath`。
- **问题**：为什么 merge 保留了切出点旧状态的依赖？现已回退 `package.json`、`pnpm-lock.yaml`、`scripts/dep-allowlist.json`。
- **预判**：从 `fba0e1e` restore 这三个文件；随后跑 `pnpm install --frozen-lockfile`、`pnpm test`、`verify:dep-audit`、`verify:env-independence`。除非有意切换 npm 二进制源，否则不能保留两条供给路径。
- **结论**：merge 回归已定性并已在工作区修复（2026-10-11）：`package.json`、`pnpm-lock.yaml`、`scripts/dep-allowlist.json` 均恢复为 `main` `fba0e1e` 内容；提交动作待用户确认。

### 6.2 审批等待中点“停止”后，composer 可能继续卡在审批态

- **位置**：`src/plugins/app-agent/index.ts:455-461`（aborted 只收过程组）、`741-746`（stopSession）、`573-642`（审批态）、`src/plugins/agent-core/service.ts:320-327`（abort 清 pending）、`src/plugins/agent-core/approval.ts:176-181`（cancelAll 记 unavailable）。
- **现象**：人工审批挂起时 `session.running` 仍为 true，Stop 可见。`session.abort()` 会 fail-closed 取消 pending，并在日志写 `unavailable`，但 app-agent 的 `aborted` 事件不清 `approvalQueue/activeApproval`，也不恢复 composer。用户随后批准/拒绝只是一个 no-op，界面仍演完“已批准/拒绝”。
- **发生场景**：①你让 Agent“整理 `/lib/a.md`，再读取库外 `/tmp/reference.md`”，输入框里还打着下一句“顺便总结成表格”；②Agent 发起越界读审批，composer 变成红色审批台，草稿“顺便总结成表格”被保存，右下主按钮变成“停止”；③你等了很久决定不继续了，点“停止”——agent-core 立即取消这次等待并把它记为 `unavailable`，后端已经没有待批请求；④但 UI 只收到 `aborted`，过程组收成“回合已中断”，忘了清理 composer 的审批队列，所以红色审批台继续留在屏幕上；⑤如果你再点“批准”或按 Esc，前端对一个已经不存在的审批 id 调 `respond`，后端 no-op，界面却显示“已批准，Agent 继续执行”或“已拒绝，Agent 可继续对话”，最后才恢复草稿。
- **问题**：后端已经取消的审批，前端是否应继续要求用户拍板？
- **预判**：在 `aborted` 事件里清空审批队列/active、移除详情并恢复 composer；同时把历史 `unavailable` 渲染成“已取消/不可用”，而不是现在的“已拒绝”（`index.ts:391-398`）。
- **结论**：审批 UI 残留已在工作区修复（2026-10-11）：`aborted` 事件清空当前/排队审批、移除详情、取消延迟展示并恢复 composer；新增单审批和排队审批中断测试。历史 `unavailable` 文案仍是独立待办。

#### 6.2.1 本机四个 AI agent 的对照结论

先用同一个日常场景看差别：你让助手运行 `rm -rf build/cache`，它弹出“是否允许执行？”并接管输入区。你犹豫一下，决定干脆点“停止”。这时合理行为是：停止按钮不仅结束整轮，也把这个“已经开始等你拍板”的审批当作退件处理，输入区立刻恢复成聊天输入框；而不是屏幕上继续挂着“允许/拒绝”，骗你再做一次已经没有对象的裁决。

| 项目 | 点“停止”时审批是否自动取消 | 结果语义与 UI 清理 | 关键依据 |
|---|---|---|---|
| **StudyWiki** | 后端会，前端不会自动清理 | `agent-core` 的 `cancelAll` 记 `unavailable`；但 `app-agent` 保留审批队列，后续点击只是 no-op | 后端见 `src/plugins/agent-core/service.ts:320-327`、`src/plugins/agent-core/approval.ts:176-181`；前端见 `src/plugins/app-agent/index.ts:455-461,741-746` |
| **dsh / DeepSeek Harness** | 会 | stop → turn cancel → approval 的 `AbortSignal` 触发；服务端记 `cancelled`，`PendingApproval` 拒绝并从 composer 移除 | `packages/interaction/user-approval/src/index.ts:258-295`、`packages/client/ui-approval/src/client/contract/slots.ts:105-150`、`packages/api/session-controller/src/client/sessions/session.ts:331-340` |
| **Codex** | 会 | 中断先取消 turn token，再清空 pending approvals；等待方收到关闭的 oneshot，按 `Abort` 终止；app-server/TUI 也撤销未决客户端请求 | `codex-rs/core/src/tasks/mod.rs:537-561`、`codex-rs/core/src/state/turn.rs:87-140`、`codex-rs/core/src/session/mod.rs:2740-2844`、`codex-rs/app-server/src/bespoke_event_handling.rs:1203-1207` |
| **Claude Code**（本地 sourcemap，非官方原始仓库） | 会 | 取消入口先清空审批队列并触发 abort；挂起的 permission promise 立即得到 cancelled/abort decision，日志记 `user_abort` | `src/hooks/useCancelRequest.ts:87-100`、`src/screens/REPL.tsx:2137-2140`、`src/hooks/toolPermission/handlers/interactiveHandler.ts:137-153`、`src/hooks/toolPermission/PermissionContext.ts:148-170` |

pi 的答案需要分两层说：它没有内置“每个工具都先弹审批”的机制，常见的是扩展在 `tool_call` 钩子里调用 `ctx.ui.confirm()` 做审批。`Agent.abort()` 只中止当前 run 的 `AbortSignal`；如果扩展写 `ctx.ui.confirm(...)` 时没有显式传入 `ctx.signal`，审批 promise 不会因为 run 中断而自动关闭。也就是说，pi 的默认形态是“停止不必然取消审批”；只有扩展自己把对话框生命周期接到 signal 上才取消。核心依据：`packages/agent/src/agent.ts:335-342`、`packages/coding-agent/src/core/extensions/runner.ts:1233-1248`、`packages/coding-agent/src/modes/interactive/interactive-mode.ts:2638-2704`。扩展文档也明确把 `ctx.ui.confirm` 当作确认危险命令的扩展能力，而不是内置审批服务：`packages/coding-agent/docs/extensions.md:166-175`。

这个对照支持 §6.2 的修复方向：StudyWiki 后端已经选择 fail-closed，UI 的 `aborted` 生命周期现在也已对齐 dsh/Codex/Claude Code；历史记录渲染成“已取消/不可用”仍是独立待办。


### 6.3 全局 Escape 会同时作用于插件模态和 Agent 审批态

- **位置**：`src/plugins/app-agent/index.ts:658-683`；`src/plugins/plugin-manager/index.ts:50-96`；`src/plugins/llm-settings/index.ts:52-84`。
- **现象**：插件/模型模态把 Esc 监听挂 `document`；Agent 审批态也把 Esc 监听挂 `document`。若审批接管期间用户再打开插件或模型面板，按 Esc 会同时触发“关模态”和“关审批详情或拒绝审批”。
- **发生场景**：①Agent 请求写入 `/tmp/report.md`，底部输入区变成审批台，里面有“批准 / 拒绝”和“查看详情”；②你还想先确认某个外置插件的状态，于是点 Activity Rail 的“插件管理”，模态浮层盖住审批台；③浮层遮住了界面，你按 Esc，本意只是“关掉设置窗口”；④但 Agent 的审批监听器和模态监听器都挂在 `document` 上，同一次 Esc 会分发到两者。审批详情没展开时，Agent 先把请求记为“拒绝”，模态随后关闭——你以为只是取消查看，实际已经替这次写入做了安全决策；如果详情已展开，则这一下会同时收起详情和关闭模态。⑤审批台随后显示“已拒绝，Agent 可继续对话”；若队列里还有下一项，400ms 后它会顶上来，更容易让人误以为刚才只是普通切换界面。
- **问题**：模态存在时，Agent 全局快捷键是否应暂停？
- **预判**：`onDocKeydown` 在 `document.querySelector('.plugin-panel')` 存在时先返回，或把 Agent 快捷键作用域限制到 Agent 面板且模态打开时挂起；避免一次 Esc 产生两个安全语义。
- **结论**：已在工作区修复（2026-10-11）：新增窗口级 `ActiveLayerStack`，插件和模型模态登记 Escape 所有权；存在浮层时 Agent 快捷键直接让路，浮层关闭后排队审批自动接管 composer。新增层序栈单测和“浮层优先 → 审批不误拒 → 浮层关闭后继续排队”集成测试。

#### 6.3.1 dsh 对照结论

用户的预期方向是对的：浮层打开时，Esc 这类“关闭当前视图”的按键应先交给当前顶层浮层；底层 Agent 审批不应同时在 `document` 上抢同一个安全手势。dsh 的实际机制接近这个方向，但不是靠通用焦点陷阱，而是靠两条生命周期边界配合。

第一，dsh 的审批不是浮窗，而是 composer takeover。`PendingApproval` 先登记成 session 级 pending interaction；`conversation.composer` chain 选中它时，隐藏普通 composer fallback 并渲染 `ApprovalPanel`。`ApprovalPanel` 本身不挂全局 Escape 监听，所以它不会和 Modal 抢同一个 keydown。第二，dsh 的 `Modal` 打开时才在 `document` 注册 Escape，关闭时移除；它用 body portal、遮罩、`role="dialog"` 和 `aria-modal="true"` 表达顶层浮层。因此审批等待中再打开 Modal，按 Esc 只会关 Modal；审批对象继续由自己的 `AbortSignal` 和 pending-interaction 注册生命周期管理，不会被浮层关闭误判成拒绝。

但 dsh 没有做到严格的“浏览器顶层焦点”：Modal 不自动聚焦，也不做焦点陷阱或把背景设为 `inert`，更没有用原生 `<dialog>.showModal()`。它的安全性来自“只有当前打开的浮层注册 Escape”和“审批面板不监听全局键盘”，而不是一个通用 layer stack。对 StudyWiki，更稳的做法是引入中央 overlay/modal 所有权栈（或直接用 native dialog top layer）：每次 Esc 只交给栈顶层；Agent 快捷键先检查当前 active layer，若不是 Agent 审批层就直接返回；浮层关闭后把焦点还给审批操作区。仅用 `.plugin-panel` 选择器可以挡住现有两个面板，但仍是散落的布尔判断，后续新增浮层时容易再漏。
