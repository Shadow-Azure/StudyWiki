## 这个 PR 想合入什么

你在 StudyWiki 里改了一段笔记还没保存，手滑点了 macOS 左上角的红点，或按了 `Cmd+Q`——旧实现里这四条"原生出口"（红点、菜单 Close Window、`Cmd+W`、`Cmd+Q`）会**绕过**前端已有的"未保存提醒"，直接关窗或杀进程，脏稿静默丢失。切文件 / 换库的守卫一直是好的，漏的恰恰是操作系统这一层。

打个比方：前端守卫像是公司前台，以前员工（关闭请求）走正门都会被前台拦下盘问；但 macOS 的红点和 `Cmd+Q` 是**消防逃生梯**——不经过前台，直通室外。这个 PR 做的事：在逃生梯口装了一个**传达室**（Rust 原生 hook），任何人从逃生梯走都会被传达室拦下，传达室打内线电话（`eval` 一座 JS 桥）问前台："这人能走吗？"前台逐个点名（聚合所有文档守卫），全部点头后，前台**亲手关灯锁门**（显式 `destroy()`）；任何人说"等等"，整个关闭作罢。

具体四块：① `src-tauri/src/native_close.rs`（新增 232 行）用 objc2 在运行时改写 `NSWindow` 的 `performClose:`/`close:`/私有 `_close:` 与 `NSApplication.terminate:` 的实现，并把红点的 target/action 改接到自家 `StudyWikiCloseTarget`——它只向前端发桥接调用，不直接关窗；② Rust 新增 `CloseGuardRegistry` + `set_close_guard_ready` 命令，主进程据此知道"哪些窗口已装守卫、需要同步拦截"；③ 前端 `WindowsService.guardClose` 从"每个插件各装一个监听器"重构为"聚合成一个监听器"，先同步 `preventDefault()` 再逐个问脏守卫，全放行才 `destroy()`；④ `Cmd+Q` 走同一套：terminate hook 逐窗发桥接，所有窗销毁后的"空窗退出请求"放行让进程正常结束。

读完应能回答三个问题：它解决"macOS 四条原生出口绕过前端守卫丢脏稿"的问题；做法是原生层同步拦截 + 前端聚合确认 + 显式销毁，脏语义留在前端、主进程只持有"就绪"一个布尔；代价是引入 objc2 运行时改写（含一个私有 selector `_close:`）、干净窗口的关闭也改由前端显式 `destroy()`、以及捆绑了 tauri 2.11→2.12 / tao 0.35→0.37 的框架升级。

## 2. 架构导览

### 2.1 原生拦截层：四类入口 → 一座桥

macOS 的关闭入口不止一个 selector，所以 `install()`（`native_close.rs:34-69`）一次改写四个方法实现：`performClose:`（`Cmd+W`）、`close`（编程关闭）、私有 `_close:`（macOS 26 实测红点走的动作）、`NSApplication.terminate:`（`Cmd+Q` / 菜单 Quit）。改写手法是经典的 Objective-C method swizzling——把方法实现函数指针换成自己的，原实现指针存进四个 `AtomicUsize`（26-29），需要放行时再转回来调用。

hook 之后的行为分两种窗口：

- **已武装窗口**（`CLOSE_GUARDS` 表里有它）：`perform_close`（204-218）查到登记就不调原实现，改为 `window.eval("window.__studywikiNativeClose?.()")`——打进内线电话，关不关由前端决定。
- **未武装窗口**：按 selector 取出对应原实现转调（220-231），行为与未 hook 完全一致。

红点比较特殊：它不是消息而是按钮，有自己的 target/action（macOS 26 实测为窗口自身 + 私有 `_close:`）。所以武装时（`set_ready`，131-135）把按钮的 target/action 改接到进程级单例 `StudyWikiCloseTarget`（166-178）的 `studywikiClose:`——这个动作（180-195）从按钮反查所属窗口，再查表打内线电话。解除武装时（147-160）把最初捕获的 target/action 原样恢复。

为什么需要私有 `_close:`？owning Note 记录：macOS 26 实测红点 target/action 是窗口自身 + `_close:`，且 AX press 不走公共 `performClose:`/`close:`——只 hook 公共方法盖不住红点。这是实测结论，本次检视无法在本机重演该测量，但 tao 0.37.1 源码侧已核实配套主张：tao 的 window delegate `windowShouldClose:` 恒返回 `NO` 只发 `CloseRequested`（`window_delegate.rs:326-331`），红点若绕过它，前端确实收不到任何事件。

### 2.2 就绪登记：主进程只持有一个布尔

主进程不理解"脏"——那是文档语义，住前端。它只需要同步知道一个事实：**这个窗口现在该不该拦？** 这就是 `CloseGuardRegistry`（`windows.rs:14-31`）——一个 label 集合 + `set_ready`/`is_ready`/`remove`。前端经 `set_close_guard_ready` 命令（118-129）上报，命令先调 `native_close::set_ready` 改接原生层、再落登记表。

登记表的消费者是 `configure_window_lifecycle`（`lib.rs:312-348`）里的 `CloseRequested` 分支：ready 窗口的关闭请求被 `api.prevent_close()` **同步取消**（320-327）——这是整个方案的地基，因为 Tauri 只在同步阶段认 prevent。`Destroyed` 分支（329-345）把窗口从两个注册表 + 原生登记表三处同时清掉。

武装时机刻意不依赖启动顺序：`guardClose` 第一次装上聚合监听器时立即上报 ready（`host/windows.ts:108-113`），bootstrap 收尾的 `markCloseGuardReady()`（`bootstrap.ts:88`）只是补一枪同步当前状态——会话中途新装守卫的窗口照样武装（有专测钉住）。重复武装幂等：已武装窗口不再重读红点 target/action（`native_close.rs:117-119`），否则会把自己改接的动作当成"原始动作"存起来，解除时恢复出一个永远打内线的红点——注释把这条坑写在了代码里。

### 2.3 前端聚合：一个监听器，显式销毁

旧 `guardClose` 是每个插件各装一个 `onCloseRequested` 监听器，脏才 `preventDefault`；新实现（`host/windows.ts:105-141`）聚合成一个：`#guards` 按注册序存所有守卫，`#handleClose` 先无条件 `preventDefault()`（同步段第一行，Tauri 时序要求），再逐个 `isDirty()` → `confirmDiscard()`，任一取消即 return，全放行后**先 `#setNativeReady(false)` 解除原生拦截，再 `destroy()`**——顺序钉死，避免 destroy 途中被自己人的拦截器再拦一次。

语义变化值得注意：**干净窗口的关闭也改由前端显式 `destroy()`**（以前是脏才拦、干净走原生默认）。这是必然的——原生侧已被同步取消，没有人替它关了，前台必须亲手锁门。owning Note 的 Consequences 诚实记录了这一点及 `core:window:allow-destroy` 继续是硬依赖。

退订对称：最后一个守卫退订时摘监听器、删 `__studywikiNativeClose` 全局、上报 not-ready（115-124），窗口回到原生直关。`#closing` 重入锁（129）保证确认弹窗挂着的时候，第二次关闭请求被静默吞掉而不是再弹一串。

### 2.4 退出路径：Cmd+Q 走同一套

`terminate:` hook（`native_close.rs:77-102`）：存在已武装窗口时，逐窗克隆 `request_close` 闭包打内线电话，**不调原实现**（退出被吞）；无任何武装窗口时转调原实现，保持原生退出。注释（71-76）写明了为什么必须 hook：tao 0.37.1 的 macOS app delegate 只实现了 `applicationWillTerminate:`、**没有** `applicationShouldTerminate:`——本次已在 `~/.cargo/registry` 的 tao-0.37.1 源码实测核实（`app_delegate.rs:62-63` 只有 WillTerminate）——AppKit 默认直接终止进程，`ExitRequested` 根本不会发。

最后一个窗口销毁后，tauri-runtime-wry 在 `Destroyed` 且窗口表为空时发 `ExitRequested { code: None }`（已在 tauri-runtime-wry-2.12.0 `lib.rs:4271-4286` 实测核实）；`run()` 的处理器（`lib.rs:356-369`）此时见 `webview_windows()` 为空直接放行，进程正常结束。处理器里 macOS 分支的逐窗 eval 是防御性兜底（理论上该路径到达时窗口表已空），非 macOS 分支逐窗 `close()` 才是 Windows/Linux 的实际退出链路。

## 3. 数据流走查

端到端主线（脏 markdown + 红点）：

1. 用户点红点 → 按钮 target/action 已被改接（`native_close.rs:131-135`）→ `StudyWikiCloseTarget.studywikiClose:`（180）→ 查表拿到该窗的 `request_close` → `eval("__studywikiNativeClose")`（143）
2. 前端桥（`host/windows.ts:110-112`）→ `#handleClose` → 同步 preventDefault（128，桥路径是空操作）→ `#closing` 上锁
3. markdown 守卫 `isDirty()` 为真（`doc-markdown/index.ts:154-157`，path 匹配 activeFile 且有未保存修改）→ 弹原生确认"放弃对 x.md 的未保存修改并关闭？"
4. 取消 → return，`#closing` 解锁，窗口原样 ✅；确认 → `#setNativeReady(false)`（136，恢复红点 + 摘登记）→ `destroy()`（137）→ `Destroyed` → Rust 三清 + emit `win://closed`（`lib.rs:329-345`）
5. 若这是最后一个窗口 → wry 发 `ExitRequested` → `run()` 见空窗放行 → 进程结束

`Cmd+Q` 变体：第 1 步换成 `application_terminate`（82-101）收集所有已武装窗口的 `request_close` 逐个 eval；后续每窗独立走 2-4。

干净窗口变体：第 3 步守卫全不脏 → 不弹窗 → 直接走 4 的后半段，用户感知与原生直关一致（多两次 IPC 的代价）。

## 6. 讨论点

### 6.1 Cmd+Q 遇"武装 + 未武装"混合窗口时退出半途而废（macOS）

- **位置**：`src-tauri/src/native_close.rs:82-101`（`application_terminate` 只对 `CLOSE_GUARDS` 里的窗口发桥接）
- **现象**：主窗开脏 markdown（已武装）+ 另开一个欢迎态窗口（无守卫，未武装），按 `Cmd+Q` → terminate hook 只给武装窗打内线 → 确认丢弃后主窗销毁 → 但欢迎窗**没有任何人关它** → 窗口表非空 → wry 不发 `ExitRequested` → 应用挂着不退。用户要再按一次 `Cmd+Q`（此时登记表已空，转调原实现）才能真正退出。
- **问题**：与 PR 描述"所有窗口都确认放行并关闭后，应用再正常退出"不符——未武装窗口根本不在关闭列表里。非 macOS 平台没这个问题（`run()` 的 ExitRequested 分支对每个 webview `close()`）。触发前提是多窗口 + 部分窗口有文档守卫，当前产品多窗口用得少，但 app-windows 插件建窗是既有能力，场景真实可达。
- **预判**：真缺陷，严重度中低（有"再按一次 Cmd+Q"的绕过路径，不丢数据——脏窗都有守卫护着）。修法二选一：① terminate hook 里对未武装窗口直接转调原 `performClose:`/`close`；② 前端桥不存在时原生侧直接关。①更纯粹（不依赖 webview 存活）。归属建议：本 PR 内小修或紧随的修复 issue，不阻塞合并由用户拍板。
- **结论**：✅ 暂不修复（2026-09-30，用户拍板保持现状）——有"再按一次 Cmd+Q"的绕过路径且不丢数据；多窗口部分武装场景当前频率低。留档于本检视文档，待多窗口使用变多或退出语义要收口时再修（修法预判：terminate hook 对未武装窗口转调原 performClose/close）。

### 6.2 私有 selector `_close:` 缺失即启动 panic

- **位置**：`src-tauri/src/native_close.rs:46-48`（`expect("NSWindow implements _close:")`）
- **现象**：`_close:` 是私有 API，hook 它本身就是赌"未来 macOS 还在"。若某个 macOS 版本移除/改名，`install()` 在 builder 装配期 panic——不是守卫降级，是**整个应用起不来**。
- **问题**：私有 selector 兜底是 macOS 26 实测必需（Note 已记录理由），本身没得选；但"缺失即进程级崩溃"把兼容性风险放大到了不可用级别。同类 hook 的惯例是缺失时跳过该路 + 记日志，其余三路（`performClose:`/`close:`/`terminate:` 都是公开 API）照常工作，退回"红点可能漏、其余出口仍在"的降级态。
- **预判**：健壮性问题，当前无实害（macOS 26 实测存在该 selector）。建议改 `match`：缺 `_close:` 时跳过这一路武装并 `eprintln!` 告警。改动 ~10 行，适合顺手带进本 PR 或下一个硬化 PR。
- **结论**：✅ 已修复（2026-09-30）——`_close:` 改为可选探测：缺失时跳过该路钩子并输出告警，公开 selector 钩子与红点 target/action 改接继续生效；owning Note 三件套同步登记降级策略。回归：cargo fmt/clippy/test、pnpm test、verify:docs（20 叶）、verify:flow 全绿。

### 6.3 `install()` 挂在共享装配函数上，测试进程也被 swizzle

- **位置**：`src-tauri/src/lib.rs:312-313`（`configure_window_lifecycle` 第一行 `native_close::install()`）；该函数同时服务 `app_builder`（275）与 `raw_binary_builder`（303，MockRuntime 测试装配）
- **现象**：macOS 上跑 `cargo test` 时，测试进程也会进程级改写 `NSWindow`/`NSApplication` 的四个方法实现（`Once` 保证只装一次）。当前无实害：MockRuntime 测试不创建真窗口、不触发这些 selector，且本机 cargo test 32/32 绿。
- **问题**：测试装配背负了不需要的副作用——测试进程一旦将来有别的代码路径触到 `close`/`terminate:`，行为会被静默改写，排查困难。`install()` 语义上属于"真实应用启动"，挪进 `run()` 即可。
- **预判**：卫生问题，一行搬运。不阻塞，建议下次触碰该文件时顺手挪。
- **结论**：✅ 已修复（2026-09-30）——`install()` 从 `configure_window_lifecycle` 挪入 `run()` 开头，测试装配（`raw_binary_builder`）不再携带进程级 swizzle 副作用。回归：cargo fmt/clippy/test 全绿。

### 6.4 Cmd+Q 时多武装窗口并发确认，与"逐个"语义有出入

- **位置**：`src-tauri/src/native_close.rs:99-101`（for 循环连续 eval，不等任何完成）
- **现象**：两个窗口都有脏稿时按 `Cmd+Q`，两个窗口的确认框**同时**弹出（各自 webview 独立跑 JS）；用户确认 A 窗后 A 立即销毁，再取消 B 窗——A 已关无法挽回。
- **问题**：PR 描述写"逐个窗口走同样的确认流程"，owning Note 的"按注册序逐个确认"指的是**单窗内**多守卫（前端 for-await 是真串行）。跨窗并发 + 部分关闭的语义没有文档记录。真正跨窗串行需要窗口间回传通道（Rust 等前一窗结果再 eval 下一窗），复杂度明显上升。
- **预判**：行为本身可接受（每窗确认框模态于各窗，用户决定处理顺序），问题是**语义无记录**。建议在 owning Note 的 Consequences 补一句"跨窗并发确认、先确认的窗先销毁"，一行成本消除描述与实现的温差。无实害留档。
- **结论**：🎯 已拍板目标语义（2026-09-30）——Cmd+Q 须**逐窗串行**：窗口 1 确认放弃并销毁后才弹窗口 2；任一窗口取消则停止退出流程并**聚焦该窗口**；需支撑大量未保存窗口的队列处理。当前并发实现不满足，定性从"文档温差"升级为**行为缺口**。实现需 JS→Rust 回执通道 + Rust 退出队列状态机（确认→下一窗 / 取消→停 + set_focus）；与 §6.1（未武装窗口进关闭队列）同域，已建 [m1-serial-quit issue #47](https://github.com/Shadow-Azure/StudyWiki/issues/47)（P2）承接，与 §6.1 同域收口，不在本 PR 内混做。

## 9. 文件级代码分析

### 9.1 `src-tauri/src/native_close.rs`（A，232 行）— 原生拦截层

职责：把四类 macOS 原生关闭入口改道到前端聚合守卫。关键依赖 **objc2 0.6**：objc2 是社区维护的 Objective-C 运行时 Rust 绑定（factories 之外最主流的一套，servo 系背景），纯构建期依赖、静态链接进二进制，不引入任何运行时/网络依赖——环境无关硬约束兼容（dep-allowlist 只管 npm 侧，Cargo 侧无白名单义务；`verify:native-links` 针对发布产物动态链接，objc2 只链系统 AppKit）。打个比方：objc2 是"对讲机"，让 Rust 能直接用 Objective-C 的协议跟 AppKit 通话——`class!`/`sel!`/`msg_send!` 就是拨号、报名字、说话。

核心块解读：

- **`install()`（34-69）**：`Once` 保证进程只装一次。四个 `instance_method(...).expect(...)` 取原实现存原子量，`set_implementation` 换 hook。`_close:` 的 expect 见 §6.2。
- **`set_ready`（105-164）**：武装 = 捕获红点原 target/action + 改接 `StudyWikiCloseTarget` + 插表；解除 = 恢复 + 摘表。幂等守卫（117-119）防"把自己的改接当原始动作存起来"——这条坑若踩中，解除武装后红点永远打内线，窗口关不掉。
- **`close_target_action`（180-195）**：红点击中后从按钮反查窗口、查表、打内线。`CLOSE_GUARDS` 以 `NSWindow` 指针（usize）为键，窗口销毁由 `remove_window`（198-202）按 label 清，无悬垂指针窗口期（Destroyed 同步清理）。
- **`perform_close`（204-232）**：armed → 内线；unarmed → 按 selector 取原实现转调。已知弱点（接受）：三参数签名套零参数的 `close` selector，多读的 sender 寄存器值无害（ARM64/SysV 调用约定下多余参数被忽略），swizzle 圈惯例写法。
- **`application_terminate`（77-102）**：见 §2.4 与 §6.1/§6.4。

实现思路：主进程只同步持有"就绪"布尔与"怎么打内线"，脏语义与确认全部留在前端；放行 = 转调原实现，拦截 = 打内线，两者之外不发明第三种状态。

检视发现：§6.1（混合窗口退出）/ §6.2（expect panic）；另观察一处信任模型事实——`set_close_guard_ready` 信任调用方自报的 label（可给别的窗口武装），与既有 `set_window_root` 同一信任前提（webview JS 均一方代码，外置插件摸不到裸 invoke），不算新增风险面。

### 9.4 `src/host/windows.ts`（M，+60/−7）— 聚合守卫

旧代码：

```ts
async guardClose(isDirty, confirmDiscard) {
  return this.#deps.onCloseRequested(async (e) => {
    if (!isDirty()) return;
    e.preventDefault();
    if (await confirmDiscard()) await this.#deps.destroy();
  });
}
```

新代码骨架（105-141）：`#guards` 注册表 + 首个守卫装聚合监听器与 `__studywikiNativeClose` 桥 + 上报 ready；`#handleClose` 无条件同步 preventDefault → 逐个脏守卫确认 → 全放行先解除原生武装再 `destroy()`。

逐块讲"为什么这么写"：

- **无条件 preventDefault**（128 首行）：原生侧已经同步取消过，前端这发是给非 macOS 的 `onCloseRequested` 路径兜底——Tauri 只认同步段内的 preventDefault，所以必须在任何 await 之前。
- **先 `#setNativeReady(false)` 再 `destroy()`**（136-137）：顺序反了会自杀——destroy 触发的关闭若再被自己的武装拦下打内线，而内线那头的守卫正要退订，死锁/关不掉。
- **`#closing` 重入锁**（129-139）：确认弹窗挂起期间第二次关闭请求静默吞掉，避免叠弹窗；finally 复位保证取消后可再关。
- **桥挂在 `globalThis`**（110-112）：Rust 只会 eval 一个固定名字；退订时 delete（121）保持"无守卫窗口桥不存在"——这也让 terminate hook 对未武装窗的 eval 变成无害空操作（但副作用是 §6.1 的"没人关它"）。

实现思路：把"多个监听器各自为政"收成"一个聚合点 + 一张守卫表"，原生桥与 Tauri 事件两个入口汇入同一个 `#handleClose`。

检视发现：无新增。已知弱点（接受）：`guardClose` 注册中途 invoke 失败会留下"#guards 有登记但监听器未装"的散态，无恢复路径——触发需 IPC 层故障，概率极低。
