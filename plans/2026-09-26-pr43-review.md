## 这个 PR 想合入什么

PR #41 落地了 Excel 查看器和读写服务面，但页面还只是"隔着玻璃看"——格子点不动、改不了、存不了。这个 PR 把展柜改成工作台：双击格子直接写字，工具盘上加粗/斜体/颜色/合并随手排版，改完 Ctrl+S 一键送回仓库，关窗时还会拦一句"你有没保存的修改"。

打个比方：PR #41 修好了**货运传送带**（raw IPC 二进制通道）并请了**排版专家**（ExcelJS）驻场，但当时只开了**阅览室**。这个 PR 做三件事：① 给阅览桌装上**操作手套**——单元格内联编辑，输入 `123` 自动变数字、输入 `'007` 强制保留前导零、清空即删值；② 摆一张**工具盘**——单击选中、Shift+单击框出矩形、按钮改字体/颜色/合并；③ 接上**寄存柜按钮**——脏标记圆点 + Ctrl+S 保存 + 写失败红条 + 关窗守卫，整条链路走 `ctx.excel.write` → ExcelJS 序列化 → Rust 原子写。顺手做两件配套事：raw IPC 补上穿过 Tauri **真实调度台**的集成测试（以前只测了函数，没测命令解析这一层）；修一个流程门禁的历史 bug（高档 issue 全部完成后降到低档，以前会把早先合法关掉的 P0 反向判死）。

读完应能回答三个问题：它解决"Excel 只能看不能改、raw IPC 只有单元测试没有真实验证、flow 门禁反向重评历史 issue"三个问题；做法是纯函数编辑内核 + 查看器插接编辑状态 + 泛型化 Rust builder 复用命令实现 + 门禁跳过已清高档；代价是查看器单文件从 315 行涨到 619 行（编辑态与渲染态仍同住一处，拆分收益待观察）、拖拽框选因虚拟滚动边界被明确拆到 #42、Windows 上 MockRuntime 集成测试因上游加载缺陷显式跳过（macOS/Linux 照跑）。

## 2. 架构导览

### 2.1 编辑纯函数层（新增）

`editing.ts` 把所有**可测试的编辑语义**从 DOM 插件里抽成纯函数：输入解析、A1 地址换算、选区归一/相交/命中、值与样式写回。结构子集 `WorksheetEditSource`（`:20`）只声明 `getCell/mergeCells/unMergeCells` 三个成员，测试用真 ExcelJS worksheet 满足，生产同样满足——**依赖倒置但不引入假实现**。这一层不 import ExcelJS 类型（只用结构子集），保持与 model.ts 同样的"纯函数 + 结构协议"风格。

输入解析是本 PR 语义最细的一块：`parseCellInput`（`:90`）用十进制白名单正则而非裸 `Number()`，理由以代码注释留档——`Number` 会把 `0x10`/`0b101` 解析成数值而 Excel/WPS 按文本处理。`'` 前缀取自 Excel 惯例，服务"学号 / 身份证号 / `007`"这类前导零长数字。

### 2.2 查看器/编辑器插接（改造重心）

`index.ts` 保持原查看器的"workbook → models → 虚拟窗口"渲染骨架，插进三个新状态：`selection`（选区矩形）、`editing`（正在编辑的格子）、`dirtyState`（脏标记）。关键接线：

- `inject` 从三服务变四服务：加 `windows`（`:23`），用于 `guardClose`（`:603`）——脏态时关窗先弹确认，行为与 doc-markdown 对齐。
- `commitEdit`（`:181`）：输入文本 → `setCellValue` 写 workbook → 置脏 → `rebuildModel` 重建该 sheet 视图模型 → 全量 `render`。**编辑总是走"改 workbook → 重建模型 → 重绘"的单向流**，DOM 不做数据 home。
- `startEdit`（`:254`）：双击先经 `clickSelection` 感知合并（覆盖格也定位到 anchor），创建 `input` 铺满格子，Enter 提交 / Esc 取消 / blur 提交（`finished` 布尔防双触发）。
- `toolbar`（`:363`）：六个控件全部"读 selection → 纯函数写 worksheet → 重建模型 → render"，与编辑共用同一条回流路径；按钮 disabled/aria-pressed 由 `updateToolbar` 跟随选区与合并命中刷新。
- 保存（`:161`）：`ctx.excel.write` → ExcelJS `writeBuffer`（`src/host/excel.ts:74`）→ `files.writeBinary`（`x-studywiki-path` header，`src/host/files.ts:87`）→ Rust `write_binary_file`（`src-tauri/src/lib.rs:225`）→ 同目录 tmp + rename 原子写（`:87`）→ 广播 `fs://changed`。

### 2.3 Rust 测试装配（泛型化而非复制）

`write_binary_file` 从具体 `tauri::AppHandle` 泛型化为 `<R: tauri::Runtime>`（`lib.rs:225`），发布装配抽成 `app_builder()`（`:256`），另提供 `raw_binary_builder()`（`:293`）给 MockRuntime 测试挂同一对命令实现。**测试与生产共用命令函数本体，不复制逻辑、不打桩命令层**——这是本次集成测试的核心价值：请求真的穿过 Tauri 的命令 resolver（body 解析、header 提取、State 注入、错误通道），而不是直接调 helper。

### 2.4 flow 门禁修复

`flow-lib.mjs:347` 加一行：issue 优先级高于当前最高未清档且状态为 done 时跳过资格重评。修复场景：P0 全部 done、里程碑推进到 P1 后，以前会把历史 P0 done 按"当前最高档是 P1"反向判死。`flow-sync.mjs` 同时补状态映射：本地 done ↔ GitHub closed，其余 ↔ open，一致则不发 PATCH——此前 flow:sync 只建不改，本地收口后远端 issue 一直开着。

### 2.5 第三方行为核实（读实际源码）

- **ExcelJS `mergeCells` 遇相交合并抛错、`unMergeCells` 自行扫描范围解除相交合并**：读 `node_modules/exceljs/lib/doc/worksheet.js:602-673` 证实。`mergeRange` 的"先 unmerge 再 merge"（`editing.ts:175`）正是针对抛错语义的防御。
- **Tauri `get_ipc_response` 走真实 resolver**：读 `tauri-2.11.5/src/test/mod.rs:296` 证实——内部调 `webview.on_message`，即命令分发通道本体，非旁路 helper。
- 本 PR 无新增运行时依赖；`Cargo.toml` 的 `tauri` dev-dependency 只为测试启用 `test` feature，不进发布产物（`verify:env-independence`/`dep-audit` 声明绿）。

## 3. 数据流走查（端到端剧本）

以"打开 `成绩表.xlsx`，把 A1 改成 `007`，加粗，Ctrl+S 保存，关窗"为例：

1. **打开**：文件树点开 → `workspace.openFile` 按 kind 分派 excel → `ctx.excel.read(path)`（`src/host/excel.ts:44`）→ ExcelJS parse → `open`（`index.ts:564`）置 workbook、`createSheetModel` 建 CSS-ready 模型（`model.ts:289`）→ `render` 虚拟窗口绘制。
2. **双击 A1**：`bindCell` dblclick（`index.ts:324`）→ `select` 选中 → `startEdit`（`:254`）查到 A1 元素，创建 `input`；原值是字符串 `"007"` 且 `parseCellInput("007") !== "007"`，预填 `'007`（`initialEditorText`，`:110`）——**编辑期可见的 `'` 是提醒"这是文本"，提交时被剥掉**。
3. **输入 `42` 回车**：Enter → `finish(true)` → `commitEdit`（`:181`）→ `parseCellInput("42")` 返回 number `42` → `setCellValue` 写 `ws.getCell(1,1).value` → `dirtyState = true` → `rebuildModel` + `render`；标题栏出现 `● 成绩表.xlsx`，保存按钮挂 `dirty`（`paintChrome`）。
4. **选 A1 点加粗**：click → `select` → 工具条 `toggleFontFlag`（`index.ts:370` → `editing.ts:119`）按 anchor 当前态定向设置 → 重建模型重绘，字体变粗。
5. **Ctrl+S**：viewer keydown（`index.ts:468`）→ `save`（`:161`）→ `ctx.excel.write` → `workbook.xlsx.writeBuffer()` → `files.writeBinary`（路径进 `x-studywiki-path` header，`files.ts:89`）→ Rust `write_binary_file` 取 raw bytes、验授权、`atomic_write`（tmp + rename，`lib.rs:87`）→ 成功清脏，失败置 `error` 并显示红条且**保持脏态**。
6. **关窗**：`guardClose`（`:603`）读 `dirty()` 实时值——干净直接关，脏则弹确认；测试用 `guardShould()` 钉住这条实时读取语义。

## 6. 讨论点

### D1 高合并的 anchor 滚出视口后，双击无法进入编辑

- **位置**：`src/plugins/doc-excel/index.ts:263`（按 anchor 行查 DOM）vs `src/plugins/doc-excel/index.ts:353`（合并片段元素地址用 `visualStart` 行）。
- **现象**：虚拟窗口把跨视口合并渲染成片段时，元素 `data-address` 记为 `anchor 列 + visualStart 行`；但 `startEdit` 拿 anchor 行去 `querySelector`。当合并 anchor 行滚到窗口上方（如 A1:A100 滚到第 20 行），可见片段在屏上，双击却查不到元素，静默不进编辑。
- **问题**：用户可见的格子双击无响应，且无任何提示；属交互层缺陷，不丢数据。
- **预判**：P2。触发条件是"合并高度大于滚动偏移"，学习资料中长表 + 标题行合并可能出现。修法很小：`startEdit` 改为用合并片段元素的实际地址查找，或把编辑目标与 DOM 查找解耦（按 anchor 定位后从 `visibleMergeSegments` 拿元素）。建议随 #42 的选区/滚动边界一起收，或单独小 PR 先修。
- **结论**：✅ 2026-09-27 用户拍板——「支持单元格编辑」的验收语义覆盖"长合并滚出视口后仍可见部分可编辑"，属交付缺陷，随当前 PR 修复。修法采用检视建议：`startEdit` 增加被双击元素参数、删除地址反查，`bindCell` dblclick 直接传入元素；合并→anchor 换算保留，继续负责值读写定位。回归测试「长合并 anchor 滚出视口后，双击可见片段仍可编辑并写回 anchor」钉住该场景（18 tests 全绿）。

### D2 Shift 扩选的锚点会漂移，与 Excel 原生语义有差

- **位置**：`src/plugins/doc-excel/index.ts:222`。
- **现象**：`select(extend)` 用**当前选区左上角**当锚点。例：点 B3 → Shift 点 A1（得 A1:B3）→ 再 Shift 点 C4，本实现从 A1 扩成 A1:C4；Excel 原生保持原始锚点 B3，结果为 B3:C4。
- **问题**：一旦扩选方向反转过一次，后续 Shift 扩选的参照点就变了；无数据风险，纯交互手感差异。
- **预判**：P3。m1-03 验收只承诺"单击 + Shift 单击矩形选区"，未承诺 Excel 全套锚点语义；#42 的选区模型改造（按索引追踪）是引入"原始锚点"字段的自然时机。可先登记不阻塞。
- **结论**：✅ 2026-09-27 用户要求调研 Excel/WPS 行为后决定修复。调研（本机无 GUI，官方文档 + 对象模型语义）：Microsoft 官方文档明确选区扩展以活动单元格为参照、ActiveCell 在 Shift 扩展期间不变；WPS 表格对该基础交互与 Excel 兼容（置信度高，未取得逐字文档）；Adobe 无 Excel 产品。两者均保持原始锚点 → 随当前 PR 修复：新增 `selectionAnchor` 状态，普通单击置锚（合并取左上），Shift 扩选始终 `normalizeRange(selectionAnchor, 点击格)`；打开/切 sheet/清空/合并同步重置或更新锚点。回归测试「Shift 扩选保持原始锚点：方向反转后再扩选不漂移」钉住 B3 → Shift+A1 → Shift+C4 = B3:C4（19 tests 全绿）。

### D3 并发 Ctrl+S 无去重，两个保存可能交错完成

- **位置**：`src/plugins/doc-excel/index.ts:161`。
- **现象**：快速按两次 Ctrl+S 会并发发起两个 `ctx.excel.write`；各自序列化 + 原子 rename，完成顺序不保证与发起顺序一致。
- **问题**：若两次保存之间 workbook 又被编辑，理论上旧序列化可能后落地（覆盖新状态一瞬）；单次连续双击（间隔内无编辑）则两份字节等价，无实害。
- **预判**：P3。原子写保证不损坏文件，最坏是"最后一次生效的不一定是最新一次点击"。修法是 `save` 加 in-flight 守卫（保存中忽略/排队后续触发），一行级改动。可与 D1 同 PR 顺手处理，也可等真实使用反馈。
- **结论**：＿＿＿

## 9. 文件级代码分析

### 9.1 `src/plugins/doc-excel/editing.ts`（A，186 行）— 编辑纯函数内核

职责：把所有可独立测试的编辑语义（输入解析、选区几何、worksheet 写回）收进无 DOM 依赖的纯函数层。变更形态：全新文件。

关键依赖：仅 `import type { ExcelMerge } from "./model"`（类型依赖，无运行时耦合）；`WorksheetEditSource` 是 ExcelJS worksheet 的结构子集协议——测试与生产共用真 ExcelJS 对象，不造假实现。

变更块分析（全新文件，按代码块）：

- `parseCellInput`（90-105）：`'` 前缀剥掉返回原文（Excel 文本强制惯例）；trim 后空白返回 null（清空）；十进制正则白名单 + `Number.isFinite` 双保险做数值化；其余原样返回字符串。**为什么不用裸 `Number()`**：`Number("0x10") === 16`，而 Excel/WPS 把它当文本——正则把十六进制/二进制字面量挡在数值化之外。这是本文件语义密度最高的一块，测试钉了 11 个输入形态。
- `clickSelection` / `normalizeRange` / `rangesIntersect`（57-87）：选区几何三件套。`clickSelection` 用"单格矩形 ∩ 合并"命中，覆盖格点击升级为整段合并——为样式工具条对完整合并生效服务。
- `toggleFontFlag`（119-136）：方向由 anchor 当前态决定（anchor 无粗体 → 全设，有 → 全清），即 Office 工具条语义；对 range 逐格写 `cell.style.font`。
- `setFontColor` / `setFillColor`（144-173）：`#rrggbb` → ExcelJS 的 `FFrrggbb` ARGB；清除分别走"删 color 键"与 `pattern: "none"`，对齐 ExcelJS 序列化面。
- `mergeRange` / `unmergeRange`（175-186）：合并前先 `unMergeCells` 清相交旧合并再 `mergeCells`——因为 ExcelJS `mergeCells` 对相交合并直接抛错（已读 `worksheet.js:612` 证实）；`unMergeCells` 自扫范围解除相交合并（`worksheet.js:656` 证实），所以 unmerge 不需要预扫描。

实现思路总结：编辑语义全部下沉纯函数，DOM 层只做状态与绑定；结构协议让测试用真 ExcelJS 往返而不复制实现。检视发现：无新增；`'` 单字符输入存空串的行为与 Excel 一致，接受。
