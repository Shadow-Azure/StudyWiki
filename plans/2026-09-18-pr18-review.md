## 这个 PR 想合入什么

Phase 1–3 建的是"重启才生效"的插件生态：装一个插件要重启应用才能看到它。PR #18 把这条路改成即时的，并给这条路装上护栏和后悔药。

打个比方：以前装插件像装修房子——工人（代码）进场前你得先搬出去（重启），装错了只能砸了重来。这个 PR 做了四件事：① 给每次装修拍一张**存档照片**（Rust 版本仓：每次成功激活留一代快照，最多 10 代，改坏了能一键"复原到照片那天"）；② 让工人**在你住着的时候施工**（热路径全即时化：安装/导入/启停/重载/回退/移除本窗立即生效）；③ 给外来工人发**门禁卡**（guard 白名单门面：外置插件只能刷自己声明过的服务，刷别人的卡当场报错并教你怎么补卡）；④ 施工完有**验收员**（fiber 等待式审计：激活后轮询确认插件真的跑起来了，2 秒没跑起来判失败并点名原因）。

读完应能回答三个问题：它解决"插件管理全靠重启、外置插件能摸到整个宿主、装坏了没有退路"三个问题；做法是版本仓 + 共享激活函数（guard 包装 → 挂载 → 审计 → 快照）+ 面板六动作全走这条唯一入口；代价是 guard 明确不是沙箱（插件仍有完整语言能力）、若干边缘分支缺测试、以及一批已记录在案的搁置项。

## 2. 架构导览

### 2.1 版本仓：活目录是唯一事实源，历史只是照片

版本仓住 `plugins/.history/<name>/<ts>-<hash12>/`，每代 = package.json 原文 + 入口文件 + meta.json（`src-tauri/src/plugins.rs:361-369`）。三个设计点：

- **去重靠内容指纹**（`hash_plugin`，plugins.rs:396-420）：package.json 原文 + 入口源码拼起来 sha256。同内容再激活不增生新代（`find_generation_by_hash`，plugins.rs:428-441）——所以"回退到初代再激活"不会让代数量 +1，PR 验收第 3 条实测了这点。
- **排序键严格递增**（plugins.rs:490-496）：时间戳只到秒，同秒连拍两张照片时第二代的时间戳人为 +1——"裁最旧"才有确定判据（否则同秒多代谁最旧是随机的）。代价见 §6-D6。
- **回滚 = 原子写回活目录**（`restore_generation` 复用 `place_plugin` 的 staging 管线，plugins.rs:544-567），激活归前端热重载路径管——Rust 只管落盘，单一职责。版本 id 只许字母数字连字符，防目录逃逸（测试已钉）。

### 2.2 guard 门面：发卡、查卡、但不搜身

`guardExternalModule`（guard.ts:11-20）只包外置插件（内置一等公民走静态表直装）。门面是两层 Proxy：外层 `facade`（guard.ts:23-46）管"能刷哪些卡"——inject 声明过的服务才放行，读未声明的抛教学错误（文案点名"在 inject 数组里声明 X"），赋值抛只读错误，`has` 陷阱让 `"files" in ctx` 也说实话；内层 `guardService`（guard.ts:49-63）管"服务吐回来的东西"——方法用原 receiver 调用（`Reflect.apply(value, t, args)`，this 不丢），返回值里直接出现 cordis Context 就拒（防经返回值摸到别人的上下文，Promise 解包也查）。

边界写得很诚实（guard.ts:7-8 与 contract.md:29 一致）：收窄的是**服务面**，不是**语言能力**——插件仍能碰 DOM/fetch/全局对象。这不是沙箱。门面的象征意义大于防御意义：它把"君子协定"变成"刷卡留痕"，让插件作者的权限意图（inject 声明）变成可机械检查的契约。

### 2.3 共享激活：唯一大门与验收员

`activateExternal`（activate.ts:84-106）是所有外置激活的唯一入口，四步：guard 包装 → `ctx.plugin` 挂载 → `waitActive` 轮询审计（10ms × 2s 预算，ACTIVE 即过，FAILED 用 `fiber.await()` 重放原始错误，超时报"声明的服务未提供？"）→ 登记 running → 快照。审计失败会先 dispose 半成品 fiber 再记入失败表——不留僵尸。

`reloadExternal`（activate.ts:116-144）是"先验证后切换"：先 dispose 旧 fiber，激活新模块失败就用**内存里的旧模块对象**回退（磁盘已被新代码覆盖，内存这份是唯一的旧版副本，activate.ts:6 的注释点破了这一点）。同一插件的操作走 `serialized` 按名串行（activate.ts:31-36），连点不交错；前序失败吞掉不连坐。

`verify:layering` 的 `scanExternalActivation`（verify-layering.mjs:70-97）把"唯一大门"变成机械事实：`ctx.plugin(` 字面量只许出现在 boot.ts 与 activate.ts，且 activate.ts 必须含 `guardExternalModule(`——别人新开一扇侧门会红门禁。

### 2.4 面板：四源合一的纯投影

`computePanelRows`（model.ts:34-70）把四个信息源合成一行：清单（id/enabled）、目录扫描（version/problem）、boot 坏行（优先作 problem）、本窗运行态（running/failed/stopped）。投影顺序先判 enabled 再判 running——停用行恒 stopped，不给热操作（清单语义是"不该在跑"，给了"重新加载"会出现"插件在跑而清单说停用"的分裂态，index.ts:253-254 注释）。

六个动作全走热路径：安装/导入 = 写清单行（`withEnabled(withRow(...), row, true)`，装即启用）→ 取模块 → `reloadExternal`（不是 `activateExternal`——覆盖安装要先 dispose 旧 fiber，否则旧 fiber 成孤儿，index.ts:143-148 注释）；启停 = reload/dispose 后落清单；回退 = restoreVersion 落盘 + 启用行随即热重载；移除 = deactivate + 删目录连历史 + 删清单行，二次确认。

## 3. 数据流走查：装一个插件到回滚它的完整剧本

1. 面板输入包名点"安装" → `ctx.plugins.install(spec)` → Rust 查 registry、拉 tgz、封闭契约校验、staging 原子落活目录（plugins.rs 安装管线，Phase 2 存量）。
2. 写清单行并启用：`writeManifest(withEnabled(withRow(manifest, "ext:foo"), "ext:foo", true))`（index.ts:149-151）。
3. `loadModule` 取模块：Rust 读入口源码 → blob 装载 → apiVersion 支持集 + zod 形状校验（host/plugins.ts:134-150）。
4. `reloadExternal` → 串行队列 →（首装无旧 fiber）→ `activateExternal` → guard 包装 → `ctx.plugin` → waitActive 验收 → 登记 → `deps.snapshot` → Rust 拍第一张存档照片。
5. 用户改坏代码点"重新加载" → loadModule 读新代码 → dispose 旧 fiber → 新模块 apply 抛错 → waitActive 见 FAILED，`fiber.await()` 重放"new code boom" → dispose 半成品 → **内存旧模块重新激活** → 快照（此时活目录是新的坏代码，坏代码也入仓一代——已文档化口径，见 §6-D3）→ 错误内联显示，旧版仍在跑。
6. 用户点"历史"→ `listVersions` 现读现列 → 点某代"回退" → Rust 原子写回活目录 → 启用行随即 reloadExternal → 内容与行为一起回到那天。
7. 第二个窗口启动 → boot 按清单装载 `ext:foo`（走同一 activateExternal 大门，boot.ts:36-46）→ 失败进 broken 报告，面板显示"待清理"不崩应用。

## 6. 讨论点

**环节定位总览**：PR 主线流程 = 开发/获取 → 激活（guard 发卡 → 挂载 → 2s 验收 → 拍照存档）→ 运行中 → 变更操作（重载/启停/回退/移除）→ 重启对齐（boot 按清单装载）。每条讨论点标注它发生在哪个环节、不改的实际影响。

| 点 | 环节 | 不改的后果 | 严重度 |
|---|---|---|---|
| D2 | 变更操作 | 清单被静默回滚（"关了又活"） | ⚠️ 低频率 × 数据丢失，最值得修 |
| D1 | 运行中 | 共享服务可被篡改，排查噩梦 | ⚠️ 低概率 × 高隐蔽性 |
| D3 | 重载回退 | 历史混入坏代 | 低，已拍板后续修 |
| D4 | 移除 | 历史残留 + 文案失信 | 很低 |
| D5 | 激活调试 | 报错指错路 | 很低，体验瑕疵 |
| D6 | 拍照 | 时间显示差几秒 | 无害 |
| D7 | 各处边缘 | 未来重构缺保护网 | 未来的债 |

### D1 门面只锁了 ctx 第一层：宿主服务对象本身可被外置插件改写

- **环节**：运行中——插件通过验收、拿到服务后日常调用的每一刻；门面只管"取服务时查卡"，不管"拿到手后动手脚"。
- **不改的影响**：写错或恶意的插件可改写全窗口共享的服务实例（如把 `files.readTree` 换成假数据），内置功能跟着出错；篡改只在内存、不落盘不留痕，重启恢复但极难排查到是插件所为。日常装可信插件大概率碰不到，碰上一次是排查噩梦。

- **位置**：`src/loader/guard.ts:52-62`（`guardService` 只定义了 `get` 陷阱）
- **现象**：外层面门的 `set` 陷阱拦住了 `ctx.files = x`，但 `ctx.files.readTree = () => 假数据` 不在任何陷阱覆盖范围——Proxy 没有 `set`/`deleteProperty`/`defineProperty` 陷阱时默认透传到目标对象，而目标对象是**全窗口共享的服务实例**（内置插件用的是同一个）。已知搁置清单提到 "`delete` 未拦"，同源。
- **问题**：外置插件（恶意的，或更现实的——写错了的）可以篡改宿主服务的行为，内置功能跟着出错；篡改在内存里不留痕、不落盘，重启才恢复，排查时很难想到是插件干的。contract.md:25 的"ctx 只读"字面读容易以为服务也不可变。
- **预判**：与"不是沙箱、只装信任的插件"的既定口径不冲突，倾向于不改代码——修法是给 guardService 补 `set`/`deleteProperty` 抛错（几行）+ contract.md 把"只读"限定到 ctx 顶层。防的是手滑不是攻击，成本低收益实在。
- **结论**：2026-09-19 已作为行内检视意见提交 PR，同日修复轮修完（提交 `5336194`，回复 [discussion_r4053024233](https://github.com/Shadow-Azure/StudyWiki/pull/18#discussion_r4053024233)）：`guardService` 补 `set`/`deleteProperty`/`defineProperty` 三个写陷阱，ctx 门面同样补齐，并把同类可变更形 `setPrototypeOf`/`preventExtensions` 一并拒绝——五个陷阱都抛只读教学错误且不改共享对象；`docs/plugins/contract.md` 中英把承诺收口成"ctx 与宿主服务对象的顶层形状只读：赋值、删除与 `defineProperty` 都抛错"。回归：`tests/guard.test.ts` 覆盖服务对象与 ctx 两层的赋值/删除/定义/改原型/改扩展形态，逐条断言原对象内容、原型与 `isExtensible` 不变。

### D2 面板并发操作的清单写竞态

- **环节**：变更操作——面板上 4 个写清单的动作（安装/导入/启停/移除），每个都凭 render 时的旧清单快照整体覆盖写回；两个动作时间重叠即竞态（最常见：安装走网络数秒期间点了别的开关）。
- **不改的影响**：偶发"灵异事件"——明明停用了插件重启后又活过来，或装了的插件重启后清单里没有；无任何报错，属静默数据回退。触发条件苛刻、频率低，但发生后只能靠记忆发现。

- **位置**：`src/plugins/plugin-manager/index.ts:149-151,165-167,213-217`（各 handler 用 render 时刻捕获的 `manifest` 快照做 `writeManifest`）
- **现象**：操作 A 在途（安装走网络/停用走 dispose，都是慢的）时点操作 B，B 完成后 A 完成，A 用过期清单覆盖 B 的写入。例：安装 foo（网络 3 秒）途中停用 bar——bar 的停用先落盘，foo 的安装后用"安装前抓的清单 + foo 行"整体覆盖，bar 的停用被静默回滚。
- **问题**：触发条件是"慢操作进行中再点别的"，低频但一旦发生是静默的数据回退——下次启动 bar 又装回来了，用户完全不知道哪一步丢了。
- **预判**：修法二选一——操作期间禁用面板其余控件（最简单），或写清单前 `readManifest` 重读再合并（更稳，多处改动）。也可接受搁置：面板是单人单窗低频界面，Note 记一笔即可。
- **结论**：2026-09-19 用户提出修改方向"Manifest 操作类封装全部写操作 + 锁串行"，经评估方向成立，两个成败要点：①读必须进临界区（闭环 `update(fn)`：锁内读盘→变换→写盘；read/write 分离则锁不住陈旧快照）；②慢操作留锁外（网络/激活等待不进临界区，清单锁与 activate 按名串行队列互不嵌套）。天花板：本窗内存锁管不了跨窗并发写，与"他窗重启对齐"立场一致——2026-09-19 用户拍板**要点 3（跨窗并发）遗留**，归后续阶段（Rust 侧原子读改写），本阶段文档如实声明即可。同日修复轮按要点 ①② 落地（提交 `5336194`，回复 [discussion_r4053024385](https://github.com/Shadow-Azure/StudyWiki/pull/18#discussion_r4053024385)）：`PluginsService.update(fn)` 同窗串行读-改-写、失败释放队列且错误原样上抛；面板安装/导入/启停/移除四个写点改成 `update(纯变换)`，render 快照退出写回路径，`loadModule`/`reloadExternal`/`install`/`remove` 留锁外；跨窗天花板按拍板写进 `docs/plugins/dynamic.md` 中英。回归：`tests/host-plugins.test.ts` 串行交替与失败后仍可用两用例、`tests/plugin-manager.test.ts` 安装慢操作与并发 update 交错不回滚用例。

### D3 失败重载入仓：历史里会有"从未成功运行"的一代（2026-09-19 本轮已修：回退不拍照）

### D5 教学错误的死胡同：JS 元属性会被当成"未声明的服务"

- **环节**：激活阶段 guard 查卡时——但触发者是插件作者的调试动作（字符串拼接 ctx 触发读 `toString`），不是正常调用。
- **不改的影响**：作者调试时收到指错路的报错（"把 toString 加进 inject"），照做也救不了（宿主没有该服务，卡审计超时），被带进死胡同。只影响开发体验、频率低；修法很小（元属性开小口子）。

- **位置**：`src/loader/guard.ts:29-33`（任何未声明的**字符串**属性都抛教学错误）
- **现象**：插件作者调试时写 `` `ctx=${ctx}` `` 或 `String(ctx)`，JS 会读 `ctx.toString`——不在 inject 里 → 抛出"外置插件 x 访问了未声明的服务 "toString"——在 inject 数组里声明 "toString" 后重新加载"。按指引声明 `inject: ["toString"]` 也救不了（宿主没有叫 toString 的服务，会卡审计超时）。
- **问题**：教学错误在元属性上给出了错误指引，是个调试体验陷阱；symbol 探测已被 guard.ts:27-28 正确缺席，字符串元属性（toString/valueOf/toJSON）漏网。
- **预判**：低成本修法是门面对一小撮 JS 元属性名返回 undefined 而非抛错。频率低（只有字符串拼接/显式转换触发），可搁置但值得记录。
- **结论**：2026-09-19 已作为行内检视意见提交 PR，同日修复轮修完（提交 `5336194`，回复 [discussion_r4053024634](https://github.com/Shadow-Azure/StudyWiki/pull/18#discussion_r4053024634)）：门面 `get` 对未声明的 `then`/`toJSON`/`toString`/`valueOf` 返回 `undefined`（`has` 同步返回 false），`inject` 里已声明的同名服务优先放行，其余未声明属性照旧教学报错——`ctx=${ctx}`、`String(ctx)` 不再被引向"把 toString 加进 inject"的死胡同；`docs/plugins/contract.md` 中英写明该缺席规则。回归：`tests/guard.test.ts` 缺席与声明优先两用例 + `tests/activate.test.ts` 真 Context 下 `provide("toString")`/`provide("toJSON")` 激活不被阻断。

## 9. 文件级代码分析

### 9.1 `src-tauri/src/plugins.rs`（M，+326/−17）— 版本仓三命令

职责：在既有安装/导入/扫描管线旁新增版本仓（快照/列表/回滚）+ 移除连删历史。变更形态：M，前身只有安装/导入/列出/读模块/移除。

关键依赖：`sha2` 是既有依赖（安装管线的 integrity 校验已在用），本 PR 零新增依赖。

核心变更块：

- `hash_plugin`（396-420）：内容指纹 = package.json 原文 + 入口源码的 sha256。注意它顺带把"活目录当前形态"（原件 + 契约块 + 版本）一次读出，`LivePlugin` 是快照的原料包——指纹与落盘原料同源，不会出现"指纹是 A 内容存的是 B"。
- `snapshot_plugin`（479-513）：hash 去重 → 时间戳严格递增（同秒 prev+1，裁决 R2）→ 写代目录 → 裁剪。返回 `Option<String>`：None = 内容已在仓。
- `list_generations`（516-541）：`current` 是比指纹比出来的磁盘事实（活目录已删则全 false）；meta 损坏的代跳过——"历史是数据不是活代码，不配让面板打不开"。
- `restore_generation`（544-567）：id 白名单字符防目录逃逸，复用 `place_plugin` 的 staging 原子管线写回活目录。
- `remove_plugin_dir`（189-197）：历史连删 best-effort（§6-D4）。
- 测试两枚钉住主路径：去重+裁剪+排序、回写+逃逸拒绝+连删。

实现思路：活目录永远是唯一事实源；版本仓只增不改不自动激活，boot 路径零改动。检视发现：D3/D4/D6 见 §6；`VersionMeta.entry` 只写不读（D7 已列，本轮删除该字段）；`read_meta` 对缺失/损坏 meta 的跳过本轮补了回归。

### 9.2 `src/loader/guard.ts`（A，73 行）— 白名单门面

职责见 §2.2。关键设计：门面 ctx 是 `Object.create(null)` 的 Proxy（没有原型链杂物）；symbol 探测一律缺席（防 thenable 副作用——插件被 await 时不会意外触发）；服务对象方法以原 receiver 调用保 this；Context 拒绝覆盖同步与 Promise 解包两路。

已知弱点（根源 + 接受理由）：不深扫嵌套容器里的 Context（深扫成本高且可绕过，门面定位是教学契约不是沙箱）。曾列的服务层无写陷阱（D1）与字符串元属性漏网（D5）已在本轮修掉（提交 `5336194`）：ctx 门面与服务代理各补 `set`/`deleteProperty`/`defineProperty`/`setPrototypeOf`/`preventExtensions` 五类陷阱，未声明的 `then`/`toJSON`/`toString`/`valueOf` 按缺席返回（已声明同名服务优先）。测试：放行/教学/只读、Context 拒绝（同步+异步）、形状透传，加本轮的五类写陷阱、协议属性缺席与声明优先——手动驱动而非真 Context（cordis 对未满足 inject 停等待态不跑 apply，集成归 activate 测试），分工注释写在测试里。

### 9.3 `src/loader/activate.ts`（A，169 行）— 唯一大门

职责见 §2.3。逐块：

- `serialized`（31-36）：按名 promise 链，`prev.catch(() => {})` 保证前序失败不连坐；同名嵌套会自锁（面板注释已规避外层再套）。
- `waitActive`（45-64）：轮询 `fiber.state`；FAILED 用 `fiber.await()` 重放原始错误（vendor cordis fiber.ts:462-467 实测：结算后抛 `_error`）；DISPOSED 立即失败；2s 预算超时点名"声明的服务未提供？"（cordis 对缺 inject 的 fiber 停 PENDING，fiber.ts:348-352 的 `_getState` 实测吻合）。
- `activateExternal`（84-106）：失败先 dispose 半成品再记失败表；快照失败只 warn 不阻断（快照是收益不是门槛）。
- `reloadExternal`（116-144）：先 dispose 旧的再激活新的；失败用内存旧模块回退（磁盘已被覆盖，内存是唯一副本）；回退也失败则记回退错误、原错误照样抛。
- `deactivateExternal`（149-157）：幂等，没在跑也成功。

检视发现：无新增；快照时机导致 D3（本轮已改为回退分支不拍照）。

### 9.4 `src/loader/boot.ts`（M）— boot 收敛到同一入口

旧：`ext:` 行在 boot 里自行 `ctx.plugin` + 50ms 固定静默窗口，覆盖不了运行期热路径的审计需求。新：`ext:` 行 `loadExternal` 后走 `activateExternal`（36-46 行），失败进 broken 报告不阻断；内置行保持静态表直装 + 50ms 窗口 + fail-loud（内置是自家代码，卡死要响）。deps 缺省 `snapshot: async () => {}`（测试不写真仓）。

### 9.5 `src/host/plugins.ts`（M）— 三方法 + 类型

`snapshot`/`listVersions`/`restoreVersion` 是纯 invoke 转发（105-118），`PluginVersion` 与 Rust `VersionInfo` 的 camelCase 契约对应。检视无发现；本轮新增 `update(fn)`（同窗串行读-改-写，失败释放队列）补 D2 竞态，是本节唯一的逻辑增量。

### 9.7 `src/plugins/plugin-manager/index.ts`（M，351 行）— 六动作热路径化

最大的单文件变更。关键块：

- 错误行跨 render 复用（90-108）：render 的 `replaceChildren` 会重建其余节点，错误行必须是同一元素才能在重渲染后仍可见；成功路径显式 `clearError()`（bbb6042 修复轮 1 的产出），取消类结果不清。

- 启停（207-220）：先动运行态再落清单，热路径失败清单不动、开关重渲染回弹。
- 重新加载（255-268）：只出现在已启用且健康的外置行（坏行连模块都读不出，停用行的清单语义是"不该在跑"）。
- 历史/回退（269-314）：现读现列不缓存（版本仓是磁盘事实）；停用行回退只落盘；历史读取失败也内联。
- 移除（316-330）：二次确认 → deactivate → 删目录连历史 → 删清单行。

检视发现：D2 清单写竞态（本节唯一新发现，本轮已修：四个写点改走 `ctx.plugins.update(纯变换)`，历史展开前补 `clearError()`）；其余裁决均有注释锚点，可追溯。
