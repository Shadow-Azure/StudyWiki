# PR #15 检视文档：Phase 2 外置插件供应链（phase2-external-plugins）

## 这个 PR 想合入什么

一句话：**让 StudyWiki 第一次拥有了"装第三方插件"的能力**。Phase 1 交付的六个内置插件是出厂自带家电，本 PR 打开的是"买新家电"的整条通道——从用户视角看，合并后多了四件事：

1. **按名安装**：插件面板里输入包名（或 `包名@版本`），应用直接从 npm registry 拉取并安装——联网只发生在点"安装"的那一秒，装完的插件是本地两个文件，之后打开、使用全程离线（环境无关铁律不破，npm 只当仓库用、不当运行时用）
2. **本地导入**：不联网也能装——选一个 `.tgz` 文件走同一条验货管线（免下载、免完整性校验，其余校验一条不少）
3. **插件管理面板**（第六内置插件 plugin-manager）：顶栏"插件"按钮 → 面板列出已装的内置 + 外置插件，可开关启停、移除外置、看到坏插件"待清理"的原因；一切改动重启后生效（本阶段不做热装载）
4. **外置插件的宿主防线**：封闭契约（恰好 package.json + 单个入口 .js、零依赖、apiVersion 协商）+ blob URL 唯一装载缝 + 装载失败分治（坏插件标记待清理，不拖垮整个应用）

顺手收掉 Phase 1 的三笔欠账：asset 授权从"配置预发全盘通卡"收窄为"运行期到访登记"（还顺修了主窗口刷新丢 root）、启动失败不再白屏（错误面板）、老用户清单自动长出新内置插件（存量迁移）。

**不做**（边界）：插件作者侧工具链（脚手架/发布校验）是下一个 PR #16 的事；热装载、插件沙箱、恶意插件治理都不在本阶段承诺内。

## 1. 一页速览

**一句话**：让 StudyWiki 支持"从 npm 仓库安装 / 本地导入"第三方插件——npm 只当仓库用、不当运行时用：联网只发生在安装那一秒（Rust 侧直拉 tarball），装完的插件是本地两个文件，装载、运行、管理全程离线；同时把 Phase 1 留下的三笔账（asset scope 过宽、启动白屏、存量清单无迁移）一并收口。

**一个比喻**：网购但不常住仓库。npm registry = 网上的仓库；安装 = 下单提货那一刻才联网，货到手放进自家储物间（`app_config_dir/plugins/<name>/`）；此后天天用储物间里的东西再也不用出门（运行期零网络）。提货时过一道海关（安装管线）：**查单**（registry 元数据）→ **验防伪码**（sha512 完整性）→ **开箱验形**（封闭契约：恰好 package.json + 一个入口文件，无夹带、无藏刀）→ **上架**（staging 写全量后原子换名，储物间里永远是完整的一件货）。

**六块交付**：

## 2. 架构导览

### 2.1 Rust 供应链（`src-tauri/src/plugins.rs`，本 PR 新增）

一个文件装下外置插件的全部 Rust 面，按"纯函数可测 → 联网薄层 → 命令壳"三层排布：

- **封闭契约解析** `parse_package_json`（`plugins.rs:63-106`）：package.json 必须同时满足五条——非空 name、keywords 含 `studywiki-plugin`、**dependencies 显式空对象**（写 `"dependencies": {}` 才算数，不写直接拒）、`studywiki.apiVersion` 正整数、`studywiki.entry` 非空且是顶层单文件（含 `/`、`\`、`..` 即拒，`plugins.rs:99-104`）。任何一条不符返回点名错误，"不从坏包里猜"。配套 `safe_plugin_name`（:47-58）拒空名、路径分隔符与任何 `..` 片段——它是所有"用名字拼路径"操作的守门员。
- **目录三命令**：`scan_plugins`（:119-162）逐子目录读 package.json，坏目录降级为带 `problem` 的行（不让单个坏插件炸掉列表），staging 残留（`.` 开头）与非目录不入列；`read_entry_source`（:165-177）安全名检查 → 严格解析 → 读入口源码；`remove_plugin_dir`（:180-188）幂等删除。
- **安装管线**：`resolve_registry`（:330-360，唯一联网的元数据查询）→ `install_plugin` 下载（:377-389）→ `verify_integrity` sha512（:203-221，只认 sha512，其他算法拒）→ `extract_and_validate`（:240-304）→ `place_plugin`（:308-320）→ `install_bytes`（:363-372）把后四步串成下载后公共管线，本地导入 `import_plugin`（:392-396）免 integrity 走同一条。
- **tgz 校验的三个细节**值得单独指出：① 条目路径含 `..` 或以 `/` 开头直接拒（:259-261）；② 符号链接等非文件条目**跳过**而非报错（:251-253）——注释点名理由：我们不落盘 tar 原条目而是重写新文件，无穿越面；③ 恰好两文件闭包（package.json + 声明的入口，:283-292），多一个夹带都不行。
- **原子落盘** `place_plugin`：先清 staging 残留与旧目录 → staging 里写全量 → `fs::rename` 上架。插件目录在任何时刻被观察到都是完整形态（rename 同文件系统原子）。时序上有一个可缩小的窗口，见 §6.2。

**依赖面实测**（Cargo.lock + crates.io 源码）：`ureq 2.12.1`（`default-features = false, features = ["tls", "gzip"]`）→ `rustls 0.23.44` + `webpki-roots 0.26.11`（**内置 Mozilla 根证书**，不读系统钥匙串）+ `ring 0.17.14`（rustls 的加密后端，C/asm 但静态编译进二进制）；`flate2 1.1.10` 指定 `rust_backend`（miniz_oxide 纯 Rust，不碰 zlib C 库）；tar/sha2/base64 纯 Rust。整栈不引入任何系统 dylib——这是"零新增动态链接"声明（release 档 otool 实扫）的物质基础，也是环境无关铁律的 Rust 侧答案：用户机器不需要 OpenSSL、不需要任何运行时。

### 2.2 装载缝（`src/loader/external.ts`，本 PR 新增）+ CSP

21 行，全前端唯一动态 import 点。机制一句话：**Rust 命令把入口源码读成字符串 → JS 端造成 Blob → `URL.createObjectURL` 拿临时通行证 → `import()` 进模块 → finally 里 revoke 作废通行证**。

为什么要绕这一道？webview 的 CSP 只认 `'self'`（打包资源），磁盘上的插件文件不是 self——直接 import 文件路径在浏览器安全模型里没有门。blob URL 是"把内容而非地址变成模块"的标准通道：内容已经在内存里（Rust 读来的字符串），Blob 只是给它一个可 import 的临时身份。单文件零依赖契约让 blob 的两个经典弱点**归零**：相对导入（`import "./util.js"`）——契约禁止第二个文件，根本没得引；URL 生命周期——`external.ts:15-19` 的 try/finally 保证成功失败都 revoke，且模块一旦求值，命名空间对象握在调用方手里，revoke 不影响已加载的模块。

`importFn` 参数（`external.ts:11`）是注入缝：vitest 里塞假 import，整条装载链离线可测（`tests/loader-external.test.ts` 连"Blob 内容逐字传递、类型是 text/javascript"都断言了）。默认实现的 `/* @vite-ignore */` 防 vite 构建期试图解析这个动态 import。

配套两处机械锁：CSP `script-src 'self' blob:`（`tauri.conf.json:23`，未开任何 connect-src——webview 自己不发网络请求）；`layering-allowlist.json` 从空表开第一条缝（单文件登记，`verify:layering` 断言全前端动态 import 只此一处，扩缝必须回 Phase 2 Note 修订）。

### 2.3 第五插座：`ctx.plugins`（`src/host/plugins.ts`，本 PR 新增）

结构与 Phase 1 四服务同构（deps 接口 + 默认绑定 + 薄门面）：`PluginsDeps` 三件（invoke / loadExternal / pickTgz），默认绑定把真 Tauri 命令、真 blob 通道、真选框接上（`plugins.ts:33-41`）。能力面：

- 四个包管理命令各一个方法（install :55-57 / importFromTgz :60-64 / list :67-69 / remove :72-74），外加清单读写（readManifest / writeManifest :77-86）——面板因此不需要自己碰任何 Tauri 绑定，分层纪律零例外。
- **`loadModule(name)`（:90-109）是装载链的收口**：`read_plugin_module` 拿源码 + apiVersion → 支持集判定（`SUPPORTED_API_VERSIONS = [1]`，:8；不在集内拒载并点名版本号）→ 经装载通道取模块 → 形状校验（name 非空字符串、apply 是函数、inject 若是数组则须字符串数组）→ 返回 `PluginModule`。任何一步失败抛错——**boot 侧负责把它分治为坏行而非崩溃**，fail-loud 与 fail-visible 在两层各司其职。
- `bootBroken` 公开可变字段（:48）：boot 结束后由 bootstrap 回填（`bootstrap.ts:82`），面板读它点名"待清理"。这是一次性启动事实的传递通道，不是持续状态。

`context.d.ts` 的标签纸同步加了 `plugins: PluginsService` 键（`context.d.ts:18-20`），`ctx.plugins` 因此有类型。

### 2.4 启动链三处改动

- **boot 第二来源**（`loader/boot.ts:33-44`）：清单行 id 以 `ext:` 开头 → 剥前缀取名字 → `loadExternal(name)` 走宿主服务 → `ctx.plugin(plugin, row.config)` 上树（config 直传，不与 defaults 合并——外置插件没有 defaults 来源）。try/catch 把装载失败收进 `broken` 数组，`continue` 走下一行——**外置资源是用户侧状态，不配让整个应用起不来**。内置行路径逐字未动（查表 → merge defaults → 上树 → states 记账）。
- **审计分治**（`boot.ts:52-65`）：50ms 静默后查 fiber 状态，卡死的**内置**行照旧点名抛错（fail-loud 契约不变）；卡死的**外置**行进 broken、从 loaded 里除名——插件 fiber 其实还在树上跑，只是被面板标记待清理。注意 50ms 固定等待对外置行的误报面比 Phase 1 大，见 §6.8。
- **存量迁移**（`loader/manifest.ts:46-57`）：读到存量清单时，把静态模块表里有而清单里没有的**内置**行合并进去（enabled 默认 true，与首启一致），合并发生即写回落盘。这个 PR 自己就是第一个受益者：老用户的清单自动长出 `plugin-manager` 行。外置行（`ext:`）不迁移不猜——插件目录才是外置行的准源。测试覆盖了"已含全部内置行则不写回"（无谓写盘）与"既有 enabled false 不被覆盖"（`tests/loader.test.ts` 末两用例）。

### 2.5 白屏收口（`bootstrap.ts` 修改 + `boot-error.ts` 新增）

`main.ts:4` 一行改动：`void bootstrap().catch(renderBootError)`。`renderBootError`（`boot-error.ts:5-20`）向 `#app` 内联渲染标题 + `<pre>` 错误原文 + 一句清理指引（删损坏的 plugins.json / plugins 目录），错误同时进 console。注意分工：**外置装载失败不走到这里**（boot 已分治为坏行，应用正常起），这里兜的是清单 JSON 损坏、内置审计失败这类致命错——"致命才白屏换文字，非致命进面板"是两级错误出口的边界线。

bootstrap 本体三处变化（`bootstrap.ts:58-82`）：① 建第五服务并 provide；② 持久 root 启动即重授权（:70-72）——配置 scope 已收空，不重授权则重启后视频全挂，这行是 asset 收权的启动侧闭环；③ 接住 BootReport 回填 `plugins.bootBroken`（:81-82）。

### 2.6 第六内置插件：plugin-manager

- **入口**（`index.ts:15-23`）：topbar.left 注册"插件"按钮——与 demo 外置插件抢同一个槽，多占用者共存机制（Phase 1 §2.1）的直接受益者。
- **面板**（`openPanel`，`index.ts:26-100`）：固定覆盖层，点遮罩关闭；每次操作后整体重渲染（状态简单，不做细粒度更新）。两处细节见功夫：`errLine`/`hint` 两个节点跨 render 复用（`replaceChildren` 会重建其余节点，失败信息因此在重渲染后仍可见，`index.ts:38-54` 注释点名）；安装/导入失败**内联显示错误**不静默（验收项 2 的红路径）。

### 2.7 assetProtocol 收权（三文件一组）

旧世界：配置里 `"scope": ["**"]`——安装即持有全盘读卡，任何 webview 内容都能借 asset 协议读任意路径。新世界分三步：

1. **配置收空**（`tauri.conf.json:26`）：`"scope": []`，出厂不带任何授权。
2. **运行期唯一授权点** `set_window_root`（`windows.rs:70-83`）：先 `allow_directory(root, true)`（recursive），**成功后才** upsert 注册表——授权失败则注册表也不动（fail-closed：宁可 root 没登记，不可登记了却放不了行）。建窗路径 `create_window` 同款（:40-45，授权失败回滚登记项）。
3. **三个触发时机**：打开文件夹（`app-windows/index.ts:26`）、新建窗口携 root（`create_window`）、启动重授权（`bootstrap.ts:70-72`）。第三处顺修了 Phase 1 缺陷：主窗口"打开文件夹"现在先 Rust 登记+授权再切前端工作区，**刷新不再丢 root**（旧版主窗口 root 只住前端内存）。

已知局限（Note Consequences 在案）：`allow_directory` 只增不减（FsScope 无 un-allow API），窗口关闭/换 root 后旧目录授权残留且为 app 级共享——"收窄的是注入面而非可撤销性"。

**Q：为什么这个 PR 会新增 setRoot？是 Phase 1 遗漏吗？**（2026-09-13 讨论补记）不是遗漏，是 Phase 1 就预登记的欠账：旧版 environment-independence.md 已知欠账区原文"assetProtocol.scope: ["**"] 过宽：收紧是 Phase 2 开放外置插件的前置（方案：dialog 选中目录动态注入）"。因果链三层：① 威胁模型变化——放任意第三方代码进 webview 前必须收回全盘通卡，否则任何插件代码都能借 asset:// 读任意文件；② 收窄必然要求"配置收空 + 运行期授权点"，授权动作在 Rust 侧（FsScope），于是需要 `set_window_root` 当唯一授权点（授权先于注册表，fail-closed）——Phase 1 做它就是死代码（scope 全开时无消费者）；③ 真正的 Phase 1 缺陷是主窗口刷新丢 root（"打开文件夹"只改前端、root 不进注册表，F5 即丢，且不在 Phase 1 终审欠账清单里）——启动重授权要求所有窗口含 main 的 root 都在注册表，`set_root` 长出 upsert 形态后该缺陷作为设计自然产物被顺带修掉。

**Q：现在的 setRoot 起什么作用？**（2026-09-13 讨论补记）一调用三职责：① 发卡——`allow_directory(root, true)` 把目录加进 asset protocol 运行期白名单（配置 scope 已收空后的唯一授权通道，没卡则 asset:// 被 Rust 403、视频全挂）；② 登记——label→root upsert 进 Rust 窗口注册表（root 的跨刷新存储，F5 后 bootstrap 凭 label 领回）；③ 顺序即语义——授权成功才登记（fail-closed），前端先 await 它再切 workspace（树渲染时授权必已生效）。调用时机三个：打开文件夹（`app-windows/index.ts:26`）、启动重授权（`bootstrap.ts:70-72`，幂等重发，重立"有 root ⟺ 有授权"不变式）、新建窗口（不走 setRoot，`create_window` 内同款授权）。两个边界：仓库另有一个同名但不同物的 `ctx.workspace.setRoot`（Phase 1 的前端状态机+广播，"表现"；windows.setRoot 落的是"事实"，打开文件夹顺序 = 事实先落、表现后动）；注册表与授权均为 Rust 进程内存态——**保刷新（F5）不保重启**，重启回欢迎态，窗口 root 从不落盘（落盘的只有插件清单 plugins.json）。

**Q：两个 setRoot 的参数有关联吗？怎么配合？**（2026-09-13 讨论补记）字面同一个变量：两个调用点（打开文件夹 `app-windows/index.ts:24-28`、启动 `bootstrap.ts:70-73`）里 `windows.setRoot(label, root)` 的第二个参数与 `workspace.setRoot(root)` 的参数都是同一个 root 字符串——数据流"pickFolder 产出 root / fetchRoot 领回 root → 先喂 windows（静默：注册表+白名单，界面不变）→ 再喂 workspace（广播 root-changed → 树 render → 点视频时 asset 卡生效）"。label 是 windows 侧独有参数（`currentLabel()` 现取）：Rust 注册表是全应用一张表，必须写明哪个窗口；workspace 每窗私有实例，不需要自报家门。顺序是正确性不是风格——反序则树立即渲染、视频立即请求 asset://，而 Rust 未授权 → 403；`await windows.setRoot` 在前保证"用卡之前卡已发出"。比喻：windows.setRoot = 去物业办登记+领仓门禁卡（手续永久、断电重启后物业登记簿还在）；workspace.setRoot = 店长按店内广播"换仓了去搬货"（只响一次、断电即忘，所以前面必须先办手续）。

### 6.1 scoped 包（@scope/name）半支持：管线前面铺路、最后一步关门【检视新发现】

- **位置**：`src-tauri/src/plugins.rs:224-234`（split_spec 支持 scoped）→ `:330-335`（resolve_registry 转义 `%2F` 查询）→ `:308-309`（place_plugin 首行 `safe_plugin_name(&extracted.name)`）→ `:47-58`（safe_plugin_name 拒含 `/` 的名字）
- **现象**：安装 `@scope/demo` 能查元数据、能下载、能过 tgz 校验（package.json 的 name 是 `@scope/demo`，parse 不禁 scoped），**最后 `place_plugin` 报"非法插件名：\"@scope/demo\""而失败**。仓库测试只测了 split_spec 的 scoped 形态（`plugins.rs:700-711`），没有端到端 scoped 安装用例，所以这个断点没被测试照见

### 9.1 `src-tauri/src/plugins.rs` —— 供应链海关（713 行，本 PR 新增）

**职责一句话**：外置插件的仓库管理员兼海关——扫描货架、验放货品、读出货物、下架货品，全部系统触达收在六个 `#[tauri::command]` 里。

**关键依赖**：五个新 crate 全部构建期静态编译进二进制（Rust 侧没有"打包"概念之外的存在形态）。`ureq` 是社区最主流的极简 HTTP 客户端之一（crates.io 下载量亿级、纯 Rust、同步 API），本仓库用法是它最简单的形态——两个裸 GET；`tls` feature 拉进 rustls + webpki-roots（根证书**编译进二进制**，运行期不读系统钥匙串——环境无关铁律的直接体现：用户机器不需要任何证书配置）；`flate2` 指定 `rust_backend`（minoz_oxide 纯 Rust 解 gzip，避免碰 zlib C 库）；`tar`/`sha2`/`base64` 是 Rust 生态的事实标准件。比喻：这不是给房子接市政管网（长期运行时依赖），是自带水泵的一次性打井队——打完井（下载安装）就撤，井水（本地插件文件）之后随便用。

**变更代码块分析**（A 文件，按数据流走读五块）：

**块 ① 契约解析（:63-106）**——五条判据顺序点名，每条失败返回带插件名的错误：

```rust
if !pkg.keywords.iter().any(|k| k == "studywiki-plugin") { ... }   // 身份标记
match &pkg.dependencies {
    None => Err("缺 dependencies（必须显式空对象）"),              // 不写 = 拒
    Some(deps) if !deps.is_empty() => Err("非空（必须零依赖）"),   // 写了有货 = 拒
    _ => {}
}
if block.entry.contains('/') || contains('\\') || contains("..") { Err("必须是顶层单文件") }
```

为什么 `dependencies` **缺字段也拒**而不当空处理：封闭契约的可机械审计性——"零依赖"必须是一个作者显式声明的状态，而不是解析器的默认补全；否则构建期夹带依赖的包会在"字段缺失"的掩护下过检。entry 的顶层单文件规则在这里单一决策（tgz 校验不重复判，注释 :238-239 点名），后续 `read_entry_source`（:171）用 `plugin.join(&block.entry)` 拼路径时因此无穿越面——**校验与使用之间不需要防御性重复**，这是把规则收敛到单一决策点的收益。

**块 ② tgz 校验（:240-304）**——解包同时验形，输出 `ExtractedPlugin { name, block, code, raw_package_json }`（package.json 原文保留，落盘原样写回不重建——作者字段不丢）。三防 + 一闭包：

```rust

if path.contains("..") || path.starts_with('/') { return Err(可疑); } // 防线②：穿越/绝对路径

    return Err("必须恰好含 package.json 与入口");                    // 闭包：两文件
}
```

防线①的取舍值得注意：symlink 条目**跳过**而非报错，注释给的证据链是"我们不落盘 tar 原条目而是重写新文件，无穿越面"——tar 里的 symlink 指向什么根本不会被带到磁盘。测试用手工改写 tar 头的恶意样本验证防线②（:603-626，`tar::Builder` 拒绝写 `..` 路径所以测试直接伪造条目头），这个测试写法本身就是对 tar crate 行为边界的实测记录。

**块 ③ 原子落盘（:308-320）**——staging 模式五步。崩溃窗口分析见 §6.2（旧目录删早了一步）；staging 名 `.staging-<name>` 以 `.` 开头正是 `scan_plugins`（:130-132）跳过它的原因——两处约定咬合。

**块 ④ 联网薄层（:330-389）**——`resolve_registry` 只做一次 GET + JSON 取三个字段（dist-tags.latest 或指定版本 → dist.tarball → dist.integrity），scoped 名 `%2F` 转义；`install_plugin` 第二次 GET 拉 tarball 字节。`install_bytes`（:363-372）把"校验 → 解包 → 落盘"串成下载后公共管线，本地导入免 integrity 复用同一条——**联网与离线路径只在"字节从哪来"分叉，验货标准完全一致**。registry 固定公网 npmjs 不内置镜像（:190 注释：用户侧差异交给系统级代理）——少一个配置面就少一个行为分叉点，与环境无关条款 3 同构。

**块 ⑤ 命令壳（:377-423）**——六个命令薄到只是把 AppHandle 换成 `plugin_dir` 再调纯函数，联网函数不进单测（注释 :328-329 划界），`list_plugins` 在 plugin_dir 取不到时降级为单行 problem（:402-409）而不是 Err——面板永远能打开。

**实现思路总结（三行）**：① 纯函数分层把可测面（解析/校验/落盘/扫描）与联网面（两个 GET）切开，15 个 Rust 测试全部零网络；② 防御收敛——名字安全、entry 顶层、两文件闭包各是单一决策点，使用侧不重复防御；③ 一切失败点名到字段，与全仓 fail-loud 纪律一致。

**检视发现**：scoped 包半支持（§6.1，新发现）；place_plugin 时序窗口（§6.2）；ureq 读超时（§6.3）与大小上限（§6.4）为 PR 已披露项，复核属实。其余无发现——测试密度（290/713 行）与实现密度匹配，恶意样本测试的写法扎实。

### 9.2 `src/loader/external.ts` —— 装载缝（21 行，本 PR 新增）

**职责一句话**：把一段插件源码文本变成一个 ES 模块命名空间对象，全前端只此一家。

**关键依赖**：零 import——Blob / URL / import() 全是 web 平台内建。这正是它能当"缝"的资格：没有依赖面就没有依赖面的攻击面/维护面。

**变更代码块分析**：

```ts
export async function loadExternalModule(
  code: string,
  importFn: (url: string) => Promise<Record<string, unknown>> = (url) => import(/* @vite-ignore */ url),
): Promise<Record<string, unknown>> {
  const blob = new Blob([code], { type: "text/javascript" });
  const url = URL.createObjectURL(blob);
  try { return await importFn(url); }
  finally { URL.revokeObjectURL(url); }
}
```

四个部件各答一个问题：**Blob**（内容 → 有 MIME 的二进制对象）——为什么需要它：`import()` 只吃 URL，不吃字符串，Blob 是"内容"到"URL"的标准桥；**type: "text/javascript"**——告诉引擎这是 ESM 源码不是数据；**importFn 参数**——把"真 import"从函数体里吊出来变成可注入参数，vitest 里塞假实现即可测"Blob 内容逐字传递"这种细节（`tests/loader-external.test.ts:16-19`），同时 `/* @vite-ignore */` 只需要出现在默认实现这一处；**finally revoke**——无论成功失败 URL 都作废，泄漏面归零。单文件零依赖契约与 blob 弱点的对合关系（相对导入无处可指、URL 生命周期有 finally）在文件头注释（:1-8）和 Phase 2 Note 决策 1 各记了一遍——代码注释管"现在是什么"，Note 管"为什么选它"，分层正确。

**实现思路总结（三行）**：① 21 行里没有一行是"逻辑"，全部是"契约"——这正是缝的样子；② 注入参数让唯一动态 import 同时是唯一可离线测试的动态 import；③ CSP（conf 侧）与 layering 白名单（门禁侧）从两个方向把它锁成单点。

**检视发现**：无。若吹毛求疵：`importFn` 返回类型 `Record<string, unknown>` 与调用方 `Partial<PluginModule>` 之间有一次 as 断言（host/plugins.ts:98）——形状校验紧跟其后（:99-107），断言风险被校验兜住，可接受。

### 9.3 `src/host/plugins.ts` —— 第五插座（111 行，本 PR 新增）

**职责一句话**：外置插件的包管理 + 装载收口——面板看到的一切插件操作都经它，boot 装载外置行也经它。

**关键依赖**：`@tauri-apps/api/core` 的 invoke 与 `@tauri-apps/plugin-dialog` 的 open（官方第一方包，Phase 1 已在 dep-allowlist；本文件是全前端少数合法 import Tauri 的位置之一——host 层特权，`verify:layering` 机械看守）。`loader/external.ts` 以默认参数身份进 `defaultPluginsDeps`——装载缝经服务暴露而非直接暴露给插件，插件层拿不到 importFn。

**变更代码块分析**：

**块 ① 支持集常量（:8）**：`SUPPORTED_API_VERSIONS = [1]`，readonly，注释"扩集必须回 Phase 2 Note 修订"。apiVersion 是宿主与外置作者之间唯一的版本协商通道：宿主升 apiVersion 2 时这里是第一改动点，旧插件拒载点名的信息里带双方版本（:96 的错误文案），作者一看就知道差在哪。

**块 ② loadModule（:90-109）**——五步收口，每步失败都是点名错误：

```ts
const src = await invoke("read_plugin_module", { name });            // Rust：读源码+apiVersion
if (!SUPPORTED_API_VERSIONS.includes(src.apiVersion)) throw ...      // 版本协商
const mod = await this.#deps.loadExternal(src.code);                 // blob 装载
if (typeof mod.name !== "string" || mod.name.length === 0) throw ... // 形状：name
if (typeof mod.apply !== "function") throw ...                       // 形状：apply
if (Array.isArray(mod.inject) && mod.inject.some(k => typeof k !== "string")) throw ...
return mod as PluginModule;
```

注意 inject 的校验形态：**是数组时逐项查字符串，不是数组时放行**——字符串/对象等非法形态会透传给 cordis（PR park 项"inject 非数组透传"）。透传的终点是 boot 审计（cordis 对非法 inject 的反应是 fiber 卡死 → broken 行），所以是 fail-visible 而非 fail-silent，但错误信息从"inject 必须是字符串数组"退化成"审计未激活"——归因变难。fast-follow 一行收紧（`mod.inject !== undefined && !Array.isArray(...)` 即拒）。

**块 ③ bootBroken 通道（:48 + bootstrap 回填）**：服务带一个公开可变数组，bootstrap 在 boot 后 `plugins.bootBroken = report.broken`（`bootstrap.ts:82`）。设计上这是"启动期一次性事实"的传递，不是事件流——面板 render 时读一次即可。若将来做热装载，这个字段语义会不够用，届时再演进。

**实现思路总结（三行）**：① 与 Phase 1 四服务完全同构（deps 接口 + 默认绑定 + 薄方法），第六个插件的开发成本因此接近零；② 装载的"判定"（版本/形状）收在服务而"执行"（blob）收在 loader——判定逻辑可在任何测试环境跑；③ 清单读写也收进来，面板因此成为纯消费者。

**检视发现**：inject 非数组透传（PR 已列 fast-follow，§6.5 同捆）；其余无发现。

### 9.4 `src/loader/manifest.ts` —— 存量迁移（修改，53 → 65 行）

**职责一句话**：清单账本新增"补记"能力——版本升级带来的新内置插件自动入账。

**变更代码块分析**（旧 vs 新，只动读路径中段）：

### 9.5 `src/loader/boot.ts` —— 第二来源与分治（修改，26 → 67 行）

**职责一句话**：boot 学会认第二种清单行（ext:），并给外置行配了一套"隔离病房"语义。

**变更代码块分析**（两块核心改动）：

**块 ① 循环体内新分支（:33-44）**：

```ts
if (row.id.startsWith("ext:")) {
  const name = row.id.slice(4);
  try {
    const plugin = await loadExternal(name);
    const fiber = ctx.plugin(plugin, row.config);   // config 直传，无 defaults 合并
    states.push({ id: row.id, state: () => fiber.state });
    loaded.push(row.id);
  } catch (e) {
    broken.push({ id: row.id, reason: (e as Error).message });  // 分治：跳过不阻断

  continue;

```

与内置行路径的三个刻意差异：装载来源（表查找 → 回调注入）、config（merge defaults → 直传，外置插件无 defaults 来源）、失败语义（查不到表项 throw → 装载任何失败 catch）。第三个差异是整个 Phase 2 错误哲学的浓缩：**内置插件失败是产品 bug（fail-loud 停机点名），外置插件失败是用户数据问题（分治进报告，应用照起）**。签名从 `Promise<void>` 变 `Promise<BootReport>`（:7-11），报告两个数组就是两条出口。

**块 ② 审计分家（:53-65）**：stuck 集合先按 `ext:` 前缀分成两半——内置半照旧抛（错误文案逐字未动），外置半进 broken 且从 loaded 除名。除名是账面操作（fiber 还在树上），与 §6.8 的误报残留同源。

**实现思路总结（三行）**：① 新增行为全部圈在 `ext:` 前缀分支内，内置路径零扰动（"fail-loud 逐字不变"的 PR 声明与 diff 相符）；② loadExternal 作为第四参数注入，boot 不 import 宿主服务——装载器不知道服务层的存在，测试传 `noExt`（一抛错的桩）即可断言"内置路径永不触达装载通道"；③ 报告即接口，bootstrap 与面板都只消费 {loaded, broken}。

**检视发现**：`"ext:"` 字面量与 `slice(4)` 在 boot.ts:33-34、model.ts:34-35、（注释里的）manifest.ts 三处出现——前缀是隐式共享常量。改动频率趋零，不立项；若将来动前缀，grep `"ext:"` 三处一起改即可。

### 9.10 assetProtocol 收权三件 —— `src-tauri/src/windows.rs` + `src/host/windows.ts` + `src/plugins/app-windows/index.ts`（修改，成组）

**职责一句话**：把"出厂自带全盘读卡"换成"到访登记发卡"——配置 scope 收空，运行期三个时机动态授权。

**变更代码块分析**（跨三层走一遍授权链）：


```rust

    if let Some(root) = &root {
        app.asset_protocol_scope().allow_directory(root, true)?;  // 失败即 Err，下面不执行
```

**实现思路总结（三行）**：① 授权点的唯一性靠"配置收空 + 单命令"双向保证——除了 set_window_root/create_window 没有第二处 allow；② fail-closed 顺序让"登记了但放不了行"这个不一致状态不可达；③ 已知局限（授权只增不减、app 级共享）在 Note Consequences 在案，属 Tauri FsScope API 面的硬限制。
