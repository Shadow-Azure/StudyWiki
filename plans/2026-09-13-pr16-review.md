## 这个 PR 想合入什么

Phase 2（#15）把插件的**消费者侧**建完了：用户能在面板里装包、导入 tgz、开关插件。但**作者侧**还是手工活——想写个插件，得对着 PR 描述里的文字契约手搓 package.json、手配 npm 打包、手动核对每个字段，搓错了要到"用户安装那一刻"才被宿主拒载。同时 Phase 2 终审留了五笔加固欠账（网络挂起无超时、包大小无上限等），以及一笔只做了一半的提案：assetProtocol 协议面收权了，但文件命令面还收任意绝对路径。

打个比方：Phase 2 装好了超市的收银台（扫描、验货、上架），Phase 6 这个 PR 做两件事——**给供货商发一套"月饼模子 + 出厂质检单 + 说明书"**（脚手架生成器、发布前校验、作者指南），让你倒进一个名字就能得到整套合格的 npm 包；**同时给收银台补装五道门闩和一道闸机**（超时、限重、拒畸形包、面板不崩、文件命令只认授权目录）。

读完后应能回答三个问题：插件作者从零到发布要做什么（一条命令起步）；宿主加固到底防什么、不防什么（防意外与 DoS，**不是沙箱**——插件同进程全权）；代价是什么（同一份契约现在有四份表达，同步靠流程）。

## 2. 架构导览

### 2.1 脚手架生成器（`scripts/gen-plugin-template.mjs`，本 PR 新增，135 行）

纯 Node 脚本，仓库零新增依赖。两个导出 + 一个 CLI 入口：

- `validateName`（`gen-plugin-template.mjs:10-12`）：小写字母/数字/连字符，≤100 字符——与宿主安装名同风格，顺手拒掉 `../evil`、`demo/hello` 这类路径形态（名字会变成磁盘目录，不能带分隔符）。
- `renderTemplate(name)`（`:17-111`）：**模板即一张文件表**（相对路径 → 内容字符串），四件套：
  - `package.json`：`keywords` 含 `studywiki-plugin`、`dependencies: {}`、`files: ["index.js"]`、`studywiki: {apiVersion: 1, entry: "index.js"}`、`prepublishOnly` 自动 build+check；
  - `src/index.ts`：顶栏 hello 示例（`name`/`inject`/`apply` 三段式）；
  - `src/host.d.ts`：本地最小类型副本（只有示例用到的 `slots.register` 一角）——不发类型包，代价是可能漂移，指南声明"以本页为准"；
  - `scripts/check.mjs`：发布前校验（见 2.2）。
- CLI 入口（`:114-135`）：取 `argv` 里第一个非 `--` 参数（pnpm 会把 `--` 原样透传——本项目踩过的坑）、校验名字、目录已存在即拒（不覆盖作者的工作区）、落盘。

**为什么模板不带 README**：npm 打包时无条件收进 `package.json` + `README*` + `LICENSE*`。宿主契约要求 tgz 恰好两文件，带 README 必三文件必被拒。作者侧文档住 StudyWiki 的 authoring.md，不重复。**为什么模板内嵌而非独立仓库**：独立仓库没有门禁看护，漂移无人发现；内嵌 + spec 钉渲染字节，宿主改契约时模板漂移在 `pnpm test` 即红（Note Alternatives 第一条）。

### 2.2 check.mjs：作者侧的镜像质检（模板内，`gen-plugin-template.mjs:69-110`）

这是同一封闭契约的**作者侧镜像**：宿主 `parse_package_json`/`extract_and_validate` 在**安装时**拒坏包，check.mjs 在**发布前**就拒——fail at publish, not install。校验项：keyword、dependencies 显式空、apiVersion===1、entry 是顶层单文件（拒 `/` `\` `..` 与 `package.json`）、`files` 只含入口、`npm pack --dry-run --json` 断言发布面恰好 `entry + package.json`。

两个工程细节：npm 各版本 `files[].path` 前缀形态不一（新版无前缀旧版带 `package/`），统一剥前缀再比（`:103-105`，生成环境实测为防御性 no-op）；`npm publish` 走 `prepublishOnly` 自动先 build+check，上传前必过质检。

### 2.3 作者指南（`docs/plugins/authoring.md`，本 PR 新增三件套）

进常驻文档体系（预算/配对/索引全登记）。三块内容：**封闭契约表**（`authoring.md:9-20`，每行标注校验方——宿主/生成器/check.mjs 分工，比如包名行如实写"check.mjs 不校验 name，手改后先对照本行"）；**全流程**（生成→安装→构建→校验→试装→发布，`:22-50`）；**信任模型**（`:52-54`）——最重要的一句披露：插件与宿主同一 webview JS 世界，**同进程全权，apiVersion/零依赖/单文件是当前全部防线，不是沙箱**（Obsidian 前鉴）。本地导入内环**重启生效**，无热装载（Phase 2 裁定不重开）。

### 2.4 宿主加固捆包（`src-tauri/src/plugins.rs`，M）

四项，全部落在 Phase 2 建好的管线上：

- **entry 拒 package.json**（`plugins.rs:104-109`）：`parse_package_json` 是装/载共用的单一决策点，在此拒绝即两路同拒。封的是"双 package.json 计数旁路"——extract 判"恰好两文件"时若 entry 就是 package.json，同一文件会被数两次冒充合规。
- **20MiB 限重**（`:201-204` 常量，`:213-222` `read_capped`）：`take(cap+1)` 读满再比——多读 1 字节即可分辨"正好 cap"与"超了"，测试钉了 100/101 边界（`:589-595`）。下载（`install_plugin`，`:415-417`）与本地导入（`import_plugin`，`:422-426`，从无界 `fs::read` 改为 File 流式）同限。
- **30s 整体超时**（`:206-210` `http_agent`）：ureq 2.12.1 `AgentBuilder::timeout` 是**从连接到响应体读完**的整体超时（本机 registry 源码 doc 例："wait max 1 second for whole request to complete"；优先于 timeout_read/write）——registry 查询（`:366-371`）与 tarball 下载（`:408-411`）两调用点共用一个 Agent。断网点名安装从"永远没有回音"变成 30s 内联报错。
- **面板包错**（TS 侧，见 2.6）+ **inject 拒载**（TS 侧，见 2.5 末）。

口径提醒（PR 描述原文）：这些是 **DoS 加固面而非安全边界**——同进程全权信任模型下，恶意插件本来就能做更多；上限防的是意外与资源耗尽。

### 2.5 命令面根域校验（`src-tauri/src/lib.rs` + `windows.rs`，M）——dynamic-asset-scope 提案闭环

Phase 2 收空了 assetProtocol 静态 scope，但 `read_tree`/`read_text_file`/`write_text_file` 仍收任意绝对路径。本 PR 加**闸机**：

- 准源 = `WindowRegistry::roots()`（`windows.rs:30-34`）：每个窗口"当前打开的文件夹"，由 `set_window_root`（`windows.rs:78-90`）在用户选目录时写入（同一动作也 `allow_directory` 授权 asset 协议——命令面与协议面同源）。
- 判定点 = `path_authorized`（`lib.rs:79-98`），三步：①路径含 `..` 组件直接拒——**词法层先收口**，因为 `Path::starts_with` 保留组件语义，`/lib/root/../evil` 前缀恰好匹配 root，但 OS 解析后落在 root 外（Phase 1 §6.1 系列的词法逃逸家族，`c7c5d46` 修复 + 两条 RED 测试钉死，`lib.rs:203-210`）；②任一 root `starts_with` 命中即放行（组件级，`/lib/rootx` 不算 `/lib/root` 内）；③否则拒"路径不在任何已授权文件夹内（先打开文件夹）"。
- 三命令各加 `state: State<Mutex<WindowRegistry>>` 参数 + `ensure_authorized`（`lib.rs:110-145`）——**欢迎态（roots 全空）三命令全拒**，这正是 boot-error 补"或重新打开文件夹"出口的原因（`boot-error.ts:17`）。
- TS 侧配套：外置模块 `inject` 非 `undefined` 且非字符串数组即拒（zod schema，`src/host/plugins.ts:16-29`——该实现随 #15 审检进 main，本 PR 带的是测试钉子 `tests/host-plugins.test.ts:64-75`）。

PR 口径值得原样记住：这是**权限面与用户意图一致性**的加固（`set_window_root` 本身是 webview 可调的授权注入点），**不是**对抗 webview 内恶意代码的边界——那由信任模型披露承接。另：窗口 A 可读窗口 B 的 root（roots 是并集，app 级共享授权），与 asset scope 已知局限一致。

### 2.6 面板 render 包错（`src/plugins/plugin-manager/index.ts:55-105`）

旧代码只把 `JSON.parse` 圈进 try——`readManifest`/`list` 的 reject 直接飞出 async 函数成 unhandled rejection，面板卡在陈旧 DOM。新代码整个 render 体包 try/catch：失败走 `showError`（errLine 内联显示），且 `box.replaceChildren(errLine, hint)` 把读不出来的陈旧列表**清掉**（`:99-104`）。一个支撑性设计：`errLine`/`hint` 是跨 render 复用的同一元素（`:38-46` 注释说明）——整体重渲染会重建其余节点，错误行想活过重渲染就得复用引用。

## 3. 数据流走查（主线剧本）

**剧本 A：一个插件从诞生到顶栏**（作者旅程，人工验收第 1 条的代码面）：

1. `pnpm gen:plugin -- demo-hello`（`gen-plugin-template.mjs:114-135`）→ 校验名字 → 落四文件到 `plugins-dev/demo-hello/`；
2. 作者 `cd plugins-dev/demo-hello && npm install && npm run build`：esbuild 把 `src/index.ts` 打成单文件 `index.js`（devDependencies 只装作者机器，宿主 dep-audit 看不见）；
3. `npm run check`：check.mjs 逐项断言 + `npm pack --dry-run` 验发布面恰好两文件 → `check: OK`；
4. `npm pack` 出 tgz → 宿主面板"本地导入…" → `import_plugin`（`plugins.rs:422-426`）`read_capped` 限重 → `extract_and_validate`（`:271-332`）封闭契约校验（entry 拒 package.json 在 `parse_package_json:104-109`）→ 原子落插件目录；
5. 重启（无热装载）→ boot 读清单 `ext:` 行 → `read_plugin_module` → blob URL 装载 → zod 形状校验（`host/plugins.ts:118-124`）→ `apply(ctx)` → `ctx.slots.register("topbar.left", …)` → 顶栏出现 hello 按钮；
6. 发布：`npm publish` → prepublishOnly 自动 build+check → 上传。之后任何用户在面板输入 `demo-hello` 安装，走 `install_plugin`（`resolve_registry` 查元数据 → `http_agent` 30s 超时下载 → sha512 → 同一校验管线）。

**剧本 B：闸机的一天**（根域校验）：

1. 冷启动欢迎态：roots 空 → 任何 `read_tree("/etc")` 在 `path_authorized` 第③步拒："先打开文件夹"；
2. 用户点"打开文件夹"选了 `/Users/me/wiki` → `set_window_root` → `allow_directory` + 注册表记 root → `read_tree("/Users/me/wiki")` 放行；`/Users/me/wiki/../secrets` 在第①步拒（`..` 组件）；`/Users/me/wikix` 第②步拒（组件级不匹配）；
3. 编辑保存 `write_text_file` 同受闸机管，成功后广播 `fs://changed`；
4. 关掉窗口 → `WindowEvent::Destroyed`（`lib.rs:152-160`）注册表 remove → 该 root 失效，回欢迎态语义。

## 6. 检视关注点（讨论题）

### 6.1 extract 展开侧无预算：20MiB 闸门称的是压缩包，不管解开后【fast-follow #1 复核，确认在档】

- **位置**：`src-tauri/src/plugins.rs:296-299`（`entry.read_to_end(&mut bytes)` 无界）
- **现象**：`read_capped` 限的是 tgz 压缩字节（≤20MiB）；gzip 压缩比可达千倍，一个 20MiB 的压缩包可在 extract 循环里展开出数 GB（经典 zip bomb 形态），再经 `place_plugin` 落盘写满。
- **问题**：加固链有个残余窗口——限重在压缩侧，展开侧无预算。
- **预判**：PR 已列 fast-follow（"累计已读上限如 64MiB"），复核维持。修法就地在循环里累加 `bytes.len()` 判上限，改动极小。定性不变：封闭契约下这是 DoS 加固面而非安全边界（触发前提是用户主动装恶意包，而恶意插件在同进程全权模型下本有更直接的路）。无实害紧迫感，按 fast-follow 排即可。
- **结论**：＿＿＿

### 6.2 Windows 作者面：check.mjs 的 `execFileSync("npm")` 按官方文档口径不可无 shell 启动 .cmd【检视新发现】

- **位置**：`scripts/gen-plugin-template.mjs:100`（模板内 `execFileSync("npm", ["pack", …])`）
- **现象**：Windows 上 npm 是 `npm.cmd`；Node 官方文档口径是 `.bat/.cmd` 不能被 `execFile` 直接启动、需 `shell: true`，且 18.20+/20.12+（CVE-2024-27980 修复后）默认更显式拒绝。**未在 Windows 实测**，按文档口径记录。
- **问题**：Windows 作者 `npm run check` / `npm publish`（prepublishOnly 链）可能直接 ENOENT/EINVAL 红。CI 的 frontend lane 只在 ubuntu 跑（spec 真跑 npm pack 也是 ubuntu），不覆盖此路径；且 spec 用 `process.execPath`（node）直跑 check.mjs，绕过了 npm 入口——即 CI 永远测不到"npm 可执行性"这一环。
- **预判**：与 fast-follow #2（`:` 盘符，"作者面按 macOS/Linux 计"）同册——建议合并处理：要么 authoring.md 明示平台支持面，要么 check.mjs 加 `shell: process.platform === "win32"`（一行）。宿主三平台 CI 绿不受影响，纯作者机器面。
- **结论**：＿＿＿

### 6.3 关窗/回欢迎态：命令面闸机落杆了，asset 协议面还留着旧授权【检视新发现】

- **位置**：`src-tauri/src/windows.rs:84-88`（`set_window_root` 仅 `Some(root)` 时 `allow_directory`，`None` 分支只清注册表）；对照 `lib.rs:79-98` 命令面全拒。
- **现象**：Tauri 2 的 `AssetScope` 只有 allow/deny，没有撤销 API。用户关文件夹回欢迎态后：命令面三命令全拒（注册表空），但 assetProtocol scope 里仍持有旧目录——webview 内 `<img src="asset://…">`（或 JS fetch）仍可读旧 root。
- **问题**：同一时刻两道门一道关一道开，与"权限面与用户意图一致"的提案口径有偏差（用户意图已撤，asset 面没撤）。触发面窄：欢迎态下插件仍装载着（清单不随关夹清空），恶意插件可绕命令面走 asset 面读旧目录——但同进程全权模型下它本可以直接等用户再开夹，或在开夹期间用命令面。**无实害，口径一致性问题**。
- **预判**：fast-follow 册——`set_root(None)` 时对旧 root 补 `deny_directory`（或评估 scope 重建）。不宜在检视中即修（涉及 Tauri API 行为实测：deny 对已 allow 的覆盖次序）。
- **结论**：＿＿＿

### 6.4 同一契约四份表达：宿主收紧时，作者侧同步靠流程无机械看护【结构性】

- **位置**：宿主 `parse_package_json`/`extract_and_validate`（Rust）↔ 模板 check.mjs（`gen-plugin-template.mjs:69-110`）↔ 指南契约表（`authoring.md:9-20`）↔ zod moduleShape（`host/plugins.ts:16-29`，模块导出面）
- **现象**：spec 钉的是**渲染字节**——它保证"模板没被随手改"，不保证"宿主改了契约后模板跟着改"。宿主明天把上限调成 10MiB 或加一条拒点，check.mjs 与指南表不会红。
- **问题**：漂移方向是"宿主收紧、作者不知情"——作者 check: OK 但宿主拒装，恰好退化回 check.mjs 要消灭的 fail at install。Note Consequences 已如实承认（"宿主改封闭契约须同步模板与指南（文档连锁）"）。
- **预判**：接受为已知代价（Note Alternatives 裁过：模板独立仓库更差）。低成本缓解可考虑：spec 里把宿主侧拒点文案关键词（如"不得是 package.json"）与 check.mjs 文案做成同词断言，让最常见的"加拒点不同步"至少在文案层显形。是否值得做，留拍板。
- **结论**：＿＿＿

### 6.5 check.mjs 不校验 name（fast-follow #3 复核维持）

- **位置**：`gen-plugin-template.mjs:81-98`（断言清单里无 name 项）；`authoring.md:13`（表格如实标注"check.mjs 不校验 name——手改后先对照本行"）

- **结论**：＿＿＿

### 9.1 `scripts/gen-plugin-template.mjs` —— 月饼模子（135 行，A）

**实现思路总结**：模板即数据（一张路径→内容表），渲染可测；字节级 spec 钉死使"模板被改"必红，把契约漂移的看护前移到 `pnpm test`。

### 9.2 `src-tauri/src/plugins.rs` —— 收银台加固（M，+40/−5）

**职责**：外置插件供应链的宿主侧海关。**变更形态**：M；前身（`git show origin/main:src-tauri/src/plugins.rs`）已有封闭契约校验，本 PR 加四项加固。

**变更代码块对照**：

- entry 拒 package.json（`:104-109` 新增）：
  ```rust
  if block.entry == "package.json" {
      return Err(format!("studywiki.entry 不得是 package.json（{}）", pkg.name));
  }
  ```
  这在做什么：extract 的"恰好两文件"判定（`:313-317`）按名字数文件，entry 指向 package.json 时同一文件被数两次，可冒充合规。拒点放在 `parse_package_json`——它是安装与装载共用的单一决策点，一处拒两路同拒（对照：另一种写法是在 extract 里判，但要判两处）。
- 限重（`:213-222` 新增）：
  ```rust
  r.take(cap + 1).read_to_end(&mut buf)?;   // 多读 1 字节分辨"正好"与"超"
  if buf.len() as u64 > cap { return Err(…); }
  ```
  为什么 take(cap+1)：直接 `take(cap)` 读满无法区分"恰好 cap"与"被截断的超限"，+1 一字节即得全信息。
- 超时（`:206-210` 新增 + 两调用点接线）：`http_agent()` 造共用 Agent；ureq 2.12.1 `timeout()` 语义已实测（registry 源码 doc：整体请求含响应体，优先于读写超时）。旧代码 `ureq::get(&url)` 每次裸调无超时。
- 导入（`:422-426`）：
  ```rust
  // 旧：let bytes = fs::read(&path)?;            // 无界：多大文件读多少进内存
  // 新：let file = fs::File::open(&path)?;
  let bytes = read_capped(file, MAX_TARBALL_BYTES)?;
  ```
  下载与本地导入从此同一限重通道（20MiB，`:201-204`，DoS 加固裁量值——封闭契约下单文件插件远低于此）。

**实现思路总结**：四项全部落点在"既有单一决策点"上（parse/read/agent），不新增判定分支数；每项配 RED→GREEN 测试（`:583-595`）。

**检视发现**：§6.1（展开侧 `:296-299` 无界，fast-follow 在档）。`safe_plugin_name` 的 `:` 窄边见 §6.6。

### 9.3 `src-tauri/src/lib.rs` —— 闸机决策点（M，+62/−5）

**职责**：宿主命令入口 + 本 PR 新增的文件命令根域校验。**变更形态**：M；前身三命令直收路径字符串。

**变更代码块对照**（以 `read_tree` 为例，`read_text_file`/`write_text_file` 同型）：
