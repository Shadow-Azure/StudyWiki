## 这个 PR 想合入什么

m1 承诺"markdown / excel / 视频三格式可读"，前两样有了，excel 一直是空白——文件树里点到 `.xlsx`，只会被当"other"列出，打不开。这个 PR 把这条路修通，并且顺手把**将来编辑要用的读写管道**也一并铺好了。

打个比方：以前前端和 Rust 之间送信只能走"逐字抄写的信使"（JSON——一个 5MB 的 xlsx 会被拆成 500 万个数字排队过关口，内存和 CPU 都遭殃）。这个 PR 做了五件事：① 修了一条**货运传送带**（Tauri 2 raw IPC：二进制整箱搬运，路径走 `x-studywiki-path` 这个"包裹面单"header，不再塞进货箱里）；② 在 Rust 侧开了**字节收发窗口**（`read_binary_file` / `write_binary_file`：Rust 不理解 Excel，只负责验明正身——路径授权——搬箱子，写入用"同目录临时文件 + rename"的原子落盘防写一半断电留残局）；③ 请了一位**排版专家驻场**（ExcelJS：解析和序列化 xlsx 的唯一数据模型，构建期打包进产物，不联网）；④ 把专家包装成**第六个服务窗口** `ctx.excel`（独立于 `ctx.files`，人和未来的 AI agent 走同一个窗口办事）；⑤ 摆了一张**带放大镜的阅览桌**（doc-excel 查看器：多 sheet 页签、样式/合并单元格渲染、虚拟滚动——十万行的表也只渲染视口附近的几十行）。

读完应能回答三个问题：它解决"`.xlsx` 打不开、二进制走 JSON 内存爆炸、未来编辑没有读写面"三个问题；做法是 raw IPC 字节通道 + 前端 ExcelJS 唯一数据模型 + 纯函数视图模型 + 虚拟窗口渲染；代价是 bundle 涨到 1.7MB（gzip 549KB，spec 已登记的已知后果）、大表全量 workbook 驻留前端内存（1M 单元格上限兜底）、格式化只覆盖常见子集（怪格式回退到 ExcelJS 原文）、图表/透视表不承诺无损。

## 2. 架构导览

### 2.1 Rust 字节边界：验明正身再搬箱，不理解箱子里是什么

`src-tauri/src/lib.rs` 新增三个部件，全部围绕"Rust 只碰字节"：

- **扩展名分派**（`lib.rs:25,32`）：`EXCEL_EXTS = ["xlsx"]` 进 `kind_for_ext`，`FileNode.kind` 的 Rust/TS 同形契约（`src/types.ts:7`）由 architecture.md 的 type-equiv 围栏机械钉住。`xls`/`csv` 明确不收（Note 决策：未来另立 issue）。
- **路径面单解码**（`lib.rs:141-180`）：raw IPC 的 body 被字节占用了，路径改走 header——但 HTTP header 只能带 ASCII，所以前端 `encodeURIComponent` 编码，Rust 侧 `decode_path_header` 纯函数解码（`lib.rs:144-168`，逐字节 `%XX` 展开，非 UTF-8 拒绝）。`request_path`（`lib.rs:170-180`）把"取 header → 必须是 ASCII 字符串 → percent 解码"收成一步，且**在授权与任何 FS 访问之前**执行。
- **两条命令**（`lib.rs:211-243`）：`read_binary_file` 返回 `tauri::ipc::Response`（raw bytes 出参，避开 JSON 序列化）；`write_binary_file` 显式匹配 `InvokeBody::Raw`，**JSON body 直接拒绝**（`lib.rs:233-237`）——这行分支是"货运传送带不收货信"的机械保证，防止未来某个调用方退化回 JSON 数组而不知。写入成功广播 `fs://changed`，与文本写同口径（各窗口树重读）。
- **原子写**（`lib.rs:87-112`）：同目录 `.{name}.studywiki-{pid}-{seq}-{nanos}.tmp` 临时文件 + `fs::rename` 正主替换。三层防碰撞（进程号 + 进程内原子序号 + 纳秒时间戳）；rename 失败清理临时文件不留残局。同目录保证同文件系统，rename 才是原子的。

### 2.2 raw IPC：从"逐字抄写的信使"到"集装箱货运"

**为什么需要它**。Tauri 应用是两个内存隔离的世界——Rust 后端（有权碰磁盘）和 WebView 前端（负责画界面），说话只能靠 IPC 跨进程传消息。Tauri 默认的 `invoke` 走 JSON：参数和返回值都序列化成 JSON 文本。传路径、传文字没问题，但 xlsx 是二进制——一个 5MB 的文件走 JSON 返回要经历三重受难：Rust 把字节变成 `[137, 80, 78, ...]` 五百万个数字的数组 → 序列化成十几 MB 的 JSON 文本 → 前端 `JSON.parse` 再解析回五百万个 JS 数字。同一份数据在内存里至少存在三种形态，CPU 和内存双输。打个比方：**默认 IPC 是逐字抄写的信使**——寄一张便条没问题，寄一本书就是灾难；**raw IPC 是集装箱货运**——字节整箱封好整箱搬运，全程不拆箱不抄写，前端拿到的就是原始二进制。

**具体实现是三件套**。读方向的完整配合（`files.ts:79-90`）：

```ts
// body 是空 Uint8Array —— 不是 bug，是"让这趟车走货运通道"的车票
const bytes = await this.#deps.invoke("read_binary_file", new Uint8Array(0), {
  headers: { "x-studywiki-path": encodeURIComponent(path) },
});
```

1. **车票：空 `Uint8Array` body**。读请求明明没有字节要传，为什么还发空 body？因为 Tauri 2 运行时按请求形态选通道：`invoke` 收到 `Uint8Array` body 才走 raw 协议（`@tauri-apps/api/core.js:201` 的 `invoke` 委托给 `__TAURI_INTERNALS__.invoke`，raw 分支在注入 internals 里按 body 类型分派；Tauri 2.0 官方发布说明亦确认 raw request/response 是 IPC 重写的主卖点）。空 body 不载货，它的作用是"让这趟车走货运线"——换来响应以 raw bytes 而非 JSON 数字数组回来。
2. **面单：路径走 HTTP header**。body 被"走 raw 通道"这个用途占了，路径没地方放，于是挪到 header（IPC 底层是 WebView 自定义协议请求，天然支持 header）。但 HTTP header 只能携带 ASCII，中文路径 `/Users/zn/笔记/高数笔记.xlsx` 过不去，所以前端先 `encodeURIComponent` 编码成 `%2FUsers%2Fzn%2F...`——好比中文地址写不上国际面单，先翻译成拼音编码。
3. **Rust 三步走**（`lib.rs:211-219`）：`request_path` 拆面单（header → `decode_path_header` 逐字节 percent 解码，`lib.rs:144-168` 手写实现零新依赖）→ `ensure_authorized` 验明正身（路径必须落在窗口注册表已授权 root 内，欢迎态无授权即拒）→ `fs::read` 搬箱子。**解码和授权永远发生在触碰磁盘之前**——这是命令面的安全顺序，不是书写偏好。

出参用 `tauri::ipc::Response`（`lib.rs:218`）而非普通 `Result<Vec<u8>>`：返回它，字节就不经过 JSON 序列化，整箱直达前端。写方向（`write_binary_file`，`lib.rs:225-243`）同理反过来：body 直接就是字节，Rust 端显式匹配 `InvokeBody::Raw`，**JSON body 直接拒绝**（`lib.rs:233-237`）——"货运线不收货信"是机械保证，防止未来哪个调用方悄悄退化回 JSON 而没人发现。

`normalizeRawBytes`（`files.ts:24-31`）把响应归一到 `Uint8Array`：生产路径接受 `Uint8Array`/`ArrayBuffer`，`number[]` 分支是给测试 mock 留的兼容口（invoke 签名返回 `unknown` 的代价），其他形态 fail-loud。`BootstrapEnv.invoke` 的签名从 `Record<string, unknown>` 放宽到 `FilesInvokeArgs`（`bootstrap.ts:19`）——装配层类型跟着通道形态走，全仓唯一动这个签名的地方。

PR 自述这条路暂缺真实 in-process `Request` 集成测试（Known limit），当前由前端契约钉样（`tests/host-services.test.ts` 断言 invoke 参数逐字匹配）+ Rust header 解码/授权单测双侧夹住。

### 2.3 `ctx.excel`：第六个服务窗口，人与 AI 同一个窗口办事

`src/host/excel.ts`（66 行）是这个 PR 的枢纽。三个设计点：

- **双注入缝**（`excel.ts:4-12`）：`ExcelFiles`（字节读写，生产 = FilesService）+ `parseWorkbook`（parser，生产 = ExcelJS）。测试可以只替换 parser 注入预制 workbook（上限测试就是这么做的，`excel-service.test.ts` 用 `Object.defineProperty` 伪造 rowCount/columnCount）——不把 ExcelJS 类型漏进 DOM 层的同一条纪律，在测试侧兑现。
- **上限在解析后、按声明维度**（`excel.ts:47-52`）：`Σ max(1, rowCount) × max(1, columnCount) > 1_000_000` 拒绝。注意两个语义点：①上限是**事后检查**——文件已被完整解析进内存后才算这笔账，它保护的是渲染与模型驻留，不是解析内存峰值；②"单元格数"实为**声明维度乘积**，一个在 XFD1048576 留过格式痕迹的近空文件也会被拒。见 §6-D2。
- **错误包装**（`excel.ts:43-46,61-63`）：解析失败统一包装成 `读取 Excel 失败：…`，查看器据此出错误面板不白屏（`index.ts:297`）。`includes("过大")` 直通分支当前不可达，见 §6-D4。

为什么独立成服务而不是塞进 `ctx.files`？Note 的裁决：表格语义独立成服务，guard 白名单、AI 工具面、测试边界都干净；m2 AI 接入只需把 `excel` 加进 inject 声明，读写路径与人完全一致。

### 2.4 纯模型层：把 ExcelJS 的"活对象"晒成"干数据"

`src/plugins/doc-excel/model.ts`（386 行，零运行时依赖、零 DOM）做三件事：

- **结构子集隔离**（`model.ts:1-16`）：`SheetSource` 声明只取 ExcelJS worksheet 用到的几个方法/字段——DOM 代码不认识 ExcelJS 类型，将来换解析库只动这一层。
- **合并归一化**（`model.ts:265-302`）：`parseMergeRange`（`model.ts:258-277`）把 `A1:B2` 字符串解析成零基坐标并 clamp 到网格内（越界合并丢弃）；`owner` 矩阵标记每个格子归属哪个合并；被覆盖格 `hidden: true` 且不读其 text（注释写明根源：`model.ts:337`——ExcelJS 覆盖格 text getter 对空合并主格会抛）。一次归一进模型，渲染层按索引查，不反复扫 `sheet.model.merges`（commit `dd43f95` 修的就是"按大范围 cell 反复扫描"）。
- **格式化子集**（`model.ts:78-256`）：自写 `formatDate`/`formatNumber`，走 `Intl.DateTimeFormat`/`Intl.NumberFormat`（locale 固定 `en-CA` 取数字中性），支持常见 token（y/m/d/h/s、引用串、反斜杠转义、货币符、千分位、小数位、百分号），不支持的语法返回 `undefined` → 回退 ExcelJS 自带 text。`m`/`mm` 是月还是分钟由 `afterHour` 状态位猜（`model.ts:127-138`）——这个启发式是 §6-D1 的案发地。整个格式化包在 try/catch 里（`model.ts:245-247`）：展示增强绝不让网格崩。

### D1 `mm:ss` 时长格式被静默误渲染为"月份:秒"

- **位置**：`src/plugins/doc-excel/model.ts:127-138`（`afterHour` 启发式）
- **现象**：`m`/`mm` 是月还是分钟靠"前面见过 `h` 没有"猜。`hh:mm:ss`、`yyyy-mm-dd` 都猜对，但 Excel 合法格式 `mm:ss`（分:秒，计时/时长场景常用，Excel 语义里 `mm` 紧邻 `ss` 即分钟）会被渲染成"月份:秒"。**本检视实测**：`2026-09-21 14:05:09` 配 `mm:ss` 输出 `"09:09"`（应为 `05:09`）；对照组 `hh:mm:ss`→`"14:05:09"`、`yyyy-mm-dd`→`"2026-09-21"`、`h:mm AM/PM`→`"2:05 PM"`、`#,##0.00`→`"12,345.68"`、`0.0%`→`"12.3%"`、`$#,##0`→`"$1,234"` 全对。
- **问题**：这不是"不支持就回退"——`mm:ss` 被**错误地支持了**，输出一个看着正常但值错的文本。静默错误比回退到 ExcelJS 原文更糟：用户没有线索起疑。学习资料场景里计时/视频笔记类表格不算冷门。
- **预判**：修法二选一——①`mm` 后紧跟 `ss` 且前面无 `h` 时按分钟解释（对齐 Excel 语义，一行分支）；②检测到该模式整体返回 `undefined` 回退（更保守，与"不承诺完整格式语法"的既有口径一致，但 ExcelJS 对 `mm:ss` 的 text 也未必对，需实测回退质量）。倾向 ①，附测试钉住。
- **结论**：2026-09-26 已按建议修法修复（行内意见 [r4111276109](https://github.com/Shadow-Azure/StudyWiki/pull/41#discussion_r4111276109)，回复 [r4111281266](https://github.com/Shadow-Azure/StudyWiki/pull/41#discussion_r4111281266)）：`formatDate` 在 `component` 判定为 `month` 时做 lookahead——token 结束处跳过分隔符（引号字面串打断）紧跟 `s` 即改判 `minute`；测试先行复现（`"09:09"` vs 期望 `"07:09"`）后修复转绿，`hh:mm:ss` → `"15:07:09"` 钉住无回归；目标测试 16/16、全量 347/348（唯一失败为已知沙箱 EPERM）、tsc 绿。改动在工作树，待随下一次提交推送。

### D2 单元格上限：事后检查 + 声明维度，与"单元格数"措辞有缝

- **位置**：`src/host/excel.ts:47-52`
- **现象**：①上限在 ExcelJS 完整解析**之后**才检查——真正的内存大户（workbook 全量驻留）已经发生了，上限保护的是渲染/模型层而不是解析峰值；②计数是 `rowCount × columnCount` 的声明维度乘积，不是实际非空单元格数——一个远端格子留过格式痕迹的近空文件会被判"过大"拒绝。
- **问题**：Note 写"超大文件设单元格数上限（约 100 万）"，与实现语义有两道缝（事后 vs 事前、声明维度 vs 实际单元格）。ExcelJS 无流式读，事前检查在当前选型下做不到；声明维度是 cheap 且确定的上界，误拒方向是"宁枉勿纵"，安全方向正确。
- **预判**：设计内代价，倾向不改代码；建议把语义如实写进 Note 的 Consequences 或错误信息（如"按声明维度计"），避免将来有人拿"实际才 100 行"来报 bug。真要解需换流式解析，那是另一个选型决策。
- **结论**：2026-09-26 已按建议修复（行内意见 [r4111285144](https://github.com/Shadow-Azure/StudyWiki/pull/41#discussion_r4111285144)，回复 [r4111288253](https://github.com/Shadow-Azure/StudyWiki/pull/41#discussion_r4111288253)）：错误信息改为“按声明维度累计”，`read` 契约注释精确化，owning Note 中英 Consequences 补明解析后累计/保护渲染驻留/近空文件计入三重语义，i18n 已重录；lint:docs 13 叶绿、目标测试 16/16、tsc 绿。改动在工作树，待随下一次提交推送。

### D3 dep-audit 对裸内建引用失明：exceljs 的 node 入口不在扫描视野内

- **位置**：`scripts/verify-dep-audit.mjs:6`（正则只认 `"node:xxx"` 带引号前缀形态）
- **现象**：exceljs 的 node 入口（`main: ./excel.js`）含裸 `require("fs")`/`require("stream")` 等内建引用——没有 `node:` 前缀，扫描零命中，门禁绿。当前安全成立靠的是另一条链：Vite 按 `browser` 字段把 `exceljs` 解析到 `./dist/exceljs.min.js` 预构建包，node 入口从不进产物（本检视实测 dist 产物无 `require("fs")` 残留，构建绿）。
- **问题**：环境无关性的这条防线实际是"browser 字段解析正确"在扛，门禁本身看不见裸内建引用。若未来升级/换包导致 browser 解析失效（比如某包只有 node 入口），dep-audit 不会红，要等问题漏进产物才暴露。当前无实害。
- **预判**：修法是给 dep-audit 加裸内建扫描（`require("fs")` / `from "fs"` 形态，内建清单有限），命中时按"该包是否经 browser 字段改道"分流——误报面需要小步试。也可接受现状并在 environment-independence.md 登记"browser 字段依赖"这条隐含前提。属防线加固，不阻塞本 PR。
- **结论**：2026-09-26 已按建议修复（行内意见 [r4111296422](https://github.com/Shadow-Azure/StudyWiki/pull/41#discussion_r4111296422)（挂 `dep-allowlist.json` exceljs 登记行——`verify-dep-audit.mjs` 不在 PR diff 内），回复 [r4111301038](https://github.com/Shadow-Azure/StudyWiki/pull/41#discussion_r4111301038)）：dep-audit 新增裸内建扫描（`require`/`from` 两形态 + 40+ 内建枚举），`browserRedirect` 三态分流（无 browser 命中即红 / string 改道非入口跳过、入口自身仍红 / object 整包豁免）；误报面实测为零（仅 exceljs 命中 52 处全部分流）；自测试新增 3 用例 7/7 绿，实包审计绿，全量 350/351（唯一失败为已知沙箱 EPERM）。改动在工作树，待随下一次提交推送。

## 9. 文件级代码分析

### 9.1 `src-tauri/src/lib.rs`（M，+155/−0）— 字节边界与原子写

职责：扩展名分派 + 两条二进制命令 + 原子写 + 测试。变更形态：M，前身只有文本读写命令。

关键依赖：`tauri::ipc::{InvokeBody, Request, Response}` 是 Tauri 2 官方一等 IPC 类型（非社区 crate），raw 请求/响应是 2.0 IPC 重写的主卖点——比喻：从"只能寄信"升级到"也能发包裹"。

变更块：

- `atomic_write`（87-112）：替身文件名带 pid+原子序号+纳秒三层防碰撞；rename 失败清理替身。同目录是同文件系统的前提，rename 原子性才成立——这一点注释没写但实现暗含。
- `decode_path_header`（144-168）：手写 percent 解码（不引 url crate，零新增 Rust 依赖）；不完整序列/非 hex/非 UTF-8 三种坏法各自报错。
- `read_binary_file`（211-219）/ `write_binary_file`（225-243）：`request_path` → `ensure_authorized` → FS——解码与授权永远先于触碰磁盘；write 显式拒 JSON body（233-237）。
- 测试四枚：扩展名分派（342）、原子写无残留（350）、header 解码（410）、JSON body 拒绝。

实现思路：Rust 不理解 xlsx，只做"验明正身 + 搬箱 + 原子落盘"三件事。检视发现：无新增；`atomic_write` 的单测在临时目录真实执行，是本 PR Rust 侧唯一碰真实 FS 的测试。

### 9.2 `src/host/files.ts`（M）— raw 通道封装

职责与机制见 §2.2。变更块：`FilesInvokeArgs`/`FilesInvokeOptions` 类型导出（invoke 签名的最小放宽面）、`normalizeRawBytes`（24-31）、`readBinary`/`writeBinary`（79-90）。

### 9.3 `src/host/excel.ts`（A，66 行）— 第六服务窗口

职责见 §2.3。变更块（全新文件）：
