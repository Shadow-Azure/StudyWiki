## 2. 架构导览

### 2.1 原生层：只有一个带闸门的“指纹窗口”

`probe_file` 先拒绝 `..`，再取 metadata，known 的 size 与 mtime 都一致时直接相信 known SHA-256；否则以 64 KiB 块流式读取并更新 SHA-256（`src-tauri/src/probe.rs:31-83`）。Tauri 命令面在进入纯函数前复用 `ensure_authorized_read`，边界与 `read_text_file` 一致：当前窗口 root + 动态读 grant，且拒用户配置域（`src-tauri/src/lib.rs:631-651`、`279-349`）。这好比所有借阅档案都要经过同一个前台，探测不能开后门。

`std_write` 的变化很小但关键：写前对非空 parent `create_dir_all`（`src-tauri/src/lib.rs:109-116`）。因此 agent 首次写 `.study-wiki/llm-wiki/concepts/rust/ownership.md` 不需要程序预建骨架；如果路径中某层是文件，mkdir 仍失败，不会覆盖。

### 2.2 宿主缝：插件仍摸不到 Tauri API

`FilesService.probeSourceFile` 只是 invoke facade，参数和返回形状带文档注释（`src/host/files.ts:33-41,139-145`）。`ctx.wiki` 进入 Context 声明合并（`src/host/context.d.ts:27-31`），静态模块表把 `app-wiki` 放在 `agent-core` 后（`src/loader/table.ts:11,37-38`）。`verify:layering` 当前全绿，源码层面没有打破“插件禁 import `@tauri-apps/*`”。外置插件服务面另有 §6.4 的契约口径问题。

### 2.3 prompt 贡献缝：每回合现组，不给 loop 增工具

`AgentService` 用 `Map` 保存 provider；同 id 覆盖，注销函数只删除同一个 provider，避免旧 disposer 误删新注册（`src/plugins/agent-core/service.ts:57-79,410-416`）。`send` 在读库根 `AGENTS.md` 后逐 provider 取段，过滤 null/空白，再进入 LLM 回合（`service.ts:297-306`）。`buildSystemPrompt` 把 extras 拼在库约定之后（`prompt.ts:15-40`），顺序与 Note 一致。测试覆盖排序、null 段、id 覆盖与注销（`tests/agent-service.test.ts:457-498`）。

### 2.4 机器索引：程序写卡片，agent 写书

受限 YAML 只接受 `version: 1`、`sources` 列表、固定字段和可选 `page`；CRLF、未知字段、重复字段、坏缩进、非安全整数和坏引号都返回 null（`src/plugins/app-wiki/index-yaml.ts:32-139`）。序列化前检查类型、safe integer 与行中断字符，只转义反斜杠和双引号（`:145-191`）。它不是通用 YAML 解析器，而是“只认自家排版”的收据打印机；这减少了依赖和意外输入面，代价是任何非自家排版都被当作损坏并重建。

`classifySource` 的判定顺序是 path → hash → unknown（`src/plugins/app-wiki/state.ts:34-48`）：同一文件内容变了先判 stale，不会被“别处有同哈希”抢成 moved。`reconcileIndex` 以现存证据为行集合，优先按 path/page/哈希找回旧行；无有效哈希与旧值时丢弃，不写空记录（`:89-127`）。

### 2.5 服务层：证据驱动与 moved 绑定

`refresh` 换 root 时清缓存，读旧索引、递归收集 sources 页证据，再按证据源探测并 reconcile（`src/plugins/app-wiki/service.ts:83-124`）。`collectEvidence` 递归展开目录 `children`，读取每个页面的 frontmatter `source`，并记录实际 page 路径与最新产物 mtime（`:60-80,258-279`）。活动文件在 prompt 构建时探测；moved 直接重写索引 path 并保留旧记录其他字段，然后向 prompt 报 fresh（`:137-175`）。index.md 头部按 80 行或 4 KiB 较小者截断，schema 全文固定在 6000 字符预算内（`:178-188`、`tests/app-wiki-schema.test.ts:5-13`）。

这套设计的关键取舍是“证据”只看现存 sources 页：agent 删除 sources 页，索引行也会消失；agent 写了页面，程序下回合补卡。程序不做骨架初始化，模板知识全部留在 schema。

## 3. 数据流走查

以库根 `/lib`、活动文件 `/lib/notes/rust.md` 为例：

1. **装载**：bootstrap 激活静态表；`app-wiki` inject `agent/files/workspace`，在 agent-core 提供服务后运行（`src/loader/table.ts:11,37-38`）。它发布 `ctx.wiki`，注册 id 为 `wiki` 的 prompt provider，并监听 root/file 事件（`src/plugins/app-wiki/index.ts:13-26`）。
2. **用户发问**：agent-core 先持久化用户消息，读 `/lib/AGENTS.md`，再逐个调用 prompt provider（`src/plugins/agent-core/service.ts:282-305`）。
3. **索引刷新**：app-wiki 读 `/lib/.study-wiki/index.yaml`，递归扫描 `/lib/.study-wiki/llm-wiki/sources`；每个页面读 frontmatter `source`，探测页面与源文件，生成证据并写出/跳过索引（`src/plugins/app-wiki/service.ts:83-124`）。
4. **活动源判态**：`/lib/notes/rust.md` 交给 Rust probe，返回 `{size,mtimeMs,sha256}`；TS 按 path/hash 判 fresh/stale/moved/unknown（`src-tauri/src/lib.rs:631-651`、`src/plugins/app-wiki/state.ts:34-48`）。
5. **prompt 组装**：状态行 +（已初始化时）index.md 有界头部 + schema 全文，拼在库约定之后（`service.ts:126-175`、`prompt.ts:36-40`）。unknown 文本会提示 ingest；unknown 视频会明说等待转录能力。
6. **agent ingest**：模型继续用既有 read/grep/write/edit 工具。首次写深路径时 Rust 自动建父目录（`lib.rs:109-116`）；写操作仍走原审批门，agent 不改 `index.yaml`。
7. **下一回合**：新 sources 页成为证据，程序补写 path/hash/size/page；用户移动源后，同哈希反查命中 moved，索引只重指 path，`page` 让后续刷新仍能认回这条记录（`service.ts:93-118,137-160`）。

这条主线在 macOS/Linux 语义清楚；Windows 分隔符会让第 3/4 步的路径切片失效，见 §6.1。

## 6. 讨论点

### 6.1 Windows 路径分隔符会让机器索引和活动源判态失效【检视新发现，P1】

- **位置**：`src-tauri/src/lib.rs:84-100`、`src/plugins/app-wiki/service.ts:64-79,137-147,199-212,234-237`。
- **现象**：Rust `walk_dir` 用 `item.path()` 生成 `FileNode.path`，Windows 上会自然产生 `\` 分隔符；`toRel` 只接受 `${root}/` 前缀，`collectEvidence` 也用 `${root}/${SOURCES_DIR}/` 字面切片。于是 `C:\lib\.study-wiki/llm-wiki\sources\notes\a.md` 无法转成 `notes/a.md`，`page === null` 直接跳过；活动文件 `toRel` 同样失败，不生成状态行。现有 TS fake 全是 `/` 路径，掩盖了这个契约差异。
- **问题**：PR 声明 Windows Rust CI 全绿，但核心 llm-wiki 数据流在真实 Windows 路径下可能完全无法物化索引或判定源状态。
- **预判**：合并前修。最小方向是在 `read_tree` 返回前统一 catalog 路径为 `/`（同时保证 Rust 命令仍接受混合分隔符），或在 TS 服务边界做 root 后第一个分隔符的相对化与 `\` → `/` 归一；补一个 Windows 形状路径的 service 级 fake 测试。不要只在 `toRel` 补 `\\`，`collectEvidence` 的 sources 前缀切片和 page rel 也要一起钉住。
- **结论**：已决并修复 2026-10-18：采纳 Windows 形状路径修复。PR 行内意见：[discussion_r4306947031](https://github.com/Shadow-Azure/StudyWiki/pull/62#discussion_r4306947031)，修复回复：[discussion_r4306984270](https://github.com/Shadow-Azure/StudyWiki/pull/62#discussion_r4306984270)；使用 `pathe` 统一 `toRel`、sources 根相对路径与 probe 缓存键，并补 service 级 Windows fake（索引 path、page、source rel、活动源状态）。

### 6.2 首次上下文和活动文件切换后会对全部已分析源重哈希【检视新发现，P1/P2】

- **位置**：`src/plugins/app-wiki/service.ts:44-57,60-80,83-124,226-230`、`src/plugins/app-wiki/index.ts:20-21`、`src-tauri/src/probe.rs:56-65`。
- **现象**：`contextSection` 每次先 `refresh`；`collectEvidence` 逐页读取并探测，`refresh` 再对每个证据源 `probeAbs`。服务重启后 `knownSamples` 为空，Rust 只能完整读源并计算 SHA-256。更频繁的是，`file-opened` 事件会调用 `invalidate()` 清空全部 known samples——用户只是打开另一个文件后提问，所有已分析源都要重新全量哈希。后续同进程回合才走 known size+mtime 快路径。
- **发生场景**：库里有 10 个各 2 GB 的已分析视频；重启应用后问一个与 wiki 无关的小问题，LLM 尚未启动，程序先读 20 GB 源文件算哈希。macOS/Linux/Windows 都会受影响，视频库最明显。
- **问题**：设计 spec 明确写“惰性探测——只探活动文件，不扫全库”（`plans/2026-10-18-llm-wiki-design.md:69-83`）；当前实现为了确定性物化索引扫描全部证据，且 `file-opened` 清空全局缓存，发生了未记录的设计漂移。
- **预判**：至少把“活动文件切换不清空全部路径缓存”作为本 PR 小修；对重启/换根后的全量哈希，需要产品取舍：索引可持久化 mtime 以复用 known 快路径，或 reconcile 时只探活动源、非活动旧行凭证据暂保留。若接受全量刷新，应更新 owning Note 的代价与上限，并补“多视频库首回合耗时”实测。
- **结论**：已决并修复 2026-10-18：用户预期只处理打开文件。PR 行内意见：[discussion_r4307058070](https://github.com/Shadow-Azure/StudyWiki/pull/62#discussion_r4307058070)，修复回复：[discussion_r4307087780](https://github.com/Shadow-Azure/StudyWiki/pull/62#discussion_r4307087780)。改为活动源惰性物化：无活动文件不扫库；有活动文件只 probe 该源、更新它自己的行；未打开源行保留；`file-opened` 不再清全量 known 样本。

### 6.3 rootMismatch 会话仍会注入当前库的 wiki 段【设计边界，不修】

- **位置**：`src/plugins/agent-core/service.ts:297-305,438-459`、`src/plugins/app-wiki/service.ts:126-140`。
- **现象**：Agent prompt provider 的输入带 `root: internal.currentRoot`，但 app-wiki 忽略 `input.root`，改读 `deps.workspace.root`。历史会话 header 的 rootPath 与当前 root 不一致时，UI 暴露 `rootMismatch`；但 `internal.currentRoot` 与 agent 工具仍是当前库，wiki 也注入当前库。问题不是工具与 wiki 指向不同库，而是历史会话语义与当前 wiki 混用。
- **问题**：实施计划 Review Focus 要求 rootMismatch 时 wiki 段降级为 null（`plans/2026-10-18-llm-wiki-impl.md:23-30`）；但仅比较 `input.root` 与 `workspace.root` 识别不了 header 旧路径，需要额外传递 rootMismatch。现有测试覆盖 welcome 与库外活动文件，没有 rootMismatch。
- **预判**：旧会话被移动/复制到另一库后继续使用是小众场景；UI 已明确提示原库根不可用。若未来仍要执行计划，应把 rootMismatch 显式传入 prompt provider 再降级，而不是让 app-wiki 猜测。
- **结论**：已决 2026-10-18：接受为设计边界，不修。历史会话保留原库根是正常且有用的审计信息，`rootMismatch` 只是提示该聊天来自另一个库；正常工作流切换库会销毁旧会话并新建当前库会话。旧会话被复制/迁移到另一库后继续使用属于小众场景，UI 提示已足够，不值得为它改变 wiki 注入策略。

### 6.4 “外置插件 guard 白名单不含 wiki/agent”的注释与实现不一致【契约措辞漂移，已提交检视】

- **位置**：`src/host/context.d.ts:27-31`、`src/loader/guard.ts:25-41,64-70`、`src/host/plugins.ts:11-19`、`docs/plugins/contract.md:23-25`。
- **现象**：注释和文档说外置插件可声明的服务只含 files/windows/workspace/slots/plugins/llm，且不含 agent/wiki；实现只按外部模块声明的任意字符串放行服务名，成员白名单只覆盖 workspace/windows/llm，未列服务保持完整方法面。因此外置模块写 `inject: ["wiki"]`（或既有 `["agent"]`）时可以拿到服务对象。guard 不是沙箱，但“inject 即权限声明”的 API 合同与实际不一致。
- **问题**：这里把 `inject` 描述成权限白名单并不准确。Cordis 的 `inject` 是依赖声明，只决定依赖满足后插件何时启动；dsh 甚至允许 `ctx.get()` 在不 `inject` 的情况下读取服务，其信任边界是“是否安装并执行插件代码”。当前 guard 把 `mod.inject` 原样转成 `declared`，因此 `inject: ["wiki"]`/`["agent"]` 会按声明放行；未列服务也没有成员级白名单。真正的问题是“依赖语义”与“外置 API 暴露策略”混写，而不是 `inject` 单独构成安全缺陷。
- **修复建议**：本 PR 至少把 `context.d.ts` 与插件契约改成“`inject` 声明插件依赖的服务”，不再声称白名单不含 `agent/wiki`；若外置 API 确实只开放 files/windows/workspace/slots/plugins/llm，则另设显式服务面 allowlist，在装载或 facade 兜底拒绝 `agent/wiki`。若决定像 dsh 一样开放，则补齐稳定契约与成员级白名单。核心口径：**`inject` 就是依赖声明，不是权限；需要最小暴露面时另设能力门禁。**
- **结论**：已修复并推送 2026-10-18，最终 head `d34b99d`（契约修正 `fd6e432`，回归 `4dafbd2`，owning Note 收尾 `5ffd8a5`，walkthrough 对账 `d34b99d`）。`context.d.ts`、插件契约、README、agent 文档及 Phase 4/AI inference 两份 owning Note 统一为“`inject` 声明依赖，不是权限边界”，`agent/wiki` 标注为内置内部服务、不属于外置 API 承诺；guard 仍按声明暴露服务，并补了“声明即可用、未声明教学拒绝”的回归。对应回复：[discussion_r4307224223](https://github.com/Shadow-Azure/StudyWiki/pull/62#discussion_r4307224223)、[discussion_r4307315353](https://github.com/Shadow-Azure/StudyWiki/pull/62#discussion_r4307315353)。是否增加外置服务面 allowlist 或正式开放 `agent/wiki`，作为后续 API 决策，不把 `inject` 当作权限机制。

### 6.5 索引损坏会丢失 stale 历史，重建后可能把已变更源判 fresh【已接受的设计边界】

- **位置**：`src/plugins/app-wiki/service.ts:89-124`、`src/plugins/app-wiki/state.ts:89-127`、`tests/app-wiki-service.test.ts:266-278`。
- **现象**：正常路径下，索引保存旧哈希，源变化会判 stale。若用户在源变化后手删/损坏 `index.yaml`，旧哈希不存在；服务看到 sources 页证据，探测当前源并把当前哈希物化为 fresh。测试“索引损坏 → fresh 不丢”正是按这一语义通过的。
- **问题**：产物页证明“曾经分析过”，但不能证明“分析后源未变”。索引既是派生物，也是 stale 判断的历史证据；一旦丢失，这部分历史不可恢复。
- **预判**：这可能是接受的设计边界，但应在 owning Note 的 Consequences 中明说“索引损坏重建会放弃 stale 历史”；若不可接受，需要让分析哈希有第二份证据（例如未来 raw 产物或 source 页机器字段），代价是打破当前“agent 页面不含机器索引知识”的干净边界。
- **结论**：已决 2026-10-18：接受为设计边界，不修。该场景需要同时满足“源已变化”和“索引随后损坏/丢失”，概率低且 repair 成本会引入 per-source meta 与双账本一致性问题；保留当前简单索引边界，并把该代价写入 owning Note Consequences。

### 6.6 known 快路径测试没有证明“跳过哈希”【测试缺口，P3】

- **位置**：`src-tauri/src/probe.rs:104-124`。
- **现象**：测试传入的是完整 probe 返回的正确 known SHA-256。即使未来实现忽略快路径并重新哈希，断言仍然通过；它验证了结果一致，没有验证跳过读盘。`hashes_known_content` 也只断言摘要长度，未对照独立已知向量。
- **问题**：PR 的性能主张主要靠代码阅读成立，测试不能防回归。
- **预判**：known 用例改成同 size/mtime 但伪造 SHA-256（如 64 个 `0`），当前实现应原样返回伪造值；再可加一个 >64 KiB 内容的独立 SHA-256 向量。若认为返回伪造值太怪，可用注入/包装读函数计数，但当前纯 `std::fs` 实现下伪造值测试最便宜。
- **结论**：已修复并推送 2026-10-18，head `677dd5d`。PR 行内意见：[discussion_r4307380069](https://github.com/Shadow-Azure/StudyWiki/pull/62#discussion_r4307380069)，修复回复：[discussion_r4307430897](https://github.com/Shadow-Azure/StudyWiki/pull/62#discussion_r4307430897)。`known_fast_path_skips_hash` 改用同 size/mtime、摘要为 64 个 `0` 的 known 样本，断言快路径原样返回伪摘要；size 失配仍断言回到真实摘要。`hashes_known_content` 与 200_000 字节用例分别对照独立 SHA-256 向量，后者跨过 64 KiB 分块边界。变异验证：临时短路 known 快路径后，新用例以“真实摘要 vs 伪摘要”失败；恢复后 probe 3/3 通过。实施计划、owning Note 与讲解站同步更新。GitHub CI 6/6 全绿。

## 9. 文件级代码分析

### 9.1 `src-tauri/src/probe.rs` / `lib.rs`（A + M）

职责一句话：新增一个只做元数据与哈希的读命令，并让文本写命令能创建深路径父目录。旧 `std_write` 直接 `fs::write`；新代码先 `create_dir_all(parent)`，失败保留 OS 错误。旧 prompt/文件面没有探测能力；新命令复用读授权后再进纯 `probe_file`。`sha2` 是既有 Rust 依赖，不是新增供应链；流式读取意味着内存峰值固定在 64 KiB，而不是文件大小。

实现思路：权限判断留在 Tauri 命令层，哈希纯函数可独立测试；known 快路径用 size+mtime 换大文件性能。检视发现：§6.6 测试原先没有真正钉住“跳过读”，已用伪 known 摘要与独立向量补齐；授权与现有读面同源，未发现绕权路径。

### 9.2 `src/host/files.ts` / `context.d.ts` / `loader/table.ts`（M）

职责一句话：把 probe 暴露给内置插件，把 `ctx.wiki` 挂进类型面，并把 `app-wiki` 纳入构建期静态模块表。旧 agent-core 之后模块表结束；新表追加 `app-wiki`，仍是静态 import，无运行时下载。这个缝像插座转换头：插件仍只看见宿主服务，看不到 Tauri 电源线路。检视发现：类型注释关于外置 guard 的说法与 guard 实现有口径差（§6.4）。

### 9.3 `src/plugins/agent-core/prompt.ts` / `service.ts`（M）

职责一句话：给 system prompt 增加可注销的贡献段。旧代码只拼角色、工具纪律、上下文、模式句和 `AGENTS.md`；新代码在 `send` 时逐 provider 收集 extra sections，再由 `buildSystemPrompt` 追加。provider 是异步的，因此 wiki 可以先做 IO；空白/null 被过滤，不给模型留空附录。

实现思路：不动工具声明和 loop 状态机，扩展点只影响 prompt 输入。检视发现：provider 异常会让本回合失败，这对索引写入失败是 fail-loud；rootMismatch 属接受的小众边界见 §6.3。

### 9.4 `src/plugins/app-wiki/index-yaml.ts`（A）

职责一句话：机器索引的受限 YAML codec。旧层不存在；新层定义 `SourceRecord`、`MachineIndex`，解析固定字段和可选 `page`，序列化恒等可回读。它像只打印一种格式的收据机：格式对不上就整张作废，不猜语义。测试覆盖未知字段、缩进、引号转义、CRLF、safe integer、空 sources。检视发现：无新增；重复 path 未显式拒绝，但 reconcile 会按证据重建，实际机器索引不保留重复行。

### 9.5 `src/plugins/app-wiki/state.ts`（A）

职责一句话：无 IO 状态机与索引归并。`classifySource` 先 path 后 hash，保证“源内容变化”优先于“同内容迁址”；`createProbeCache` 只在 size+mtime 一致时复用哈希；`reconcileIndex` 用 path/page/hash 三条线索找回旧行，moved 保留 artifact/analyzedAt，缺有效样本时丢弃。检视发现：同 hash 多记录的 `find` tie-break 已在 Note 登记；无其他新增。

### 9.6 `src/plugins/app-wiki/service.ts`（A）

职责一句话：把文件树、probe、codec、状态机和 schema 组成 `ctx.wiki`。关键新块有三段：`collectEvidence` 递归 sources 页并读 frontmatter；`refresh` 产物证据物化索引；`contextSection` 判活动源、处理 moved、拼状态/index 头/schema。它像编目员：不替作者写书，只检查书是否存在并更新卡片。

实现思路：索引是派生物，agent 只维护页面；`page` 字段解决 moved 后页面 frontmatter 仍指旧路径的持久绑定。检视发现：§6.1 Windows 路径切片、§6.2 全量哈希已修；§6.3 rootMismatch 按用户决定保留；损坏索引重建的历史语义见 §6.5。

### 9.7 `src/plugins/app-wiki/index.ts` / `schema.ts`（A）

职责一句话：插件入口与 LLM 行为契约。入口提供 `ctx.wiki`、注册 prompt provider，并在卸载时注销事件与段；schema 常量约 3.6 KB 文件、实际常量低于 6000 字符预算，覆盖 frontmatter、三流程、视频欠账和“不手改机器索引”。检视发现：`file-opened` 清空全部 probe 缓存导致 §6.2；其他生命周期主路径有测试。

### 9.8 测试（A/M）

新 app-wiki 测试共 4 个文件，分别钉 codec、schema 预算/关键词、服务状态和纯 reconcile；agent 测试补 prompt provider 排序/覆盖/注销。相比旧实现，测试把“真实递归树”和“moved 双回合/重启/再变更”补进来了，正好覆盖此前打包冒烟发现的两个 P1。检视发现：Windows 形状路径与活动源惰性边界已有回归（§6.1、§6.2）；probe 快路径测试原先不能证明跳过哈希，已由伪 known 摘要与独立 SHA-256 向量补齐（§6.6）；rootMismatch 保留为小众设计边界（§6.3）。
