# 四层叙事写作规范

## feature：这个 PR 实现了什么

**回答三个问题**，顺序固定：

1. 现在用户能做什么（一句话能力描述，动词开头）
2. 之前缺什么 / 为什么值得做（动机，从 issue 与 note 提炼，不抄原文）
3. 影响面（谁会感知到：哪些操作、哪些场景、哪些边界变化）

**通俗性标准**：假设读者不知道任何内部模块名。第一次提到模块/服务/协议时，用括号一句话解释它在本 PR 里的角色。**禁止**出现未解释的缩写。

**禁止**：实现细节（属方案设计与代码地图）、变更过程叙述（"本次重构了…"→ 改成现状式"现在 X 由 Y 负责"）。

## userFlow：用户怎么操作

每一步一行，格式：`在 <入口> <动作> → <系统做什么> → <用户看到什么>`。

- 3-6 步为宜；超过 6 步说明功能该拆页或用子流程图
- 必须包含：主路径、至少一条边界/错误路径（如超限、无权限、能力不足时用户看到什么）
- 步骤之间可插入图（见 diagram-guide）
- 纯开发流程 PR（无用户面变化）写单行：`无用户面变化（<一句原因>）`

**自检**：拿这组步骤给没见过该功能的人，他能照着走一遍。走不通就是写失败了。

## architectural：架构变化

**先分两类，再写**：

- **结构变化**：新增/移动/删除了模块、接口、数据通路、所有权。每条写：变更点 → 现在归谁负责 → 为什么挪（链 Agent Note，不抄全文）。
- **语义变化**：既有结构不动，但行为/边界/时序变了（如缓存策略、错误分类、守卫条件）。每条写：旧语义 → 新语义 → 触发条件。

没有变化就写：`无结构变化；<一句说明为什么这个 PR 不需要动架构>`。**不许空着，不许写"无"就完事**。

**分层建议**：从外到内（用户面边界 → 模块间契约 → 模块内关键机制），每层 1-3 条。跨模块关系变化必须配图。

## design：方案设计说明（可选但强烈建议）

模板（四段，段落标题用 markdown 三级标题）：

### 问题与约束
- 要解决的核心矛盾是什么；硬约束（离线、安全边界、平台、既有契约）列清

### 候选方案
- 2-3 个真实考虑过的方案（从 Agent Note 的被否方案提炼；没有就诚实写"直接方案，未考虑替代"并说明为什么不需要）
- 每个候选一段：怎么做 → 优点 → 代价

### 选型与理由
- 选了哪个、为什么、放弃了什么（这是本节的核心价值）

### 关键权衡与边界
- 明确说清：牺牲了什么换来了什么；已知不处理的情况；后续演进方向（如有）

**写作标准**：让读者读完后能回答"如果我来做，我会做同样的选择吗"。这是检视者判断设计合理性的主要依据。

## 通用禁令（四层共用）

- 不写"本次""新增了""原来""之前"——渲染产物是长期页面，不是 PR 描述（diff 语义已在代码地图）
- 不用感叹号、不用营销词（"强大""优雅""完美"）
- 数字带单位；行数引用写"约"，除非来自门禁精确计数
- 中英混排：中文句子内的英文术语两侧加空格
