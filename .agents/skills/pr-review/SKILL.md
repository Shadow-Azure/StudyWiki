# PR 结构化检视

对 **$ARGUMENTS**（缺省：当前分支对应的 PR）执行以下流程。全程中文。检视文档落 `plans/`（语料之外，无双语 / 预算 / 骨架门禁义务）；若 `plans/` 下已有同体例的检视文档，沿用作模板保持一致。

## 核心诉求：通俗易懂、举例说明，辅助用户理解变更

检视文档的第一使命不是罗列事实，而是让用户**读懂这个 PR 在做什么、为什么这么做**。后续所有步骤、章节、汇报均服务于此：

- **通俗易懂**：抽象机制配一个生活化比喻（如“传话员 / 插座 / 公告板”这类），术语首次出现给一句白话解释，不堆术语墙
- **举例说明**：论断跟着具体例子走——真实调用链、真实交互场景、真实的“输入 → 输出”；讲“这是什么”之前先讲“你什么时候会碰到它”
- **辅助理解**：分析落在实现思路层面（为什么这么设计、取舍是什么、放弃了什么），不是复述代码；用户读完应能回答三个问题——这个 PR 解决什么问题？怎么解决的？代价是什么？

## 第一步：收集事实（不靠记忆，全部实测）

1. `gh pr view <N> --json title,body,baseRefName,headRefName,additions,deletions,changedFiles,state`
2. `git diff --name-status <base>...<head>`——逐文件 A/M/D 状态；开头统计“共 X = 新增 A + 修改 M + 删除 D”
3. PR 描述里的验证声明与人工验收清单原样提取
4. 读 `docs/AGENTS.md` 与 `.agents/notes/README.md`——检视产出的分流规则以它们为准

## 第二步：通读关键源码

- 按变更的核心数据流通读主线文件（入口 → 各层 → 底层壳），行号锚点必须来自实际 Read，不估
- 第三方 / 框架行为主张必须实测：包数据用 `gh api repos/<owner>/<repo>` + `npm view` + tarball 解包扫描依赖面；框架行为语义（如事件监听、生命周期包装）翻 `node_modules` 里的实际源码核实，不凭记忆下结论
- 未读完的文件在导读地图里标 ◻，不假装读过

## 第三步：生成检视文档 `plans/yyyy-mm-dd-pr<N>-review.md`

结构（体例，各节按 PR 实际情况裁剪）：

- 元信息：检视对象 / owning Note / 实现计划 / 日期
- §0 变更文件树与职责：按架构故事排序，每组标 A/M 计数 + 每文件一行职责，成组文件（双语三件套 / vendor 源码 / 测试）折叠
- §1 一页速览：一句话 + 一个比喻 + 交付块表 + 验证基线
- §2 架构导览：分层小节，论断带 `文件:行号` 锚点；支撑性基础件（注入缝、类型声明、微型工具）也要讲清机制
- §3 数据流走查：一条端到端主线剧本（启动 → 核心交互 → …），每步带锚点
- §4 导读地图：分层文件表，✅ 已通读 / ◻ 待细读，检视过程实时更新
- §5 人工验收清单：从 PR 描述提取，checkbox
- §6 讨论点：每条固定五段——**位置**（file:line）/ **现象** / **问题** / **预判**（初步看法，供拍砖）/ **结论**（留空给用户拍板）；新增讨论点同步登记 §7
- §7 分流表：发现 → 定性 → 去处 → 状态（已决的标 ✅ 并写明日期与理由）
- §8 链接：PR / owning Note / 实现计划 / 后续 PR
- §9 文件级代码分析（逐文件累积，体例见下）

## §9 单文件体例（变更代码块驱动，用户要靠它理解实现思路）

1. 职责一句话 + 变更形态（A/M/D；M 的前身用 `git show <base>:<path>` 拉出来对照）
2. 关键依赖解读：第三方包讲清“官方第一方还是社区 / 构建期打包还是运行时加载 / 在本文件干什么”，配一个帮助理解的比喻
3. 变更代码块分析：**旧代码 vs 新代码对照块**，每块讲“这在做什么、为什么这么写”（讲变更，不是复述最终文件）；实现思路总结 ≤ 三行
4. 检视发现：无发现也明说；已知弱点写明根源与接受理由

## 检视纪律

- **不替用户拍板**：讨论点给预判不给结论；已决事项记录日期、理由、实测数据留档（将来重评估的起点）
- **分流口诀**（以 docs/AGENTS.md 为准）：bug → 修复 PR / postmortem；理由与取舍 → 更新 owning Agent Note（不建重复）；步骤 → development.md；现状 → docs；过程记录 → 本检视文档。检视报告本身**不进** `.agents/notes/`（那是封闭的决策记录系统，类目 / 骨架 / 双语三件套都不是为它设计的）
- **新增依赖类提议**：先过本仓库环境无关硬约束（dep-allowlist 白名单、零 `node:` 引用、构建期可打包、tarball 实测），再谈 API 契约匹配与长期维护成本
- 框架级隐患要指明修法与建议归属阶段；当前无实害的发现如实标注“无实害”，不制造紧迫感

## 第四步：汇报

向用户输出：文档路径 + 最值得先讨论的 2–3 个点（一句话理由）+ 建议下一步（跑人工验收 / 逐条拍板 §6 / 继续钻 §4 的 ◻ 文件）。用户在会话中逐条拍板的结论，实时回写 §6 结论栏与 §7 分流表。
