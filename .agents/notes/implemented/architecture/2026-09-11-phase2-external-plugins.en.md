# Agent Note: Phase 2 external plugins: registry pull + local import + load-time validation

Status: implemented

English | [中文](2026-09-11-phase2-external-plugins.md)

## Problem

Phase 1 delivered static loading of built-in plugins (module table + JSON manifest + fail-loud audit), but the product has no external plugin capability: third-party authors cannot distribute plugins and users cannot install them. The hard constraint is environment independence — no Node, no network runtime, no package manager on user machines; the solution was pre-registered in Phase 1 ([environment-independence.en.md](../../../../docs/environment-independence.en.md) clause 5: the install action may go online and is limited to direct registry tarball pulls; runtime stays fully offline; everything is a prebundled zero-dependency single file and the host refuses any other shape). Three debts block the start: the overly broad `assetProtocol.scope: ["**"]`, the unverified CSP/custom-protocol loading channel, and the missing legacy-manifest migration (same document, known-debts section).

The Phase 1 whole-branch final review also left four ride-along debts: the layering scanner's no-whitespace import blind spot, the white-screen boot failure (external load failures need a visible outlet), the missing dep-audit/layering entries in the single home, and 32 deferrable minors (triage recorded with PR #14).

## Decision

Scope: **this phase = the full external-plugin chain** (install/import/load/validate/manager panel) + closing the three prerequisite debts + the three ride-along debts; file watching (notify), cross-window same-file staleness, dep-audit symlink following, and the remaining minors stay out. Guiding rule: the host uses npm as a repository, never as a runtime — installation is a one-shot Rust-side networked action; loading is offline local-resource reads at runtime.

1. **Loading channel (prerequisite; a technical verification decides)**: dynamic `import()` of the external single-file ESM inside the webview. Two candidates: a Tauri custom protocol (Rust registers a `plugin://`-style protocol serving the plugin directory) vs a blob URL (a Rust command reads bytes → JS-side Blob → import). The first task runs a real-channel verification (dev and build forms, darwin WKWebView); **custom protocol preferred, blob URL as fallback** (pre-approved by the Phase 1 Note). Once decided: CSP `script-src` gains the corresponding source (the protocol or `blob:`); networking happens only in the Rust install action — the webview CSP opens no connect-src at all. `src/loader/external.ts` becomes the frontend's only dynamic import point — the first seam ever opened in `layering-allowlist.json` (single-file registration; widening requires revising this Note).

   **Landing decision (2026-09-11)**: the channel is blob URL — the single-file zero-dependency contract drives the blob's weaknesses (relative-import resolution, URL lifetime) to zero, and the channel is testable end-to-end in vitest/Node with an injected fake import; custom-protocol ESM loading can only be verified in a real webview and stays reserved as a pre-approved fallback. CSP `script-src` gains `blob:`, with no connect-src opened. The technical-verification task is absorbed by this ruling (both candidates are pre-approved forms; the ruling only picks one).
2. **Rust package-management commands** (global state lives in Rust): `install_plugin(spec)` (spec = `name` or `name@version`: fetch registry metadata → download dist.tarball → sha512 verify (npm dist.integrity, base64) → extract → validate format (item 3) → place under `app_config_dir/plugins/<name>/`), `import_plugin(path)` (local tgz, same pipeline without network), `list_plugins()` (directory scan + package.json metadata), `remove_plugin(name)` (delete directory). HTTP/TLS/gzip/tar/sha512 all on a pure-Rust stack (rustls family; system OpenSSL dylibs forbidden — `verify:native-links` is the mechanical watchdog; concrete crates belong to the implementation plan). Registry is fixed to public npmjs; no built-in mirror configuration (user-side variance goes to system-level proxies).
3. **External plugin format (closed contract)**: the tgz must contain exactly `package.json` + a single entry `.js` (ESM); the `package.json` declares `"studywiki": { "apiVersion": <number>, "entry": "<file>" }`, has `"studywiki-plugin"` in `keywords`, and an empty `dependencies` object (zero deps). The host support set is currently `{1}`; an apiVersion outside the set → refuse to load. Any mismatch → reject at install time (fail-loud, naming what is missing); never guess from a broken package.
4. **Second loader source**: at boot, scan the plugin directory via a command; external modules load through the channel via dynamic import and merge with the static built-in table into the same flow (same `ctx.plugin`, same activation audit). Manifest row ids are namespaced: built-in ids unchanged, external always `ext:<name>`. **Missing resources vs malformed shapes are treated differently**: a malformed manifest row still throws per existing validation; a missing plugin directory or broken entry → that row is skipped, named in the panel as "needs cleanup", and does not block the remaining plugins (external resources are user-side state and must not keep the whole app from starting).
5. **Legacy-manifest migration**: when `loadManifest` reads an existing manifest, it merges built-in rows that are new in the static table but absent from the manifest (enabled defaults to true, matching first-run — a version upgrade bringing new built-ins is an in-design change under the behavior-consistency clause) and writes it back. External rows are never migrated or guessed; the plugin directory is the source of truth.
6. **assetProtocol tightening** (debt closed; the approach pre-registered in the single home): the configured scope shrinks from `["**"]` to empty; when the user picks a folder or a window is created carrying a root, Rust dynamically injects that directory (recursive); video and images keep using the asset protocol.
7. **Host service `ctx.plugins`**: a PluginService wraps the four package-management commands plus channel module loading (install/import/list/remove/loadModule) — external plugin management and loading go through the host service; `src/plugins/**` layering discipline has zero exceptions. plugin-manager is its only consumer (within Phase 2).
8. **plugin-manager built-in plugin** (the sixth, minimal management surface): a topbar button → a panel listing installed (built-in + external), install by name, local import, enable toggles, external deletion; every change writes the manifest and then **prompts a restart to take effect** (Phase 2 does no hot loading — cordis natively supports runtime ctx.plugin, but the simplest correct shape for audit/manifest consistency is restart-to-apply; hot loading is left to a later phase). Needs-cleanup rows (item 4) get a one-click remove in the panel.
9. **Minimal boot error panel** (M1 closed; the visible outlet for external load failures): when bootstrap rejects, render the error text inline into `#app` with cleanup guidance instead of a white screen; errors still go to console.
10. **Gates and doc chain**: fix the layering no-whitespace import blind spot (`import{x}from"…"` form — complete the scanner before opening the loading seam); environment-independence gains the dep-audit/layering mechanical-gate entries (M2), the "external plugin install networking" exemption flips from pre-registered to active, and the known-debts section drops the three items this Note closes; architecture trio (composition tree + external-loading dataflow + decision table), commands generated region (new commands carry doc comments), code-map, and this Note itself closing out to implemented. Rust dependency changes naturally land in the existing route:gates `src-tauri/` surface (native-links included).

## Alternatives considered

- **npm/pnpm runtime install (DSH as-is)**: rejected in the Phase 1 Note — requires Node ≥22 + pnpm + network on user machines, three direct hits against the iron law; unreviewed postinstall code execution. Not reopened.
- **Local import only (no registry download)**: safest but gives up name-based distribution convenience; registry pull gets both convenience and zero runtime by "using npm as a repository". Local import stays as a second entry point, not the only one.
- **WebWorker/iframe sandboxed loading**: better isolation, but host API injection (ctx.* straight to DOM/slots) becomes far more complex and breaks the one-contract-two-habitats premise; same-process full authority is the established trust model (the Obsidian precedent recorded in the Phase 1 Note), with apiVersion + zero deps + single file as the current defense line. Sandboxing waits for a phase with real malicious-plugin governance needs.
- **Hot loading (activate on install, no restart)**: cordis supports it natively, but the simplest correct answer to manifest write-back consistency, failure rollback, and multi-window sync is all "see you at next boot"; Phase 2 trades restart for correctness and leaves hot loading until there is a real pain point.
- **Legacy migration with enabled defaulting to false (conservative)**: upgrading users would "silently miss" new built-ins and fork away from first-run behavior, manufacturing two initial states; true matches "same version + same plugin set → same behavior" (a version upgrade swapping the plugin set is an in-design change).
- **Opening CSP connect-src so the webview downloads directly**: drags networking into the render layer, against the pre-registered "networking only in the Rust install action" clause; downloads must go through Rust commands.

## Consequences

- Runtime stays offline; the install action becomes the product's first user-visible networked point (the exemption registry entry goes active).
- The loading seam goes from zero to one: `src/loader/external.ts` is the frontend's only dynamic import; the single-entry allowlist is itself the assertion; any second seam must revise this Note with justification.
- External plugins run with same-process full authority: apiVersion refusal + zero deps + single-file format is the entire defense line; the author side guarantees format via prepublishOnly auto-build (distribution contract in the Phase 1 Note); malicious-plugin governance is not promised in this phase.
- Upgrading users' legacy manifests automatically gain new built-in rows (enabled true); external rows treat the plugin directory as source of truth — a directory deleted first shows up as needs-cleanup in the panel.
- If the technical verification lands on blob URL (custom-protocol ESM loading failing on WKWebView), CSP gains `blob:` and this Note records the actual channel and reason when it lands as implemented — both candidates are pre-approved forms; the verification only picks one.
- The three known debts close; one new debt is expected: the linux-side ureq/rustls link scan awaits the first real release verification (the native-links allowlist covers the system C runtime; a pure-Rust stack should add zero dylibs in theory).
- File watching, cross-window staleness, symlink following, and the remaining minors stay parked; triage is archived with this Note's PR description.
- Authorization-residue limitation: asset authorizations injected via `allow_directory` are add-only (no un-allow API) — a window closing, a root change, or a create-window rollback leaves old directories authorized, and the scope is shared app-wide; the "single authorization point" narrows the injection surface, not revocability — a known limitation.
