# Agent Note: Phase 4 dynamic loading and guard tightening

Status: implemented

English | [中文](2026-09-16-phase4-dynamic-plugins.md)

## Problem

Phases 1–3 built the "persistent ecosystem": npm supply chain + closed-contract directories + restart-to-activate (the [Phase 2 Note](../../implemented/architecture/2026-09-11-phase2-external-plugins.en.md) traded restart for correctness, leaving three debts: manifest consistency, failure rollback, multi-window sync). The Phase 4 direction was ratified in [pr15 review §6.11](../../../../plans/2026-09-13-pr15-review.md): dynamization plus mandatory guard tightening. Against the current state there are four concrete pain points: (1) changing an external plugin's code, toggling it, installing, or removing it all require an app restart — the debug inner loop is cut by restarts; (2) boot's fixed 50ms tree-wide audit covers only startup loads, so any runtime load bypasses the audit; (3) the inject declaration is an honor system — an external plugin's apply receives the real ctx and can reach services it never declared; the facade is not a boundary; (4) once AI-agent-written plugins arrive (ratified 2026-09-16 as out of this phase, to be developed separately), "stranger code enters the app at any time" becomes the norm, and without version history there is no rollback backstop. This phase delivers the minimal complete dynamization loop: a persisted version store + single-entry panel-wide instant activation + a guard whitelist facade + a runtime activation audit, plus two resident documents (how to write a plugin / how dynamic loading works), laying the foundation for the agent phase.

## Decision

Scope (ratified item by item by the user on 2026-09-16): **full version-store semantics (multi-generation + persisted) + all hot paths made instant (reload/toggle/install/remove — scope C) + guard wrapping external plugins only + fiber-waiting audit + two new documents under docs/plugins/ (three-piece sets). The AI agent, the runtime network exemption, key storage, cross-window hot sync, and a true in-process sandbox are out of scope; the skill is deferred (the two documents are written so an agent can consume them directly; a future skill merely wraps them).**

1. **Persisted version store (snapshot store + rollback-by-write-back)**: the live `plugins/<name>/` directory stays as-is (boot path, closed contract, and install pipeline untouched); a new `plugins/.history/<name>/<timestamp>-<first-12-of-sha256>/` holds one generation each — `package.json + entry source + meta.json` (created-at, npm version, apiVersion). One snapshot rule: **snapshot after every successful activation** — a new Rust `snapshot_plugin_version` command is invoked after the audit passes on all three paths (boot activation, hot reload, install-and-activate); content-hash dedup (reactivating identical code mints no new generation); keep 10 generations per plugin, pruning the oldest, with same-second generations ordered by a strictly increasing stamp (`created_at` is monotonic). Rollback = pick a historical version in the panel → `restore_plugin_version` reuses the atomic-replace pipeline to write it back into the live directory → activate via hot reload when the row is enabled (a disabled row only lands it on disk, taking effect at the next activation) → the post-success snapshot dedups onto the same generation. Removing a plugin also removes its history (noted in the panel confirmation), so a same-name reinstall does not resurrect history.
2. **All hot paths instant (this window live, other windows on restart)**: a new `src/loader/activate.ts` shared activation function (load checks → guard wrap → ctx.plugin → fiber-waiting audit → snapshot), shared by boot's ext: rows and every hot path. Four hot paths: **reload** (re-read source through the blob seam; only after all checks pass is the old fiber disposed and the new one activated — validate-then-switch; on failure the old version keeps running and the row reports the error inline); **instant toggle** (fiber.dispose / re-activate + manifest write); **install/import-and-activate** (after the pipeline lands, the manifest gains an enabled row and this window activates; on failure the row becomes a broken row — directory and manifest kept, panel names it, next boot retries; writing that manifest row also closes the Phase 2 gap where panel-installed plugins had no manifest row and were never loaded after a restart); **instant removal** (dispose + delete directory + delete manifest row + delete history, in one action). Concurrency discipline: operations on one plugin serialize on a `Map<name, Promise>` chain (the equivalent of dsh's starting table), preventing interleaving from rapid clicks; the shared activation function itself stays outside the queue (reload calls it from inside its own serialized block, so nesting on the same key would deadlock) and the install path wraps it in an explicit `serialized`. The manifest stays the cross-window source of truth: panel changes are written immediately, other windows follow on next boot; the panel drops the "takes effect on restart" hint and gains a standing note: "changes take effect in this window immediately; other windows follow the manifest on restart."
3. **Guard whitelist facade (external plugins only)**: a new `src/loader/guard.ts`, ported from dsh's `cordis-client-runner/guard.ts` Proxy pattern. After shape validation, an external module is wrapped: the ctx its apply receives becomes a facade Proxy — it allows only the service names declared in inject (the lifecycle-verb whitelist was cut at implementation: built-in plugins, host services and the generated template have zero call sites, so the narrower surface is strictly safer); reading an undeclared service throws a teaching error (naming "declare 'xxx' in inject"); assignment is forbidden; a cordis Context returned directly from a service method (including as a resolved promise value) is denied — one nested in a container is not deep-scanned. Built-in plugins are not wrapped (first-class citizens, loaded from the static table). **Honesty about the boundary**: the facade narrows the service surface, not language capability — external plugins can still reach the DOM/fetch/globals; the docs and this Note state plainly "this is not a sandbox; a true in-process sandbox remains parked." `verify:layering` gains a scan: `ctx.plugin(` may appear only in the two loader files, and activate.ts must call `guardExternalModule`.
4. **Runtime activation audit**: hot paths replace boot's fixed 50ms silence with a fiber-waiting audit — after ctx.plugin, poll fiber.state (10ms interval, 2s budget); reaching ACTIVE is success. On timeout or error, dispose the half-built fiber and quarantine per path (reload keeps the old version / install becomes a broken row). **The waiting state gets no separate panel state**: when the 2-second ceiling hits, the row turns into a failure row naming "the declared service is not provided" rather than sitting silently stuck. Boot's 50ms audit keeps covering built-in rows only.
5. **Panel (plugin-manager) rework**: external rows expand to version history (short hash + time + npm version + whether current); row actions: reload / roll back to this version. The row state projection grows from three sources to four (adding this window's runtime state): running / disabled / load failure (reason) / pending cleanup (a broken row offers removal only — reload and history appear on healthy rows, since a broken directory cannot pass load checks anyway).
6. **New Rust command surface**: three commands — `snapshot_plugin_version` / `list_plugin_versions` / `restore_plugin_version` (doc comments complete → `pnpm gen:commands` + record:i18n); hashing uses sha2 (dependency already present); after the install/import pipeline succeeds, the front end calls the snapshot from the activation-success callback, leaving existing Rust paths untouched.
7. **Two-document set (docs/plugins/, three-piece sets + budget registration)**: `contract.md` (**how to write a plugin** — the single-file contract in the dynamization era: the name/apply/inject triad, inject as the permission declaration, what the facade makes unreachable, failure handling and broken-row semantics, apiVersion); `dynamic.md` (**how dynamic loading works** — the behavioral contract of reload/version store/rollback/toggle/removal, this-window-live-other-windows-on-restart, audit semantics, and the honest guard-boundary statement). `authoring.md` gets a minimal cross-link touch-up (its npm supply-chain view unchanged); `docs/architecture.md`'s data-flow section gets a one-sentence minimal update for the external path + code-map regeneration. The corresponding items in `plans/2026-09-13-phase4-worklist.md` are checked off (the W1/W2 startup-performance items are not covered by this Note).
8. **Gates and environment independence**: zero new npm/Rust dependencies (dep-audit allowlist untouched); fully offline, zero network (exemption registry untouched); release-product behavior changes only in the panel and the loading path, with the full `verify:release` lane green.

## Alternatives considered

- **Pointer-based version store (dsh as-is)**: the live directory holds no code, the manifest records an activeVersion pointer, and boot reads from the store. It touches the closed contract, the boot loading path, and the install pipeline, and the plugin directory stops being self-contained (manual backup/sharing yields an empty shell). Keeping the disk as the single source of truth and the store as append-only history is simpler; dsh pointers exist because everything there lives in memory and the store must be the source.
- **dsh's full run/update dual-pointer + mode-exclusion semantics**: with the disk as the single source of truth, "write back to switch" already covers every scenario (current = live directory content; switching = one write-back + reload action); dual pointers would add manifest fields and a panel state machine whose complexity buys nothing here. Left to be re-added when real pain arises.
- **dsh closure evaluation + CSP unsafe-eval**: already ruled out in pr15 §6.11; the blob loading seam (source string → real ESM module) has stronger semantics and does not touch CSP.
- **Cross-window hot sync (other windows instant too)**: the minimal correct answer to the Phase 2 trilemma (manifest consistency / failure rollback / multi-window sync) remains "other windows see it on restart"; the narrowed single-entry panel form is the compromise and is not reopened in this phase.
- **Keeping install restart-gated (not reopening the Phase 2 ruling)**: rollback and consistency backstops were missing then; with the version store + validate-then-switch + broken-row quarantine in place, install-and-activate failures have somewhere to go, and the user ratified reopening it (scope C) on 2026-09-16.
- **Wrapping built-in plugins in the guard facade too**: more consistent, but guarding against ourselves buys nothing and would rewrite every built-in plugin's ctx usage — a large diff with regression risk; the trust split (built-in full trust / external facade) stands on its own.
- **A true in-process sandbox (iframe/worker isolation etc.)**: stays parked. The facade delivers discipline and auditability, not containment; the docs disclose this honestly, leaving no "already secure" illusion.

## Consequences

- The external-plugin ecosystem moves from "restart to take effect" to "instant," removing the author inner-loop and user-experience break; the manifest becomes the final source of truth written by this window and read by others.
- The version store is append-only data and never activates anything by itself — after a restart the only activation basis remains the manifest's enabled rows, and rollback is always an explicit act by a person (or the future agent). The "restart is a clean slate" property is preserved by the manifest toggle.
- The guard facade is API discipline, not a security boundary: dynamization turns "a real need to govern malicious plugins" from a parked premise into a live requirement; this phase delivers the narrowed service surface + teaching errors + audit visibility; the true-sandbox debt remains, see Alternatives.
- Debt list (later phases): cross-window hot sync; a true in-process sandbox; two of the four agent-phase prerequisites (the runtime network exemption, key storage) ship with the agent itself; schema-based config validation (the zod base is already in the host); version diffing/annotation and other store refinements.
- The two documents are written to an "AI-agent-consumable" standard (contract first, runnable examples, failures named verbatim); the future built-in agent's plugin-authoring ability = reading these two documents + the panel command surface, with a skill as mere packaging.
