# Agent Note: llm-wiki compiled knowledge layer

Status: implemented

English | [中文](2026-10-18-llm-wiki.md)

## Problem

The agent already had generic read, write, search, and approval capabilities, but knowledge remained scattered across sources and conversations. Repeated reading, stale conclusions after source edits, and later video timestamp questions all lacked a verifiable compiled layer. The knowledge layer had to define where the schema lived, how the agent received it, how the program classified source state, how a derived index avoided manual registration gaps, and how moved sources retained artifacts without re-analysis.

## Decision

- Schema v1 ships inside the `app-wiki` plugin and is not copied into a library; the same version and plugin set produce the same LLM behavior contract.
- `AgentService.registerPromptSection` provides id overwrite, registration-order concatenation, and an unregister function; the schema is appended after library conventions.
- Ingest/query/lint remain conversation-driven; the agent maintains `.study-wiki/llm-wiki/` only through the existing read/grep/write/edit tools.
- The machine index is separated from the LLM-maintained layer: `.study-wiki/index.yaml` is a program-owned data file, `llm-wiki/` is the readable wiki output, and raw artifacts wait for m3.
- index.yaml uses a fixed-field, LF-only restricted YAML subset; no yaml dependency is added, parse failure is treated as corruption, and the index is rebuilt from artifact evidence.
- Source classification is fixed as same-path fresh/stale, same-content-hash moved, otherwise unknown; path precedes hash so a moved source cannot be misreported as merely duplicated.
- `probe_source_file` streams SHA-256 inside the authorized root; a known size+mtime hit reuses the hash, while a miss rereads the content.
- `write_text_file` creates parent directories automatically so the agent can create deep concepts/entities paths while preserving file-component conflict failures.
- An index row exists only when surviving sources artifacts provide evidence; with no artifacts and no prior index, refresh leaves the library untouched instead of creating an empty index file. Reconcile preserves old kind/hash/artifact where possible, and moved only re-points path to the new location.
- `ctx.wiki` refreshes the index before building context; root changes and file opens invalidate the probe cache, and plugin teardown unregisters the prompt section.

## Alternatives considered

- Markdown plus a YAML fence for the machine index: the document wrapper invited accidental edits, so it became the pure data file `index.yaml`; `index.json` is less human-readable and was not chosen.
- Schema in a library file: the library copy drifts and violates same-version behavior consistency; rejected.
- Dedicated wiki_ingest/query/lint tools: open-ended writing is hard to parameterize and would overturn the generic-tool consensus; rejected.
- A separate wiki plugin with a task queue and vector index: over-engineered, and the vector index conflicts with environment independence; rejected.
- Programmatic skeleton initialization: the program would learn wiki page templates; the agent writes first according to the schema, keeping the contract in one place.

## Consequences

- The index contracts of #31 and #34 are merged: #31 lands `index.yaml` and content hashing first, while #34 later focuses on raw artifacts and field extension; its “md5/index.md” wording becomes “content hash/index.yaml.”
- m4-01 depends on source-page topic mappings and raw topics; m4-02 depends on frontmatter, wikilinks, and append-only log semantics.
- Debts remain: ingest batch writes still use per-file approval cards; mechanical lint, schema override merging, and tie-breaking for identical evidence/hashes are not implemented; plugin teardown covers the main path but does not assert each event, prompt-unregister, and cache-clearing channel.
